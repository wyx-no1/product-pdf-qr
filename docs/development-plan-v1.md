## 1. 本次调整

业务负责人 2026-08-01 确认两项：

1. **第一阶段必须包含 PDF 上传能力**，目标调整为完成最小业务闭环：
   `管理员创建产品 → 上传 PDF → 生成永久二维码 → 客户扫码 → 查看当前 PDF`
2. **后续所有开发任务必须遵循**：`GitHub Issue → Codex Worker → PR → 审核 → 合并`

阶段数由五个调整为四个，原「工程初始化」并入 Phase 1。

### 该调整解决的问题

上一版拆分中，读路径（扫码、PDF 读取）在阶段二，而写路径（上传）在阶段三——阶段二没有任何办法产生 PDF，只能靠测试夹具构造数据。新拆分把最小闭环收进 Phase 1，**读写在同一阶段闭合**，这个结构性缺陷消失。

### 该调整引入的新问题及业务负责人的处理决定

**Phase 1 包含上传，但「管理员登录」在 Phase 2。** 上传是写操作。若 Phase 1 存在一个网络可达且无需认证的上传端点，任何人都可以替换任意产品的资料——这不是排期问题，是一个严重漏洞。

**业务负责人 2026-08-01 确认的处理方式**：

> Phase 1 采用**最小验证环境，不要求正式部署**，但必须保证**可启动、可测试、可迁移**。
> Phase 1 范围：创建产品、PDF 上传、二维码生成、扫码访问 PDF。

即：**认证不在 Phase 1 范围内**，安全边界改由「不部署」提供。这使以下约束成为**硬约束，而非建议**——因为在 Phase 2 补齐认证之前，「不部署」是替代认证的唯一防线。

#### Phase 1 环境硬约束（违反即视为交付失败）

1. **Phase 1 产物禁止部署到任何公网可达环境**，包括候选环境。产物只在本地开发环境与 CI 中运行。
2. **服务默认只绑定本地回环地址**（`127.0.0.1`），不得默认绑定 `0.0.0.0`。
3. **仓库中不得提供任何面向公网部署的配置**（不含公网反向代理配置、不含生产 compose 文件、不含 TLS 证书挂载）。
4. **README 与启动文档必须显著标注**：本阶段产物不含认证，禁止对外暴露。
5. **G-17 公网验收在 Phase 1 不触发**，也不得以任何形式进行联网验收。
6. Phase 2 补齐认证并通过 G-10 之前，**不得进入任何部署流程**。

#### Phase 1 必须满足的三项能力（业务负责人明确要求）

| 要求 | 含义 | 验证方式 |
|---|---|---|
| **可启动** | 一条命令即可在本地拉起完整环境（应用 + 数据库 + 文件卷） | `docker compose up` 后服务健康检查通过 |
| **可测试** | 全部自动化测试可在本地与 CI 中执行并产出报告 | CI 全绿，测试报告可复现 |
| **可迁移** | 数据库迁移可正向执行、可回滚，且可在空库上从零重建 | 迁移正向、回滚、重建三条路径均验证 |

#### 认证能力的完整归属

| 能力 | 阶段 |
|---|---|
| 单管理员账号、Argon2id、CLI 设初始密码、登录与会话 | **Phase 2** |
| 首次登录强制改密的服务端拦截 | Phase 2 |
| 双维度限流与指数退避 | Phase 2 |
| 改密后吊销其他会话 | Phase 2 |
| 密码重置 CLI 与操作手册 | Phase 2 |
| 写入端点强制会话校验 | Phase 2 |

### 另一处按同样理由前移的能力

**审计写入**。Phase 1 已包含产品创建与 PDF 上传两类写操作，若审计留到 Phase 2，则 Phase 1 的全部写入不可追溯，事后无法还原。审计表本就在数据库初始化中创建，写入事件成本极低。

因此 Phase 1 写入其所实现操作的审计事件（`product_create`、`pdf_upload`、`pdf_upload_rejected`、`login_success`、`login_failure`）；其余事件类型与后台审计查询界面留在 Phase 2。

### Phase 1 的子阶段拆分（正式定义）

原计划中的 Phase 1「最小业务闭环」在执行时拆为两个子阶段，本表为正式定义：

| 子阶段 | 范围 | 明确不含 |
|---|---|---|
| **Phase 1-A：工程初始化与基础环境** | 项目目录结构、后端框架初始化、数据库连接、migration 机制、**初始 schema 创建**、基础配置管理、Docker 开发环境、测试框架初始化、README 启动说明 | **任何业务逻辑**；产品创建、PDF 上传、二维码生成、扫码访问、管理员认证 |
| **Phase 1-B：业务闭环开发** | 产品创建、编码规范化、`public_token` 生成、PDF 上传与当前版本管理、二维码生成、扫码访问 PDF | 管理员认证、停用/启用、恢复历史版本、Excel 导入、批量 ZIP（属 Phase 2、3） |

**边界原则**：建表结构、约束与触发器属 **schema 定义**，归 Phase 1-A；任何读写这些表的业务逻辑归 Phase 1-B。

**门禁范围**：

- **Phase 1-A** 只适用 G-04、G-05、G-06、G-16。其余 12 项一律标注「不适用」或「未触发」，**不得标记通过**——本阶段无业务逻辑，声称通过业务门禁即为虚假证据。

### G-09 端到端主线的闭合点

主线为：`新建即出码 → 未上传 → 首次上传 → 新版替换 → 历史恢复 → 停用 → 重新启用`

- **Phase 1 覆盖前四段**（新建、未上传、首次上传、新版替换）
- **后三段（恢复、停用、启用）在 Phase 2**

因此 **G-09 在 Phase 2 闭合，Phase 1 不得声称已通过 G-09**。Phase 1 可以断言"主线前四段通过"，但不能表述为"端到端主线已通过"。

## 4. 各阶段详述

### Phase 1：最小业务闭环

**目标**：`管理员创建产品 → 上传 PDF → 生成永久二维码 → 客户扫码 → 查看当前 PDF`

#### 输入条件

- G-02 已由门禁责任方判定通过
- **GitHub Issue 已创建**，含背景、范围、非目标、可验证验收标准、责任人
- 业务负责人已确认第 1 节的认证范围假设
- Worker 已分配独立 worktree 与分支

#### 实现内容

**工程与数据库基础**
- 仓库结构与模块骨架（按 `architecture-v1.md` 第 6 节的八个域）
- 依赖清单与锁文件；`docker compose`（应用 + PostgreSQL + 文件卷）
- 数据库迁移：五张业务表 + `admin_sessions`，含唯一约束、CHECK、**复合外键**、**只追加触发器**
- 数据库角色与权限分离（`app_rw` / `app_migrate` / `app_backup`），表级与列级授权
- 测试框架与 CI（构建、类型检查、lint、单元、API）
- **补齐 `quality-gates-v1.md` 中所有「具体命令待补」占位**

**环境约束**（见第 1 节，硬约束）
- 服务默认只绑定 `127.0.0.1`
- 不提供任何面向公网部署的配置
- README 与启动文档显著标注「本阶段不含认证，禁止对外暴露」
- 满足可启动、可测试、可迁移三项要求

**产品域**
- 产品创建：编码规范化（去空格 → 校验 `[A-Z0-9_-]{1,64}` → 转大写 → 原子唯一性判断，T-03）
- `public_token` 生成：CSPRNG ≥128 位、Base32 26 字符、唯一约束、与编码/自增 ID 无推导关系（T-10）

**上传与版本域**
- PDF 上传多层校验：大小 ≤50 MB → 扩展名 → 声明 MIME → **文件签名** → 结构可解析（T-12），隔离临时区
- **上传锁边界**：产品行锁**先于**当前版本判重获取；当前版本读取与 size + SHA-256 比对**全部在锁内**完成
- **文件移动顺序**：验证 → 取锁 → 移入正式存储（同文件系统原子 `rename`；目标已存在则跳过、**绝不覆盖**）→ 提交事务
- 内容判重：与当前 PDF 相同则拒绝（T-05）；与历史版本相同但非当前版本则**允许创建新版本**（B-13）
- 当前版本管理：上传新版本时追加版本行并移动指针；历史只追加
- 孤儿文件**只读**对账报告（**不实现自动清理**）

**二维码域**
- 生成规格：PNG / 总尺寸 1024×1280 / 上方二维码主体 1024×1024 / 下方产品名称标签 1024×256 / 纠错 H / 静区 4 / UTF-8（B-14 + Issue #42）
- **作为派生缓存，不参与任何事务**；载荷只含公开 URL
- 剥除 PNG 元数据；**禁止中心嵌 logo**
- 生成失败补偿：缓存写入失败直接返回内存图片；生成本身失败则拒绝并标记，**绝不产生占位图或改名文件**
- 单个下载，文件名精确等于规范化编码

**公开访问域**
- 扫码端点：**四态统一返回 200**（不存在 / 停用 / 未上传 / 正常）
- 三态判定顺序：先停用 → 再判当前版本是否为空 → 正常（B-10）
- PDF 应用层代理流式返回，`Cache-Control: no-store`（T-01、T-02）
- 提示页不含产品编码、内部 ID、版本信息

**审计域**
- 只追加写入 `product_create`、`pdf_upload`、`pdf_upload_rejected`
- 成功路径事务内写；失败路径回滚后用**独立连接**写
- 登录相关事件（`login_success`、`login_failure`）随认证一并留至 Phase 2

- 最小业务闭环可完整走通
- 可重复构建的 Docker 镜像；迁移可正向执行与回滚
- CI 全绿；quality-gates 中不再有「命令待补」占位

### Phase 3：批量能力

#### 输入条件
- Phase 2 PR 已合并，G-09 主线通过
- **GitHub Issue 已创建**并含验收标准

#### 实现内容
- **Excel 导入两阶段**：阶段一全量校验**不持写事务**；阶段二单事务提交
- **解析前防护**：≤10 MB 大小检查**先于任何解析**、ZIP 容器签名、压缩比检查、**禁用 XXE 与 DTD**、解析超时与内存上限
- 行数上限 5000
- **三类语义严格分离**：
  - 完全空白行忽略，不计入任何计数（B-11）
  - 数据库既有重复与同文件后续重复**共用同一「重复跳过数量」**，均不阻断批次（B-08）
  - 任一非空行格式错误 → **整批零持久化**，列出全部错误行号与原因
- 导入幂等：同一文件二次导入全部落入「重复跳过」
- **审计事务隔离**：失败路径回滚后用独立连接写 `product_import`（`result=failure`）
- 批量 ZIP 下载（≤1000 个），生成失败的产品跳过并**明确列出被跳过的编码**

#### 输出结果
- 导入可用，三个计数准确
- 失败导入零产品数据但**有审计留痕**

#### 验收标准
- 用例：T-I-01~20（全组）、T-A-01~08（全组）、T-F-07、T-F-10、T-C-27、T-C-28
- 门禁：G-13 并发一致性（导入原子性）、G-14 审计日志
- **T-I-06 必须以「导入前后产品总数完全相同」为断言**，不能只验证返回了错误信息
- **T-A-01 的两个条件必须同时成立**：产品总数不变 **且** 审计记录存在

#### 是否需要业务确认
否

> **本阶段最容易出现语义混淆**：把"重复"误当成阻断批次的异常，或把"整批失败"理解成连审计也不写。**必须调用参谋**。

## 6. 标准工作流（业务负责人 2026-08-01 确认）

**所有后续开发任务一律遵循：**

```
GitHub Issue → Codex Worker → PR → 审核 → 合并
```

**强制顺序，不得跳步：**

1. **先创建 GitHub Issue**，且 Issue 必须包含验收标准。无 Issue 不得开始实现。
2. **Orchestrator 派发 Codex Worker**，Worker 在独立 worktree 与独立分支工作。
3. **Worker 完成后提交 PR**，PR 必须引用对应 Issue。
4. **审核**（见第 8 节流程）。
5. **人工合并**，禁止自动合并。
6. **未通过审核不得进入下一阶段。**

### 每个阶段的 Issue 必须包含

| 项 | 说明 |
|---|---|
| 背景 | 该阶段在整体计划中的位置 |
| 范围 | 明确列出要实现的能力 |
| **非目标** | 明确列出**不做**什么，防止范围蔓延 |
| **验收标准** | 引用 `test-plan-v1.md` 的**具体用例编号**与 `quality-gates-v1.md` 的**门禁编号**；必须可观测、可测试、可判定 |
| 责任人 | |
| 依赖 | 前置阶段与前置确认事项 |

**验收标准不得写成"功能正常""测试通过"这类主观描述**——必须落到用例编号与门禁编号上。

## 7. Codex Worker 工作原则

以下为强制约束，违反即视为交付失败：

**7.1 不修改 requirements**
`docs/requirements-v2.md` 是唯一有效业务事实来源，`requirements-v1.md` 为历史版本且必须保持字节级不变。Worker **一律不得修改任何 requirements 文件**。发现需求与实现冲突时**停止并上报**，由业务负责人决定；不得自行调整需求以适配实现。

**7.2 不自行扩大范围**
- 只实现当前阶段「实现内容」中列出的能力
- 第一期明确不做的六项（ERP 同步、微信小程序、多管理员与权限、审批流、防伪追溯、多当前文件）**不得顺带加入**
- 不得为"将来可能需要"预留抽象、加字段、建表
- 发现相邻问题时登记为新 Issue，不在当前 PR 中一并解决

**7.3 不跳过测试**
严禁删除、`skip`、`xfail`、注释、放宽断言、缩小覆盖范围或降低阈值来让流水线变绿。若某条用例本身有误，**保留证据、说明原因**，并在同一 PR 中以不降低业务保护强度的方式修正。

**7.4 不修改测试用例以适配实现**（G-03）
测试用例设计者与实现者分离。Worker 实现功能，**不得自行改写 `test-plan-v1.md` 中的判定标准**。用例与实现冲突时上报，由独立测试设计者裁决。

**7.5 每阶段完成后提交 PR**
- 独立 worktree、独立分支；一个分支只承载一个阶段
- PR 必须引用对应 GitHub Issue
- PR 描述须列出：实现内容、覆盖的用例编号、通过的门禁及证据位置、已知未覆盖项
- **禁止直接推 main**

**7.6 未通过审核不得进入下一阶段**
PR 合并前不得开始下一阶段实现。**禁止自动合并**（`agent-orchestrator.yaml` 已声明 `auto_merge: false`）。

**7.7 完成声明不构成交付证据**
每项交付必须附可由他人复现的验证产物：完整命令与退出码、测试报告、截图、差异清单。自称"已完成"不算数。

**7.8 环境边界**
严禁访问正式服务器、正式数据库和真实业务文件。开发与验证只使用合成数据。G-17 公网验收由获授权人员执行，Agent 只审阅脱敏证据。

## 8. 审核流程

```
Codex Worker 完成阶段实现
        ↓
   ① 自动测试（CI）
      构建 / 类型检查 / lint / 单元 / API / 端到端
      失败 → 退回 Worker 修复，不得进入下一环节
        ↓
   ② Reviewer 审核
      代码质量、是否越界、测试是否被弱化、证据是否可复现
      要求修改 → 退回 Worker
      发现需求问题 → 重新触发 G-01
      发现架构问题 → 重新触发 G-02
        ↓
   ③ DeepSeek Advisor 复核（必要时，见 8.1）
      存在未解决冲突 → 门禁判定为「未通过—冲突未解决」，不得继续
        ↓
   ④ 业务负责人批准
      人工批准并留下带时间的记录
        ↓
      人工合并 PR（禁止自动合并）
        ↓
      进入下一阶段
```

### 8.1 DeepSeek Advisor 何时是必须的

按 `advisor-protocol-v1.md` 第 3 节，以下情形**必须调用**，不得以"时间紧""已有 Reviewer""参谋大概率同意"为由跳过：

| 情形 | 对应门禁 |
|---|---|
| Phase 1、2、3 的合并（均属高风险功能） | G-10 |
| Reviewer 发现需求问题 | 重新触发 G-01 |
| Reviewer 发现架构问题 | 重新触发 G-02 |
| 公网发布前（Phase 4） | G-17 + G-18 |

**可跳过的情形**：仅限低风险文案或简单样式调整，且须同时满足协议第 4 节全部七项条件，并留下经 Reviewer 复核的 `[Advisor Skip]` 记录。**跳过不得静默发生。**

### 8.2 参谋输出与冲突处理

- 参谋必须产出**七项完整输出**，缺任一项视为未产出，相关门禁不得通过
- 参谋只读、无执行权与决定权：不改代码、不指挥 Worker、不提交或合并 PR、不替业务负责人决定业务规则
- 参谋意见**不构成门禁通过**；门禁责任方仍须结合全部证据独立判定
- 参谋与 Orchestrator 存在**未解决冲突**时，门禁判定为未通过，工作不得自动继续；须将分歧转为普通人能理解的说明后交业务负责人裁决

> **两轮上限规则不适用于开发阶段。** `advisor-protocol-v1.md` 的两轮上限只约束**需求阶段（G-01）**，用于防止需求被反复重开。开发阶段的参谋调用按 8.1 执行，不设轮次上限。

### 8.3 责任方

| 环节 | 责任方 |
|---|---|
| 实现 | Codex Worker |
| 自动测试 | CI |
| 用例设计与裁决 | 独立测试设计者（非实现者） |
| 代码审核 | Reviewer |
| 独立第二视角 | DeepSeek V4 Flash（只读） |
| 门禁判定 | 门禁责任方 |
| 业务批准与合并 | 业务负责人 |
| 调度与证据完整性监督 | Orchestrator |
