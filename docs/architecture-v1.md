## 1. 设计约束的来源

架构不是从零选型，而是由已确认的业务规则和技术默认值倒推出来的。以下五条约束决定了架构的骨架，其余选择都是在它们之下的自由度：

| 约束 | 来源 | 对架构的强制含义 |
|---|---|---|
| 公开访问必须经受控入口，禁止长期存储直链 | T-01、T-02 | 文件不能由 Nginx/CDN/对象存储直接对外，必须由应用逐次鉴权后转发 |
| 停用后原链接立即失效 | B-07、T-02 | 禁止对 PDF 响应做长缓存；状态检查必须在每次请求的读路径上 |
| 公开标识 ≥128 位熵、不可推导 | T-10 | 标识独立于产品编码与自增 ID，必须有独立列与唯一约束 |
| 导入格式错误整批零持久化 | B-08、T-04 | 导入必须在单一数据库事务内提交，先全量校验后写入 |
| 历史版本只追加、不物理删除 | B-05、T-08 | 存储只增不减；恢复是指针移动，不是文件操作 |

## 2. 整体系统架构

第一期采用**单体应用 + 单数据库 + 本地卷存储**的三件套，不引入微服务、消息队列或对象存储。

```
                    ┌─────────────────────────────┐
   客户手机          │      反向代理 (Caddy)        │
   扫二维码  ──────▶ │   TLS 终止 / HSTS / 限流     │
                    └──────────────┬──────────────┘
   管理员浏览器 ────▶                │
                    ┌──────────────▼──────────────┐
                    │      应用服务 (FastAPI)      │
                    │  ┌───────────┬────────────┐ │
                    │  │ 公开扫码模块 │ 管理后台模块 │ │
                    │  ├───────────┴────────────┤ │
                    │  │ 产品域 / 版本域 / 导入域  │ │
                    │  │ 二维码域 / 审计域        │ │
                    │  └────────────────────────┘ │
                    └────┬───────────────────┬────┘
                         │                   │
              ┌──────────▼────────┐  ┌───────▼────────────┐
              │  PostgreSQL 16    │  │  文件卷 (本地磁盘)   │
              │  元数据 / 版本指针  │  │  内容寻址存储        │
              │  审计事件          │  │  <sha256 前缀分层>  │
              └───────────────────┘  └────────────────────┘
```

**关键点：文件卷没有对外暴露的路径。** 反向代理不配置任何 `root`/`alias` 指向文件卷，PDF 只能由应用读出后以流式响应返回。这是 T-01 的物理保证，而不仅是约定。

## 3. 各部分关系

### 3.1 前端

第一期**不做 SPA**，采用服务端渲染（Jinja2 模板）+ 极少量原生 JS。

- **公开扫码页**：三态之一。停用/未上传时返回提示页；正常时直接返回 PDF 响应流。
- **管理后台**：登录页、产品列表、产品详情（版本历史）、导入页、二维码下载页。

理由：只有一个管理员、页面不足十个、无实时协作需求。SPA 会引入构建链、依赖树和一套额外的鉴权前端逻辑，却不带来收益，反而增加 G-04（构建）、G-06（代码规范）、G-10（依赖风险）三个门禁的负担。**扫码页尤其应当零 JS 依赖**——客户在弱网、老旧手机浏览器上打开，任何 JS 失败都会变成"扫不出来"。

### 3.2 后端

单进程 FastAPI 应用，按业务域分模块，域之间只通过函数调用，不跨域直接操作对方数据表。

### 3.3 数据库

PostgreSQL 16。选它的决定性理由是**导入的原子性**（T-04）：5000 行的校验与写入必须在一个事务里全成或全败，且需要在规范化编码上做唯一约束以防并发重复创建（G-13）。SQLite 在单管理员场景下够用，但在并发写与约束表达上留的余地太小，且备份/恢复演练（G-15、G-19）的可验证性不如 PostgreSQL。

### 3.4 文件存储

本地卷 + **内容寻址布局**：文件按 SHA-256 存放为 `files/ab/cd/<sha256>.pdf`。

好处有三：
1. T-05 的"大小 + SHA-256 判重"天然成立，无需额外查表即可定位；
2. 同一份 PDF 被多个产品使用时只存一份，而版本记录各自独立；
3. 文件名完全由哈希决定，**用户输入永远不参与路径构造**，从根上消除路径穿越（见 `security-design-v1.md`）。

代价是文件名不可读，因此原始文件名存在数据库里，下载时再作为 `filename` 返回。

### 3.5 二维码服务

**不引入独立服务**，作为应用内的一个模块。二维码内容就是公开 URL（`https://<域名>/p/<public_token>`）。

生成策略：**二维码是派生缓存，不是业务状态**（G-02 门禁复核修正）。图片以规范化大写编码命名（B-09、T-06）。批量 ZIP 下载时从缓存打包，超过 1000 个按 T-09 拒绝并提示分批。

### 二维码生成必须在事务之外（G-02 门禁复核修正）

**二维码生成不参与产品创建事务，也不参与导入事务。**

原设计在产品创建时同步生成二维码。问题有二：

1. **图像编码与文件写入被卷进数据库事务**，事务持有时间从毫秒级变成数十毫秒级；
2. **批量导入时后果被放大 5000 倍** —— 一次导入 5000 个产品若在事务内逐个生成二维码，事务将持有数分钟，长期锁表并阻塞其他写入，且任何一个生成失败都会回滚整批已校验通过的产品。

**关键认识：二维码不含任何独立状态。** 它是 `public_token` 的纯函数——给定 token 与规格（B-14），任何时刻都能确定性地重新生成出字节完全相同的图片。因此它属于**缓存**，缓存丢失只影响性能，不影响正确性。既然如此，就没有理由让它参与事务。

**流程：**

```
产品创建 / 批量导入
  → 事务内：写产品行、生成并写入 public_token
  → COMMIT                                   ← 事务到此结束，不含二维码
  → 提交后异步预生成二维码并写入缓存（尽力而为，失败不影响产品）

二维码下载（单个 / ZIP / 后台预览）
  → 缓存命中 → 直接返回
  → 缓存未命中 → 即时生成 → 返回 → 尝试写入缓存
```

**验收标准 1「新建产品后可立即获得二维码」仍然满足**：下载路径本身具备即时生成能力，缓存未命中不会导致"拿不到二维码"，只是首次略慢。

### 二维码生成失败的补偿机制

产品一旦创建即不可删除（v2 编码规则 6），因此**绝不允许因为二维码生成失败而让产品创建失败或回滚**。补偿按失败类型分为两类：

**类型一：缓存写入失败**（磁盘满、权限错误、并发写冲突）

- 图片已在内存中生成成功 → **直接返回给用户**，本次请求正常完成。
- 写入 `qrcode_cache_failure` 审计事件，记录产品编码与失败原因。
- 不重试、不阻塞。下次请求再次尝试写缓存。
- **对用户完全无感**——这是缓存写入失败应有的表现。

**类型二：生成本身失败**（编码不符合契约、生成库异常）

编码不符合 B-02/B-03 契约时，T-06 要求**拒绝生成而不是改写文件名**。但此时产品已存在且不可删除，因此：

- **绝不产生占位图、默认图或改名文件**。宁可没有二维码，也不能发出一个文件名与编码不一致的图片——它会被印到实物上，且不可召回。
- 该产品在后台列表中标记为「二维码生成失败」并显示原因；单个与批量下载均跳过该产品，ZIP 中不包含它，并在下载结果中明确列出被跳过的编码。
- 写 `qrcode_generation_failure` 审计事件。
- 提供**手动重试**入口。生成是纯函数，重试无副作用、可反复执行。
- 若失败原因是编码不符合契约，则属于上游数据缺陷——修复路径是停用该编码并新建正确编码（B-04），不是修改编码（编码不可修改）。

**对账能力**：提供只读报告，列出所有「已创建但无有效二维码」的产品。与孤儿文件对账一样是只读的，不执行任何删除。

**批量导入的特殊要求**：导入提交后的二维码预生成必须**逐个独立进行**，单个产品生成失败不得影响其余产品，也不得影响已提交的导入结果。导入返回的三个计数（成功新增 / 重复跳过 / 格式错误）**不受二维码生成结果影响**——那三个数反映的是产品数据的写入结果，二维码是之后的派生动作。

**二维码规格（业务负责人已确认，2026-08-01）：**

| 项 | 取值 |
|---|---|
| 格式 | PNG |
| 尺寸 | 1024 × 1024 px |
| 纠错等级 | H（约 30% 冗余） |
| 静区 | 4 个模块 |
| URL 编码 | UTF-8 |

该规格关闭了 G-02 降级待办·风险 5。1024 px 与纠错等级 H 的组合面向**实物印刷后可能磨损、油污或部分遮挡**的现场场景；静区 4 模块是 QR 规范的最小值，低于它会显著降低识别率。规格的安全含义（禁止中心嵌 logo、必须剥除图片元数据）见 `security-design-v1.md` 第 9 节。

## 5. 数据流转

### 5.1 客户扫码（读路径，最热）

```
扫码 → GET /p/{public_token}
  → 按 token 查产品（唯一索引命中）
  → 产品不存在 → 200 无效链接提示页            ← 统一 200，不用 404
  → status = disabled → 200 停用提示页          ← 优先判定（v2 补充规则 6）
  → current_version_id IS NULL → 200 未上传提示页
  → 否则 → 读 pdf_versions → pdf_files.storage_path
        → 流式返回，Content-Type: application/pdf
        → Content-Disposition: inline; filename="<原始文件名>"
        → Cache-Control: no-store        ← T-02 的强制要求
```

**公开端点统一返回 200**（G-02 第一轮参谋审查修正）。原设计对不存在的 token 返回 404、对停用返回 200，这本身就是一个可用于存在性探测的差异——攻击者只需看状态码即可判断某个 token 是否对应真实产品。现改为**四种状态一律返回 200**，仅页面内容不同：

| 状态 | 状态码 | 页面内容 |
|---|---|---|
| 正常 | 200 | PDF 流（`Content-Type: application/pdf`） |
| 停用 | 200 | 「该产品资料已停用」 |
| 未上传 | 200 | 「资料暂未上传」 |
| token 不存在 | 200 | 无效链接提示 |

**三态判定顺序不可交换**：先停用、后未上传。这是 B-10 明确确认的，且写在 v2 补充规则第 6 条。「不存在」在三态之前判定，因为它是查询未命中，不属于产品状态。

残余风险与限流补偿见 `security-design-v1.md` 第 2 节。

**`Cache-Control: no-store` 是硬约束**：一旦允许缓存，停用就无法即时生效，B-07「停用即失效」直接落空。这也意味着 PDF 流量全部由应用承担，容量需在 G-17 前实测。

### 5.2 上传新 PDF（写路径）

```
── 阶段一：锁外，昂贵且无副作用的工作 ──
上传 → 隔离临时区落盘（不进正式存储）              ← T-12
  → 校验：扩展名 / 声明类型 / PDF 签名 / 结构可解析 / ≤50MB
  → 任一失败 → 拒绝，删除临时文件，不建版本，写拒绝审计
  → 计算 size + SHA-256

── 阶段二：锁内，短且串行 ──
BEGIN
  → SELECT ... FOR UPDATE 锁定该产品行            ← 必须先于任何判重
  → 锁内重新读取 current_version_id 及其 size + SHA-256
  → 与当前版本比对：两者均相同
        → ROLLBACK，删除临时文件，提示"与当前文件相同"，零副作用   ← T-05
  → 将临时文件移入内容寻址正式存储（原子 rename）   ← 先落盘，后提交
  → 写 pdf_files（哈希已存在则复用，不新增行）
  → 写 pdf_versions（新增一行）
  → 更新 products.current_version_id
  → 写成功审计（事务内）
COMMIT                                            ← 锁在此释放
```

### 锁边界（G-02 门禁复核修正）

**产品行锁必须在当前版本判重之前获取，且当前版本的读取与 SHA-256 比对必须全部在锁内完成。**

原设计把判重放在事务与锁之外，存在如下竞态：两个并发上传同一份 PDF 的请求，都在锁外读到当前版本为 v1（哈希 A），都判定"与当前不同"（新文件哈希 B），随后都写入——结果产生 v2(B) 与 v3(B) 两个内容完全相同的版本。若串行执行，第二次应被 T-05 拒绝。**判重结论在锁外读取即已过期，锁内不复核等于没有判重。**

| 步骤 | 位置 | 理由 |
|---|---|---|
| 文件校验、PDF 结构解析 | **锁外** | 耗时且无副作用，放锁内会显著拉长锁持有时间 |
| SHA-256 计算 | **锁外** | 纯 CPU 工作，与数据库状态无关 |
| 读取当前版本 | **锁内** | 锁外读到的值随时可能过期 |
| size + SHA-256 比对 | **锁内** | 判重的依据必须与写入在同一临界区 |
| 文件移入正式存储 | **锁内** | 见下节顺序说明 |
| 版本写入与指针移动 | **锁内** | |

锁粒度为**单个产品行**，不同产品的上传互不阻塞。锁持有时间只覆盖一次文件 rename 与三条 SQL，不包含解析与哈希计算。

### 文件移动与事务提交的顺序（G-02 门禁复核修正）

**顺序：临时区验证 → 获取锁 → 文件移入正式存储 → 数据库事务提交。**

这个顺序是在两种失败之间做的选择：

| 顺序 | 失败后果 | 严重性 |
|---|---|---|
| 先提交事务、后移动文件 | 数据库有版本记录，文件不存在 → **扫码直接失效** | 破坏业务 |
| **先移动文件、后提交事务** | 文件在存储中但无数据库引用 → **孤儿文件** | 仅浪费存储 |

选择后者：**往无害的方向失败**。悬空引用会让客户扫码打不开资料，而孤儿文件对任何业务路径都不可见。

**文件移动的原子性要求**：临时区与正式存储必须位于**同一文件系统**，使用 `rename()` 完成移动——该操作在 POSIX 下是原子的，不会出现"移动了一半"的文件。跨文件系统的移动退化为复制加删除，不具原子性，**不允许**。

**目标已存在时不得覆盖**：内容寻址下同一哈希对应同一路径。若目标路径已存在（该内容此前已被其他产品或版本使用），**跳过移动，删除临时文件**，直接复用既有文件。绝不覆盖——覆盖一个已被引用的文件，在写入中断时会损坏其他产品的现有版本。

### 事务失败后的孤儿文件处理策略

事务在文件移动之后、提交之前失败（数据库错误、连接中断、进程崩溃），会在正式存储中留下无 `pdf_files` 行引用的文件。

**第一期策略：不做自动清理，只做可见化。**

1. **孤儿文件是无害的**。内容寻址意味着它的路径完全由内容决定：同一份 PDF 下次被成功上传时，移动步骤发现目标已存在即跳过，该文件**自动转为被引用状态**。孤儿具有自愈性。
2. **不实现自动清理任务**。T-08 规定存储只增不减、不设任何删除入口。为孤儿文件开一条自动删除路径，就是在系统里种下一个"判断某文件无引用后删除它"的逻辑——一旦该判断有缺陷（并发上传期间的文件短暂无引用、备份恢复后引用尚未重建），删除的就是真实业务数据，且不可逆。**这个风险远大于孤儿文件占用的存储。**
3. **提供只读对账报告**：一个可人工触发的核对命令，列出正式存储中无 `pdf_files` 行引用的文件及其大小与时间。只读，不删除任何内容。
4. **上限可控**：孤儿只在"文件已移动但事务失败"这一窄窗口产生，每次至多 50 MB。若对账报告显示孤儿持续增长，说明事务层面存在稳定故障，应作为缺陷排查，而不是靠清理任务掩盖。
5. **失败时写审计**：事务回滚后用独立连接写 `pdf_upload_rejected`，`detail` 记录已移动的文件哈希，使孤儿可被追溯到具体的失败请求。

**第一期明确不做**：孤儿自动清理、引用计数、垃圾回收。若未来存储压力确实需要清理，必须作为独立需求走完整评审，并附恢复方案。

### 5.3 Excel 导入（最容易实现错的路径）

```
上传 Excel → 解析 ≤5000 行                    ← T-09
  ── 阶段一：全量校验，不写任何数据 ──
  → 逐行：完全空白行 → 直接忽略，不计入任何计数     ← B-11
  → 非空行：去空格 → 校验字符集与长度 → 转大写      ← B-02/B-03/T-03
  → 收集全部格式错误行号与原因
  → 存在任一格式错误 → 整批终止，返回全部错误，新增数量 = 0，零持久化   ← B-08/T-04
  ── 阶段二：单事务写入 ──
  → 同文件内规范化后重复：首次为候选，后续计入"重复跳过"    ← B-08 补充确认
  → 数据库既有编码：跳过，计入"重复跳过"（与上者共用同一计数）
  → 其余写入，生成 public_token（**不生成二维码**）
  → 提交事务，返回三个计数
  ── 事务外：提交后逐个预生成二维码，失败不影响导入结果 ──
```

**两类"重复"与"格式错误"的语义必须分开实现**：重复不阻断批次，格式错误阻断全批。把二者混为一谈是本模块最可能出现的缺陷，G-13 已就此设可判定断言。

### 5.4 恢复历史版本

只做一件事：把 `products.current_version_id` 指向目标版本，并写审计事件。**不复制文件、不新建版本记录、不删除任何东西**（T-08）。

## 6. 核心模块划分

| 模块 | 职责 | 关键不变量 |
|---|---|---|
| `public` 公开访问 | 三态判定、PDF 流式返回 | 顺序判定；`no-store`；不泄露内部标识 |
| `product` 产品域 | 创建、启停、编码规范化与唯一性 | 编码创建后不可改；不提供删除入口 |
| `version` 版本域 | 上传、版本追加、指针移动、恢复 | 任意时刻恰一个当前版本；只追加 |
| `storage` 存储域 | 临时区校验、内容寻址落盘、读流 | 用户输入不参与路径构造 |
| `importer` 导入域 | 两阶段导入、三类计数 | 格式错误零持久化；重复不阻断 |
| `qrcode` 二维码域 | 生成、命名、单个与批量下载 | 文件名精确等于规范化编码 |
| `auth` 认证域 | 登录、会话、限流、密码哈希与重置 | 不存明文；无网页找回入口 |
| `audit` 审计域 | 只追加事件写入与查询 | 不可修改；不含敏感内容 |

**编码规范化只允许有一处实现**（`product` 域导出的单一函数），`importer`、`qrcode` 域必须调用它，禁止各写一份。这是 T-03 影响面最大的一条：一旦出现两份实现，大小写与判重就会分叉。

## 7. 为什么选择该方案

### 7.1 为什么是单体

第一期只有一个管理员、一条核心读路径和五个写操作。拆分服务会把「导入原子性」变成分布式事务、把「停用即失效」变成跨服务缓存一致性问题——用架构复杂度去换一个当前不存在的扩展需求。单体让 T-04 的原子性退化成一个数据库事务，让 T-02 的实时状态检查退化成一次查询。

### 7.2 为什么是 Python + FastAPI

决定性因素是**这个项目的工作几乎全在"解析与校验"上**：Excel 解析（openpyxl）、PDF 签名与结构校验（pypdf）、二维码生成（segno）、Argon2id（argon2-cffi）——Python 在这四项上都有成熟且被广泛审计的库。FastAPI 提供类型注解驱动的接口定义，直接支撑 G-05（类型检查零错误）与 G-08（API 契约测试）。

**已考虑并放弃的替代方案：**

- **Node.js + TypeScript**：类型与生态同样可行，但 PDF 结构校验与 Excel 解析的库成熟度略逊，且依赖树更深，对 G-10（依赖风险）不利。
- **Go**：单二进制部署与性能最优，PDF 流式返回也最省心，但 Excel/PDF 解析生态较薄，开发速度慢于本期需要。若未来 PDF 流量成为瓶颈，**可以只把 `public` 读路径重写为 Go 服务**而不动其余部分——这是本架构刻意保留的退路。

### 7.3 为什么服务端渲染而不是 SPA

见 3.1。核心理由是扫码页必须在最差的手机浏览器上工作。

### 7.4 为什么本地卷而不是对象存储

对象存储的价值在于分发，而本项目**明确禁止直链分发**（T-01）。用了对象存储也必须让流量绕回应用，既付了存储成本又没得到分发收益，还多一个凭据管理面。第一期数据量（产品数千、单文件 ≤50MB）本地卷完全承受得住。

## 8. 后续扩展空间

设计时刻意留出的接口，按可能性排序：

1. **读路径独立**：`public` 模块无写操作、无会话依赖，可整体拆为独立服务或换语言实现，只需共享数据库读副本与文件卷。
2. **存储后端替换**：`storage` 域已抽象为「按哈希存取」，换成 S3 兼容对象存储只需替换实现，但**必须保留应用侧鉴权转发**，不得改为直链。
3. **多管理员与权限**：`admins` 表与审计事件已记录 `actor`，加入角色只需扩表，不改动其余域。第一期明确不做（v2 第一阶段不做清单）。
4. **二维码预生成与 CDN**：二维码图片本身不含敏感信息，未来可缓存到 CDN；但**PDF 永远不可以**。
5. **审计事件外送**：`audit` 域是只追加写入，未来可加一路输出到外部日志系统，不影响主流程。

**刻意不预留的**：不为"多个当前文件""审批流""ERP 同步"预留结构。v2 已明确第一期不做，提前埋抽象只会增加当前的理解成本。

## 9. 本方案暴露的待决技术问题

以下问题不阻塞架构评审开始，但需在 G-02 判定前给出结论：

1. **PDF 流量容量未实测**：`no-store` 意味着每次扫码都穿透到应用与磁盘。需在 G-17 前用合成数据测出单实例的并发上限，并据此决定是否需要多实例。
2. **审计事件的保留期与访问控制**未定义（T-11 影响项）。
3. **`automation/outputs/advisor-g01-full.txt` 未纳入版本控制**：参谋在 G-01 最终复核中指出该证据索引问题，判定为不阻塞，但建议在后续记录中说明原始文件存放位置。
4. **公开端点内容层面的存在性差异**：统一 200 后，四种状态仍以页面内容区分，理论上仍可据此判断 token 是否存在。在 128 位熵前提下枚举不可行，判定为可接受残余风险，详见 `security-design-v1.md` 第 2 节。
