## 0. 本系统的安全处境

必须先说清楚这个系统真实的安全模型，否则后面的措施会被误解为过度设计或防护不足：

**公开面是无认证的，且业务方已明确接受。** B-07 确认：二维码和公开链接允许被转发，任何拿到链接的人都可以查看当前 PDF，第一期不做身份验证。因此：

- **随机公开标识不是访问控制，而是"不可发现性"**。它防的是枚举，不防转发。
- **唯一的访问停止手段是停用产品**（B-07、T-02）。这条链路必须绝对可靠。
- 已被客户下载到本地的副本无法追回——这是需求层面接受的事实，不是缺陷。

管理面则相反：单管理员账号一旦失守即全站失守，因此管理面的防护必须显著强于公开面。

## 1. PDF 访问控制

### 强制路径

所有 PDF 字节流**只能**经由应用的受控端点返回（T-01）。具体保证：

1. 反向代理**不配置任何指向文件卷的 `root` / `alias` / `try_files`**。文件卷对外部网络不可达。
2. 文件卷挂载在容器内部，容器不暴露该目录的任何端口或静态服务。
3. 应用返回 PDF 前，**每次请求**都执行完整状态检查，无缓存、无短路。

### 每次请求的检查顺序

```
1. public_token 存在？          否 → 200 无效链接提示页
2. status = disabled？          是 → 200 停用提示页，不读取任何文件
3. current_version_id 为空？    是 → 200 未上传提示页
4. 读取版本 → 读取物理文件 → 流式返回（200）
```

三态顺序由 B-10 确认并写入 v2 补充规则第 6 条，**不可交换**。「不存在」在三态之前判定，因为它是查询未命中，不属于产品状态。

### 缓存策略是安全措施而非性能选项

```
Cache-Control: no-store
Pragma: no-cache
```

理由：B-07 承诺"停用后原链接立即失效"。任何形式的响应缓存——浏览器、代理、CDN——都会让停用在缓存有效期内失效。这是把一条业务承诺翻译成一个 HTTP 头，**不允许为性能优化而放宽**。若未来需要缓解容量压力，只能通过多实例或读副本，不能通过缓存 PDF 响应。

### 明确不做的事

- 不生成任何长期有效的签名 URL。若未来引入临时签名地址，其有效期必须远短于"停用生效"的可接受延迟，且仍需经过状态检查（T-01 影响项）。
- 不把 `pdf_files.storage_path` 或内部 `id` 暴露给客户端。

## 2. 随机公开标识

| 要求 | 取值 | 来源 |
|---|---|---|
| 熵 | ≥128 位 | T-10 |
| 生成源 | 操作系统 CSPRNG（`secrets` 模块，非 `random`） | T-10 |
| 编码 | Base32 无填充，26 字符 | 可读、URL 安全、无大小写歧义 |
| 唯一性 | 数据库 UNIQUE 约束 | 处理极小概率碰撞 |
| 可推导性 | 与 `code`、`id`、`created_at` **无任何关系** | T-10 |

**不采用的方案与原因**：

- UUIDv4：122 位有效熵，且含版本与变体位，信息密度低于纯随机。
- 时间戳或自增派生：直接违反不可推导要求。
- 短标识（如 8–12 字符）：熵不足，可被在线枚举。

**验证方式**（对应 G-12）：审查生成源确为 CSPRNG；统计检验大量样本无共同前缀或可预测模式；黑盒枚举测试确认无法通过修改 URL 命中其他产品。

### 公开访问状态码策略（G-02 第一轮参谋审查修正）

**问题**：初版设计对不存在的 token 返回 `404`、对停用产品返回 `200`。这个差异本身就是一条存在性探测通道——攻击者无需解析页面，只看状态码即可判断某个 token 是否对应真实产品。

**修正**：公开端点 `/p/{token}` 的**全部四种结果一律返回 `200`**。

| 结果 | 状态码 | 响应体 |
|---|---|---|
| 正常 | 200 | PDF 流 |
| 停用 | 200 | 「该产品资料已停用」提示页 |
| 未上传 | 200 | 「资料暂未上传」提示页 |
| token 不存在 | 200 | 无效链接提示页 |

**统一要求**：

- 四种响应均设 `Cache-Control: no-store`，包括不存在的情形——否则可通过缓存行为差异间接判别。
- 三种提示页的 HTML 骨架、静态资源引用、响应头集合保持一致，仅提示文案不同。
- 服务端处理时延应尽量接近：token 不存在时同样走完索引查询，不做提前短路返回。
- 任何提示页均不含产品编码、内部 id、版本信息（见第 5 节）。

**已知残余风险（明确接受）**：四种状态的**页面内容仍然不同**，因此基于响应体的区分依然可能。要彻底消除存在性探测，「不存在」与「停用」必须返回字节级相同的响应——但那会让真实客户在链接输错时看到"已停用"，属于用可用性换取一个在当前威胁模型下并不必要的防护。

判定为可接受的依据：`public_token` 有 128 位熵，攻击者**无法先获得一个候选 token 再去探测**；存在性探测只在已持有 token 时才有意义，而此时他本就能看到内容（B-07 已确认链接可转发、无身份验证）。因此该残余差异不构成额外的信息泄露。

**枚举防护的第二道**：对 `/p/{token}` 端点按 IP 限流（阈值见第 10 节），并对短时间内大量未命中的来源记录审计事件。

## 3. 文件上传安全

多层校验，任一层失败即拒绝，且**失败文件不进入正式存储**（T-12）。

### 校验顺序

```
1. 大小上限        ≤ 50 MB（T-09）——先于任何解析，防止解析炸弹
2. 扩展名          .pdf
3. 声明 MIME       application/pdf
4. 文件签名(魔数)   以 %PDF- 开头        ← 不信任 2、3，它们由客户端控制
5. 结构可解析      能被 PDF 库打开、页数可读
6. 内容判重        size + SHA-256 与当前版本比对（T-05）
```

**第 4 步是关键**：扩展名与 MIME 完全由上传方控制，只有文件签名与结构解析是对内容本身的检查。仅靠扩展名放行，等于允许任意文件伪装成 PDF 进入存储，并在后续被回传给扫码客户。

### 隔离临时区

上传先落到与正式存储**物理隔离的临时目录**，全部校验通过后才移入内容寻址路径。失败文件立即删除，不建版本记录、不产生 `pdf_files` 行。

### 上传体积与解析防护

- 流式接收并在超过上限时立即中断，不先落盘再判断。
- PDF 结构解析设超时与资源上限，防止畸形文件导致解析挂死。
- 解析在应用进程内进行，但**不渲染、不执行 PDF 内的任何动作**（不做缩略图、不解析 JavaScript 动作）。

### 规模上限（T-09）

| 项 | 默认上限 | 超限行为 |
|---|---|---|
| 单个 PDF | 50 MB | 拒绝并提示 |
| 单个 Excel 文件 | **10 MB** | 拒绝并提示，**在解析前检查** |
| 单次 Excel 行数 | 5,000 行 | 拒绝并提示分批 |
| 单次 ZIP | 1,000 个产品 | 拒绝并提示分批 |

均为集中配置项，公网测试后校准（已登记为待办）。

### Excel 大小限制与解析前检查（G-02 第二轮参谋审查补强）

**问题**：原设计只限制了 Excel 的**行数**（5,000 行），没有限制**文件字节大小**。行数只有解析之后才知道——而 xlsx 本质是 ZIP 压缩包，**恶意构造的小文件可以在解压时膨胀到极大体积**（ZIP 炸弹 / XML 实体膨胀）。若先解析再判断行数，攻击载荷在"行数检查"生效之前就已经把内存耗尽了。

**修正**：新增 **10 MB** 文件大小上限，且**必须在任何解析动作之前完成检查**。

**执行顺序（不可调换）：**

```
1. 流式接收，累计字节数超过 10 MB 立即中断连接   ← 不先落盘再判断
2. 校验文件签名确为 ZIP/xlsx 容器
3. 检查解压后总大小与压缩比，超过阈值即拒绝      ← 防 ZIP 炸弹
4. 禁用外部实体解析（XXE）与 DTD               ← 防 XML 实体膨胀
5. 解析
6. 检查行数 ≤ 5,000
```

**为什么 10 MB**：一份 5,000 行、仅含产品编码的 xlsx，正常体积在数百 KB 量级。10 MB 已留出约一个数量级的余量，足以覆盖含格式、多工作表的真实文件，同时把恶意载荷的空间压到很小。

**为什么行数限制不能取代大小限制**：二者防的是不同阶段的攻击。行数限制防的是"合法但过大的业务批次"，大小限制防的是"解析阶段的资源耗尽"。**只有后者能在解析之前生效**，因此不可省略。

**解析防护补充**：

- 解析设超时与内存上限，超出即中断并拒绝。
- 明确禁用外部实体（XXE）与 DTD 处理——xlsx 内部是 XML，这是标准攻击面。
- 解析在隔离临时区进行，失败文件立即删除，与 PDF 上传同一策略。
- 只读取所需工作表与列，不解析嵌入对象、宏或外部链接。

## 4. 密码安全

| 项 | 方案 | 来源 |
|---|---|---|
| 哈希算法 | Argon2id，参数经技术评审确定 | T-07 |
| 明文存储 | **禁止**，任何持久化数据中不得出现 | B-06 |
| 默认密码 | **禁止硬编码**；部署时经 CLI 设置 | T-07 |
| 首次登录 | 强制修改（`must_change_password`） | T-07 |
| 网页/邮箱找回 | **不提供** | B-06 |
| 遗忘重置 | 由业务负责人本人登录服务器执行受控命令 | B-06 |
| 登录限流 | 按 IP 与账号双维度，失败后指数退避 | T-07 |
| 会话 Cookie | `HttpOnly`、`Secure`、`SameSite=Lax`、合理过期 | T-07 |
| 改密后旧会话 | 立即失效（服务端会话表置 `revoked_at`） | 本设计补充 |

### 首次密码修改的强制校验

`must_change_password` 标志**必须在服务端强制**，不能只做前端跳转。前端跳转可被绕过（直接请求目标接口），而初始密码在部署过程中可能经过 CLI 历史、部署脚本或运维聊天记录，属于已知暴露面。

**执行规则**：

1. 会话有效但 `must_change_password = true` 时，**除以下两个端点外的所有管理端点一律拒绝**：修改密码端点、登出端点。拒绝方式为重定向到修改密码页，不返回任何业务数据。
2. 拦截在**认证中间件层**统一实现，不在各端点内逐个判断——逐个判断必然会漏。
3. 新密码必须**不同于初始密码**（与当前 `password_hash` 比对，相同则拒绝），否则"强制修改"可被一次原样重填绕过。
4. 修改成功后：清除 `must_change_password`、更新 `password_updated_at`、**吊销该管理员的其他全部会话**、写 `password_change` 审计事件。
5. 密码重置（业务负责人经服务器 CLI 执行）后，`must_change_password` **重新置为 true**——重置产生的临时密码同样经过了人工传递环节。

**密码强度初始默认值**（可在技术评审调整）：最短 12 字符；不得与用户名相同；不设强制字符类别组合与定期更换要求（二者已被证明会诱导可预测的弱密码）；建议但不强制使用密码管理器生成。

**不提供网页找回本身是最有效的防护**：账号找回流程历来是账号接管的主要入口。第一期用"责任人 + 服务器访问权限"替代它，攻击面从公网收缩到服务器登录凭据。

**日志与审计中禁止出现**：明文密码、密码哈希、会话令牌、重置命令的输入内容。

## 5. 权限边界

### 角色

| 角色 | 能力 | 边界 |
|---|---|---|
| 匿名客户（扫码） | 读取启用产品的当前 PDF | 无任何写能力；看不到编码、内部 id、历史版本、产品列表 |
| 管理员 | 全部管理操作 | 不能修改编码、不能物理删除产品或历史 PDF |
| 业务负责人（服务器） | 密码初始化与重置 | 经服务器 CLI，不经网页 |

### 公开面绝不泄露的信息

- 产品编码（`code`）——即使产品已停用
- 内部自增 `id`
- 历史版本的存在与数量
- 产品总数或列表
- 其他产品的任何信息

停用提示页与未上传提示页**只显示提示文案本身**，不带产品编码或任何标识。否则拿到一个 token 就能读出内部编码体系，间接削弱了编码不可枚举的意义。

### 管理面防护

- 所有管理端点要求有效会话，无会话一律重定向登录，不返回数据差异。
- 状态变更操作使用 CSRF 令牌（服务端渲染表单）。
- 管理端点不接受跨源请求。

### Agent 与环境边界

按 `CLAUDE.md`：Agent 严禁访问正式服务器、正式数据库和真实业务文件。开发与验证只用合成数据。G-17 公网验收必须由获授权人员执行，Agent 只审阅脱敏证据。

## 6. 防止路径遍历

**根本手段：用户输入永不参与路径构造。**

| 输入 | 是否进入路径 | 处理 |
|---|---|---|
| 上传的原始文件名 | **否** | 只存入 `pdf_versions.original_filename`，仅用于下载时的展示名 |
| 产品编码 | **否**（存储路径）/ 是（二维码文件名） | 字符集已限定为 `[A-Z0-9_-]`，不含 `/`、`\`、`.`、空格 |
| PDF 存储路径 | 由 `sha256` 派生 | `files/ab/cd/<64位十六进制>.pdf`，字符集固定 |

因此不存在可被 `../` 污染的拼接点。这比"过滤 `../`"可靠——过滤总有编码绕过（`..%2f`、`..\`、Unicode 变体），而**结构上不接受用户路径**没有绕过空间。

**补充防护**：

- 读取文件前校验最终解析路径仍位于文件卷根目录之内（规范化后前缀比对），作为实现缺陷的兜底。
- 下载响应的 `filename` 参数按 RFC 6266 正确编码，防止响应头注入。
- ZIP 打包时校验条目名不含路径分隔符与 `..`，防 Zip Slip（虽然名称来自受限字符集的编码，仍做兜底）。

**二维码文件名**（B-09、T-06）：直接使用规范化大写编码，如 `A001.png`。不静默替换、不截断、不追加摘要；若兜底检查发现编码不符合契约，**拒绝生成**而不是改写文件名。

## 7. 防止未授权访问

| 威胁 | 防护 |
|---|---|
| 枚举公开标识 | 128 位熵 + 限流 + 响应无差异化（第 2 节） |
| 绕过状态检查直取文件 | 文件卷不对外可达 + 每次请求实时检查（第 1 节） |
| 停用后仍可访问 | `no-store` + 每次实时检查 status |
| 跨产品越权 | 复合外键保证指针不跨产品（数据模型第 3 节） |
| 未登录访问管理面 | 会话校验；无会话不返回任何业务数据 |
| 会话固定/劫持 | 登录后重新签发会话；`HttpOnly` + `Secure` |
| 暴力破解密码 | 双维度限流 + 指数退避 + 失败审计 |
| 上传恶意文件 | 多层内容校验 + 隔离临时区（第 3 节） |
| 通过错误信息探测 | 统一错误页，不回显内部路径、SQL、堆栈 |

**已知且被接受的残余风险**（B-07 明确接受）：链接被转发后无法单独收回；停用前已下载的副本无法追回。停用是唯一的止血手段，因此 G-09 与 G-17 都必须包含"停用即时生效"的断言。

## 8. 数据备份与恢复

### 备份范围必须是两者

| 对象 | 内容 | 缺一的后果 |
|---|---|---|
| PostgreSQL | 产品、版本、指针、管理员、审计 | 只有文件，不知道哪份是当前版本 |
| 文件卷 | 全部 PDF 与二维码缓存 | 指针指向不存在的文件，扫码全部失败 |

**两者必须一致地备份**。数据库与文件分离存储，若备份时点不一致，恢复后可能出现"版本记录存在但文件缺失"。建议：先备份文件卷（只增不减，早备份不会丢新增之外的东西），再备份数据库；恢复时按相反顺序验证。因为存储只追加（T-08），文件卷备份早于数据库备份是安全的方向——反过来则可能出现数据库引用了尚未备份的文件。

### 恢复验证（对应 G-15、G-19）

备份不做恢复演练等于没有备份。演练必须在隔离环境用合成数据完成，并断言：

1. 恢复后产品总数、版本总数与备份时点一致；
2. **每个产品的 `current_version_id` 所指向的文件在文件卷中真实存在**（这是最关键的断言，直接暴露两者不一致）；
3. 扫码主线可完整走通（三态 + 版本切换）；
4. 审计事件未丢失且无被修改痕迹。

### 与"不物理删除"的边界

T-08 规定业务数据只增不减。备份轮转会删除**过期的备份副本**，这不违反该原则——被删除的是备份介质上的历史快照，不是业务数据本身。此边界需在运维手册中写明，避免实现者把"不删除"错误地推广到备份保留策略，导致备份无限增长。

`admin_sessions` 中过期会话属于运维数据，可物理清理，同样不适用"不物理删除"原则。

## 8A. 审计事务隔离策略（G-02 第二轮参谋审查补强）

### 问题

审计有两个互相冲突的目标：

1. **成功操作的审计必须与业务变更原子** —— 否则会出现"产品已创建但无审计记录"，或"审计说创建了但实际没有"。
2. **失败操作的审计必须在回滚后存活** —— 而这恰恰是最需要审计的场景。

若把审计写入一律放进业务事务，则 Excel 格式错误导致整批回滚时（B-08、T-04 要求零持久化），**审计记录会随业务数据一起被回滚掉**——留下一次完全无痕的失败导入。攻击者反复尝试恶意文件也不会留下任何记录。

若把审计一律放在事务外，则成功路径可能出现业务已提交、审计写入失败的不一致。

### 策略：按结果分路

| 路径 | 写入方式 | 保证 |
|---|---|---|
| **成功** | 在**业务事务内**写入审计 | 业务变更与审计同生共死，不会出现只有其一 |
| **失败 / 拒绝** | 业务事务回滚后，用**独立连接**在新事务中写入审计 | 审计不受回滚影响，必然留痕 |

PostgreSQL 没有原生的自治事务，因此失败路径必须使用**独立于业务事务的数据库连接**。实现上：从连接池取一个专用连接写审计并立即提交，不参与外层事务。

### 必须留痕的失败场景

以下失败**一律**产生审计记录，不因业务数据零持久化而省略：

| 场景 | 审计动作 | 关键说明 |
|---|---|---|
| Excel 格式错误整批失败 | `product_import`，`result=failure` | **产品数据为零，但审计必须存在**；`detail` 记录错误行数与三类计数 |
| Excel 超出大小或行数上限 | `product_import`，`result=failure` | 记录拒绝原因与实际大小 |
| PDF 上传校验失败 | `pdf_upload_rejected` | 记录拒绝阶段（签名/结构/大小） |
| 上传与当前文件相同被拒 | `pdf_upload_rejected` | 记录为正常业务拒绝，非异常 |
| 登录失败 | `login_failure` | 暴力破解的唯一发现手段 |
| 未命中 token 的异常密集访问 | 枚举探测事件 | 见第 2 节 |

**「零持久化」约束的是产品数据表，不是审计表。** 这一区分必须在实现与测试中明确——B-08 要求"失败时不得产生任何产品数据"，指的是 `products`；`audit_events` 是治理数据，恰恰必须写入。这是最容易被实现者误解的一处：把"整批失败 = 什么都不写"理解成连审计也不写。

### 一致性与失败处理

- **成功路径**：审计写入失败即整个事务失败，业务变更一并回滚。宁可操作失败，也不接受无审计的业务变更。
- **失败路径**：审计写入本身若再失败（如数据库不可用），必须记录到应用日志并触发告警。**审计不可用不应静默**。
- **审计不可被回滚影响的验证**：见 `test-plan-v1.md` 中导入失败审计测试组——断言"产品总数不变**且**审计记录存在"，两个条件必须同时成立。

### 与权限层的配合

`app_rw` 对 `audit_events` 只有 `INSERT` 与 `SELECT`（见 `data-model-v1.md` 第 9A 节），因此审计一旦写入即无法被应用修改或删除。事务隔离保证"写得进去"，权限保证"改不掉"，两者缺一不可。

## 9. 二维码安全规格

业务负责人 2026-08-01 确认的规格（关闭 G-02 降级待办·风险 5）：

| 项 | 取值 | 安全含义 |
|---|---|---|
| 格式 | PNG | 无损；不含 JPEG 压缩伪影导致的识别劣化 |
| 总图片尺寸 | 1024 × 1280 px | 下方 256 px 产品名称标签只供人工辨认 |
| 二维码主体 | 上方 1024 × 1024 px | 保持原印刷缩放余量 |
| 纠错等级 | H（约 30%） | 磨损、油污、部分遮挡后仍可识别 |
| 静区 | 4 个模块 | QR 规范最小值；不足会显著降低识别率 |
| URL 编码 | UTF-8 | 域名与 Base32 token 均为 ASCII，UTF-8 下即字节模式 |

### 生成与分发的安全约束

**1. 二维码内容只允许是公开 URL。** 不得嵌入产品名称、产品编码、内部 id、版本号或任何附加参数。图片下方的产品名称是二维码载荷之外的可视标签。二维码是印在实物上的永久载体，一旦印出就无法收回——任何多余载荷都会永久暴露。

**2. 必须剥除 PNG 元数据。** 生成库可能写入 `tEXt`/`iTXt`/`tIME` 块，其中可能包含库版本、生成时间戳甚至临时路径。这些图片会被批量下发给外部印刷方，**元数据是一条容易被忽略的泄露通道**。生成后统一剥除非必要块，只保留图像数据。

**3. 禁止在二维码中心嵌入 logo。** 中心嵌图会消耗纠错冗余——用了 H 级纠错却把预算花在 logo 上，等于把面向磨损的容错额度提前用掉。若未来业务要求加 logo，必须重新做印刷后解码验证并重新评估纠错等级，不能直接叠加。

**4. 纠错等级 H 与 token 长度的相互作用。** 公开 URL 约 50 字符（域名 + `/p/` + 26 字符 token），在 H 级纠错下所需版本仍然很低，1024 px 下单模块像素充裕。**但若未来域名变长或 token 编码变更，必须重新核算模块密度**——模块过密会在小尺寸印刷时失效。

**5. 二维码图片本身不含敏感信息**，因此与 PDF 不同，未来**可以**缓存到 CDN。PDF 永远不可以。

### 印刷后验证

规格再合理，也必须验证真实印刷件可扫。测试要求见 `test-plan-v1.md` 第 4 节（T-Q-08 至 T-Q-11），包括缩放至最小实际尺寸、部分遮挡、低光照条件下的解码。

## 10. 限流与 Argon2 参数的初始安全默认值

以下为**初始默认值**，均为集中配置项，需在容量与硬件基准测试后校准。列出具体数值的目的是让 G-10 可判定——没有数值就无法验证"限流是否生效"。

### 10.1 Argon2id 参数

| 参数 | 初始默认值 | 说明 |
|---|---|---|
| 算法 | Argon2id | T-07 指定；抗 GPU 与抗侧信道的折中方案 |
| 内存 `m` | 64 MiB | 高于 OWASP 最低建议（19 MiB） |
| 迭代 `t` | 3 | |
| 并行度 `p` | 1 | 单管理员，无并发登录压力 |
| 盐长度 | 16 字节（CSPRNG） | |
| 输出长度 | 32 字节 | |

**校准目标**：在目标部署硬件上单次哈希耗时 **0.5–1.0 秒**。低于 0.5 秒说明成本过低，高于 1.0 秒会影响正常登录体验。

**为什么可以取得比常见 Web 应用更高**：本系统只有一个管理员、登录频率极低，因此**可以承受远高于多用户系统的单次哈希成本**。这里不存在"登录高峰打垮服务器"的场景，没有理由压低参数。

**参数升级路径**：哈希串中已包含算法参数，登录成功后若检测到存储参数低于当前配置，应就地用新参数重新哈希（rehash-on-login）。

### 10.2 限流阈值

| 端点 | 维度 | 初始阈值 | 超限行为 |
|---|---|---|---|
| 登录 | 单账号 | 连续失败 5 次后指数退避（1s→2s→4s…，上限 5 min） | 延迟响应，**不永久锁定** |
| 登录 | 单 IP | 15 分钟内 20 次失败 | 临时拒绝 15 分钟 |
| 公开扫码 `/p/{token}` | 单 IP | 60 次/分钟，突发 120 | 429 + `Retry-After` |
| 公开扫码未命中 | 单 IP | 10 分钟内 20 次未命中 | 收紧限流并写审计事件 |
| PDF 上传 | 单会话 | 10 次/分钟 | 拒绝并提示 |
| Excel 导入 | 单会话 | 3 次/分钟 | 拒绝并提示 |
| 批量 ZIP 下载 | 单会话 | 10 次/小时，并发 1 | 拒绝并提示 |

**两个刻意的设计取舍：**

**1. 登录失败不做永久账号锁定。** 本系统只有一个管理员账号，永久锁定等于给攻击者一个**零成本的拒绝服务开关**——只要持续发错密码，合法管理员就永远进不来，而恢复手段（业务负责人登服务器）成本很高。指数退避同样能把暴力破解拖到不可行，却不会把管理员锁在门外。

**2. 公开扫码的限流阈值必须偏松。** 真实场景下大量客户可能共用一个出口 IP（同一工厂、同一展会、同一运营商 NAT），阈值定得过紧会直接表现为"扫码扫不出来"——那是比枚举风险严重得多的业务故障。因此对**未命中**单独设一条更严的规则：正常客户扫的是印在实物上的有效码，几乎不会连续未命中；连续未命中才是枚举特征。

**限流状态存储**：第一期存于应用内存即可（单实例）。若未来多实例部署，必须改为共享存储，否则限流会随实例数被稀释——这一点须在扩容时重新评审。

## 11. 待决安全事项

1. **审计日志保留期与访问控制**未定义（T-11 影响项）；归档方案不得成为删除入口。
2. **PDF 流量容量**：`no-store` 使每次扫码穿透到应用与磁盘，单实例并发上限需在 G-17 前实测。
3. **Argon2id 与限流的初始值仍需实测校准**：第 10 节已给出可判定的默认值，但内存参数需按目标硬件基准测试确认耗时落在 0.5–1.0 秒；限流阈值需按真实扫码规模校准，避免误伤共用出口 IP 的客户。
4. **多实例部署下的限流共享**：当前限流状态存于应用内存，仅适用于单实例。扩容前必须改为共享存储并重新评审。
