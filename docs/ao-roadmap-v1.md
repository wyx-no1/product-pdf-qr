## 一、AO 当前架构问题总结

**本节全部基于 product-pdf-qr 的真实经历，不做理论假设。** 每个问题都标注了它在哪里实际发生过。

### 项目实际产出（截至 2026-08-03）

| 项 | 数量 |
|---|---|
| PR | 5（#2、#4、#6、#7、#10） |
| Issue | 5（#1、#3、#5、#8、#9） |
| Worker 会话 | 4（`product-pdf-qr-2` ~ `-5`） |
| 已确认业务决策 | 14（B-01 ~ B-14） |
| 参谋审查轮次 | G-01 三轮、G-02 三轮、G-10 待进行 |
| Reviewer 意见批次 | PR #6 两批、PR #10 三批共 5 项 |

### 问题 1：技术操作确认过多，业务负责人无从判断

**实际发生的打扰：**

| 被要求确认的事项 | 业务负责人能判断吗 |
|---|---|
| 是否可以创建 GitHub Issue | 无从判断，只能说「可以」 |
| 是否可以创建 Worker | 同上 |
| 是否可以把设计文档提交入库 | 同上 |
| PostgreSQL healthcheck 在初始化阶段误判如何修 | 需懂 initdb 时序与临时 socket |
| `verify_clean_start.sh` 依赖未声明的 jq 如何处理 | 需懂 shell 与 Docker |
| rebase 冲突如何解决 | 需懂 git 三点式与 merge base |
| 上传大小限制在 ASGI 层还是服务层 | 需懂 Starlette multipart 物化时机 |

**对照真正的业务决定**（B-01 ~ B-14，共 14 项）：三态提示优先级、二维码地址泄露是否接受、Excel 格式错误是否整批失败、停用期间管理端权限、历史版本内容重复的处理……**这些只有业务负责人能判断，且总数不到打扰次数的一半。**

**结论**：问题不是「确认太多」，而是**确认的密度掩盖了它们的重要性差异**。「确认业务规则」与「确认可以创建 Issue」在流程上等权，导致真正需要深思的决策被淹没。

### 问题 2：多 Agent 之间证据传递不足

**实际发生：**

- Reviewer 可直接访问 PR 分支代码，能给出精确到行的意见（PR #10 的行级评论 `discussion_r3700862167`）
- **Advisor 无法访问 AO 的外部 worktree**。G-01 最终复核时它明确报告：「`automation/outputs/advisor-g01-full.txt` 在仓库中不存在（glob 未找到 automation 目录）」——它运行在某个 commit 的 git worktree 内，**只能看到已提交的内容**

**验证过的解决方向（已在本项目实测三轮迭代）：**

| 迭代 | 做法 | 结果 |
|---|---|---|
| 第一版 | `review-context-pr6.md` 内含大量文件内容摘录 | **结构性缺陷**：Advisor 只能看到 Orchestrator 决定摘录的内容，而摘录者正是被审查方案的制定方 |
| 第二版 | 改为纯索引（只给位置，不给内容） | 独立性恢复，但 **Advisor 访问不到外部 worktree 中的材料** |
| 第三版 | Evidence 目录**提交进 PR 分支**，只含元数据/清单/diff/验证记录，**不含源码副本** | 可用：Advisor 在同一分支 worktree 内即可读到证据，源码本就在分支上 |

**结论**：证据必须**与被审查代码在同一 commit 内**，且**不得包含源码副本**——包含副本会重新引入「选哪些文件」的筛选偏差。

### 问题 3：Advisor 需要标准化输入

**实际发生**：G-01 阶段，参谋意见经「业务负责人 → Orchestrator → Worker」两次转达后落库，结果**七项固定输出中有五项标注为「本次转达未提供」**，事后必须重新补录原始输出文件才补齐。

该问题已通过 `docs/advisor-protocol-v1.md` 第 9 节（PR #7 写入）成为规则：review-context 只能作为索引、原始证据必须可访问、无法访问时必须标注「该项未核验」、冲突时以原始证据为准。

**但规则目前只是软约束**——没有任何机制检查 Advisor 是否真的读了原始证据。

### 问题 4：用户视角不足

**实际发生**：业务负责人在整个流程中看到的是 PR 编号、commit SHA、分支名、CI job 名、门禁编号（G-04 ~ G-19）、测试用例编号（T-C-18 ~ T-C-30）、`RLIMIT_AS`、`CancelledError`、`multipart materialization`……

**没有任何一层把这些翻译成业务语言。** 每次决策请求的翻译工作，实际由 Orchestrator 在对话中临时完成，**未成为系统能力**，也无法保证一致性。

### 问题 5：缺少 Mac 与 iPhone 之间的决策闭环

**实际发生**：所有决策都在 Mac 前完成。业务负责人必须坐在电脑前才能推进流程，且必须逐条阅读技术上下文。

设计已完成（`docs/apple-decision-channel-v1.md`），但**尚未实施**，且已识别出关键平台限制：**iOS 快捷指令无法由 iCloud Drive 文件变化触发**，必须借用提醒事项作为推送载体。

### 贯穿性风险（不属于任何单一模块，但会影响全部）

| 风险 | 状态 |
|---|---|
| **分类者即被授权者** —— Orchestrator 既执行动作，又判断哪些需要人工授权 | 未解决，与「证据摘录者即被审查方」同构 |
| **软约束缺乏强制手段** —— CODEOWNERS、分支保护、CI 断言均未建立 | 未建立。Phase 1-A 中 Worker 修改 `CLAUDE.md` 即为实例 |
| **`agent-orchestrator.yaml` 未验证** —— 是否被 AO 实际读取仍未证实 | 自 G-01 登记至今未执行 |
| **Reviewer 角色未定义** —— 迄今由业务负责人本人扮演 | 未定义是人、Agent 还是 CI 检查集合 |
| **批准记录由 Orchestrator 代写** —— Issue #3/#5/#8 的「审核通过」均为转达留痕 | 已在记录中标注，但未改变 |

## 二、改造目标

**让非程序人员也能管理 AI 开发团队。**

### 目标的可判定形态

改造完成后，业务负责人应当：

1. **只在真正需要业务判断时被打扰**——技术操作、流程动作、缺陷修复不再询问
2. **收到的每个决策请求都是业务语言**——不含 git、PR、CI、容器、SQL 等术语
3. **能在 iPhone 上完成选择**——不必坐在电脑前
4. **看不到工程细节**——除非主动切换到技术视图
5. **仍然掌握不可逆动作的最终决定权**——合并与发布永远需要人

### 明确不追求

- **不追求减少人工审批的严格程度**。目标是让精力集中到真正的决策上，不是让批准变容易。
- **不追求端到端无人值守**。
- **不追求缩短交付时间为首要指标**。首要指标是**减少转达失真**与**保证证据完整**。

## 三、改造模块

### P0-1：Evidence Snapshot 自动生成

**当前问题**
PR #6 与 PR #10 的证据包全部由 Orchestrator 手工整理，经历三轮形态迭代才收敛。每次都要手工执行 `git diff`、查 CI run、抓 Reviewer 线程 URL、写清单，且**证据与实际不一致的风险持续存在**——PR #10 就出现过 diff.patch 因 main 前进而误报「删除」的情况（两点式 vs 三点式）。

**目标状态**
PR 创建或更新时，`docs/evidence/pr<N>/` 自动生成并随代码提交入库，内容始终与 HEAD 一致。

**实现方案**
- 固定四件套：`metadata.md`、`changed-files.md`、`diff.patch`、`validation.md`
- 一律使用**三点式** `origin/main...<HEAD>`（与 GitHub「Files changed」一致）
- 证据目录**排除自身**，避免自引用
- **不含源码副本**（源码本就在同一分支）
- 自动填充：PR 元信息、提交清单、变更文件与类型、未修改文件核验命令、CI run ID 与结论、Reviewer 线程 URL
- 代码提交与证据提交**分离为两个 commit**，便于分别审阅

**风险**
- **自动生成会掩盖「选择」问题**：四件套的字段集合仍由设计者决定。缓解：`diff.patch` 为完整权威记录，且 `metadata.md` 必须声明本目录的局限与盲区
- **证据滞后**：代码提交后证据未刷新即失效。缓解：证据生成必须作为 PR 更新的强制步骤，不可跳过

**验收标准**
1. PR 更新后，`diff.patch` 与 `git diff origin/main...<代码提交>` **逐行一致**
2. `changed-files.md` 中的未修改文件核验命令**执行后全部无输出**
3. 证据目录不含任何源码副本
4. `metadata.md` 明确声明「不替代源码，Advisor 仍须读分支源码」
5. 人工整理耗时降为零

### P0-2：Advisor 证据自动挂载

**当前问题**
Advisor 无法访问 AO 外部 worktree。PR #10 用了三轮才确定「证据必须提交进 PR 分支」这一形态。目前每次都要人工判断该把什么放进去、放在哪。

**目标状态**
Advisor 被调用时，自动获得：被审查分支的 worktree（含源码）+ 同分支内的 Evidence 目录 + 判定依据文档，无需任何人工搬运。

**实现方案**
- Advisor 的 worktree 检出**被审查 PR 的 HEAD**，而非 main
- 调用时自动传入：PR 编号、Evidence 目录路径、适用门禁编号、七项输出模板
- Advisor 输出**直接落文件**（如 `automation/outputs/advisor-<gate>-<n>.txt`），再由 Worker 走 PR 入库
- **禁止 Orchestrator 转述后落库**——G-01 的五项缺失正是这条缺失导致的

**风险**
- **Advisor 仍可能只读 Evidence 不读源码**。缓解：Evidence 中明确要求「第 3 步不可省略」，并在七项输出中要求每项指明依据的原始证据；但**这仍是软约束，无法机器校验**
- **原始输出留存缺口**：G-02 三轮审查的原始输出至今未落在 `automation/outputs/`。缓解：把「原始输出已落文件」设为门禁判定的前置检查项

**验收标准**
1. Advisor 无需任何人工搬运即可读到源码与 Evidence
2. 参谋原始输出**自动落文件**，不经转述
3. 七项输出完整性可被机械检查（缺项即判定未产出）
4. 门禁记录中可追溯到参谋原始输出的文件路径

### P0-3：自动动作授权策略

**当前问题**
创建 Issue、创建分支、创建 Worker、创建 PR、触发 Reviewer、调用 Advisor、CI 重试、rebase、缺陷修复、生成证据——**每一项都在打扰业务负责人**，而他对其中任何一项都无从判断。

**目标状态**
上述十类动作默认自动执行，业务负责人不再收到通知。

**实现方案**
沿用 `docs/ao-automation-plan-v1.md` 第 1 节的白名单与三条件判定：
1. 不改变业务规则、功能范围或用户可见行为
2. 出错可通过撤销单个 PR 或终止单个任务完整恢复
3. 不合并 main、不发布生产、不触及正式资产

「低风险冲突处理」的边界必须写死（同文件 1.2 节），rebase 自动处理仅限文档冲突且解决方式为并集或采用已发生事实。

**风险**

⚠️ **本模块风险最高，且是整个 v1.1 的结构性弱点。**

**分类者与被授权者是同一方**——Orchestrator 既执行动作，又判断某动作属「自动」还是「人工」。这与 Evidence 曾经的「摘录者即被审查方」完全同构。

三条缓解措施**缺一不可**：
1. 全部自动执行的动作**必须留痕**，形成可事后批量查阅的清单
2. **分类存疑时默认升级为人工**——「不确定算不算业务决定」本身就是需要人判断的信号
3. **Advisor 在门禁复核时检查分类是否合理**，发现被错误归类为「自动」的业务决定须指出

**另一风险**：本模块无硬约束支撑。CODEOWNERS、分支保护、CI 断言均未建立，「禁止自动合并」目前只靠 `agent-orchestrator.yaml` 声明，而**该文件是否被读取仍未验证**。

**验收标准**
1. 十类动作执行时无人工确认
2. 每个自动动作都有留痕，可批量查阅
3. 存疑动作升级为人工的比例可统计，且不为零（为零说明判定过于宽松）
4. 一个完整 Phase 的链路中，人工介入**只出现在业务决策与合并批准两处**
5. **前置**：`agent-orchestrator.yaml` 的实际生效性已验证，或已改用 GitHub 分支保护作为主防线

### P0-4：用户确认层重构

**当前问题**
所有确认都以同一形态、同一优先级呈现。业务负责人无法区分「这个必须我拍板」与「这个只是流程走到这里」。

**目标状态**
确认分为三段：**业务决策节点 → 自动执行链 → 责任审批节点**。只有第一段与第三段会打扰业务负责人。

**实现方案**
- 保留人工的五类（`ao-automation-plan-v1.md` 第 2 节）：改变业务规则、改变功能范围、明显增加成本或周期、接受不可逆业务风险、最终合并与正式发布
- 每个确认请求带**唯一编号**、**类型标签**、**是否不可逆**
- 超时**保持暂停，绝不默认同意**
- 边界情形按既定规则归类（技术方案业务结果相同→自动；不同→人工；门禁失败修复方式明确→自动；唯一修复方式是放宽标准→人工）

**风险**
- **归类错误会静默吞掉业务决定**。缓解同 P0-3
- **「不可逆」标注失真**：若为了让对方容易点头而淡化，会导致错误的快速批准。缓解：不可逆判定必须给出具体的不可恢复机制，不得只写「可能不可逆」

**验收标准**
1. 确认请求带编号、类型、可逆性标注
2. 五类人工决策一项不漏地触发确认
3. 十类自动动作一项不触发确认
4. 超时后任务保持暂停，无任何默认同意路径
5. 决策日志只追加，含时间、编号、选择、后续动作

### P1-5：Decision Translator

**当前问题**
技术问题原样交给业务负责人。翻译工作目前由 Orchestrator 在对话中临时完成，**未成为系统能力**，质量不可保证、不可复现。

**目标状态**
每个决策请求经固定翻译，产出六项：发生了什么 / 对业务有什么影响 / 推荐方案 / 其他选择 / 判断错误的后果 / 按钮。

**实现方案**
沿用 `docs/apple-decision-channel-v1.md` 第 3 节的字段定义与禁止项：
- 「发生了什么」不得出现 git、PR、CI、分支、容器、SQL
- 「推荐方案」必须明确一个，不得列平行选项
- 「判断错误的后果」必须明确「容易改回来」或「改不回来」，**不可逆的事必须说不可逆**
- 「其他选择」最多两个

**风险**
- **翻译质量无法自动校验**。缓解：前若干次决策由业务负责人反馈是否可读，作为校准
- **翻译过程可能丢失关键约束**。例如把「四态统一 200」翻成「让回应一致」时，若丢掉「客户正常扫码不受影响」这一句，业务负责人可能误以为影响客户
- **推荐倾向可能诱导**。缓解：推荐方案必须给理由，且「其他选择」不得被写成明显不合理的陪衬

**验收标准**
1. 每个决策请求六项齐全，缺一即不发出
2. 「发生了什么」经关键词检查，不含技术术语黑名单
3. 不可逆决策的后果描述明确写「改不回来」
4. 业务负责人抽查确认「读得懂、知道在决定什么」

### P1-6：用户视图（User View）

**当前问题**
业务负责人看到的是工程信息：PR 编号、commit、分支、CI job、门禁编号、用例编号。

**目标状态**
只看到四样：当前项目、需要决定的事情、推荐方案与影响、操作按钮。

**实现方案**
沿用 `docs/apple-decision-channel-v1.md` 第 7 节。Git、PR、Worker、CI、命令、技术日志、门禁编号、用例编号、文件路径**默认隐藏**。

**风险**
- **隐藏过度会削弱知情权**。业务负责人有权知道自己在批准什么。缓解：保留「查看摘要」入口，并可切换到技术视图（P1-7）
- **隐藏可能被用来掩盖问题**。缓解：用户视图不得省略「判断错误的后果」与不可逆标注

**验收标准**
1. 用户视图中零技术术语
2. 「查看摘要」可展开完整六项翻译
3. 可一键切换到技术视图
4. 隐藏的内容仍可在 Mac 上完整查阅

---

### P1-7：技术视图（Engineering View）

**当前问题**
没有分层。所有人看同一份信息。

**目标状态**
Reviewer、Advisor、Orchestrator 使用技术视图，含完整工程上下文；业务负责人默认不进入。

**实现方案**
- 技术视图保留：PR、commit、分支、CI、门禁编号、用例编号、Evidence 目录、原始日志
- 与用户视图**共享同一决策编号**，可双向跳转
- 技术视图**不做简化**——它的读者具备判断能力

**风险**
- **两套视图可能不同步**，导致业务负责人批准的与工程实际执行的不是一回事。缓解：两视图必须由同一决策记录派生，禁止各自维护
- **技术视图可能成为绕过翻译层的后门**。缓解：业务决策的批准仍只能在用户视图完成

**验收标准**
1. 同一决策在两个视图中编号一致、内容可追溯到同一记录
2. 技术视图不影响业务负责人的默认体验
3. 两视图不存在信息矛盾

---

### P2-8：Apple iOS 决策通道

**当前问题**
所有决策必须在 Mac 前完成。

**目标状态**
Mac 发起 → iPhone 收到通知 → 完成选择 → 结果回到 Mac，全程 Apple 原生。

**实现方案**
沿用 `docs/apple-decision-channel-v1.md` 第 4 节的方案 A：iCloud Drive 传数据 + **提醒事项作为推送载体** + iPhone 快捷指令展示与作答。

第一版只支持四个操作：同意 / 拒绝 / 稍后处理 / 查看摘要。

**风险**
- **iOS 快捷指令无法由 iCloud Drive 文件变化触发**——这是已确认的平台限制，因此必须借用提醒事项推送
- **iCloud 同步延迟不可控**。缓解：超时保持暂停，绝不默认同意
- **Mac 休眠时结果滞留**。v1 接受，任务保持暂停不会出错
- **锁屏泄露**：通知在锁屏可见，业务摘要本身可能泄露经营信息。缓解：提醒事项标题只写类型与编号，详情需解锁查看
- **「拒绝」不自动改用备选**：v1 一律停下等待，不用一次点击替代两次决定

**验收标准**
1. Mac 发起后 iPhone 能收到系统通知
2. iPhone 上可完成四种操作并写回结果
3. Mac 能读到结果并继续或保持暂停
4. 决策编号幂等，同一编号只处理一次
5. 超时后请求保留、任务暂停、无默认同意
6. 通知不含密钥、代码、服务器信息、业务标识

## 六、实施顺序与理由

```
P0（Evidence + 授权）→ P1（翻译 + 视图）→ P2（通知通道）
```

### 为什么先做 Evidence

**因为不可信的证据会让后面所有环节失效。**

- Advisor 是 G-10 等高风险门禁的强制环节。若它拿不到完整证据，它的「接受」不构成任何保证——**一个基于残缺证据的通过，比没有审查更危险**，因为它制造了已被审查的假象
- G-01 已经真实发生过：转达摘要缺失七项中的五项，事后必须重新补录
- Evidence 也是 P0-3 自动授权的**前提**：自动执行的动作需要留痕可查，留痕机制与证据机制是同一套

### 为什么先做授权与确认层，再做翻译与视图

**因为决策的「量」必须先降下来，翻译才有意义。**

- 当前打扰中多数是技术操作。若不先砍掉，翻译层要翻译的大部分内容是「是否可以创建 Issue」——**把无意义的问题翻译得更好读，仍然是无意义的问题**
- 先做 P0-3/P0-4 把决策量压到只剩真业务决定，翻译层面对的就是少量、高价值、确实需要人判断的内容

### 为什么最后做通知通道

**三个理由：**

1. **通知只是传输层。** 传输一个未经翻译的技术问题到手机上，只是让业务负责人在更小的屏幕上看不懂同样的东西
2. **平台限制需要前面的工作来降低影响。** iCloud 同步延迟不可控——只有当决策量降到很低、且每个决策都真正重要时，「延迟几分钟」才可接受；如果每天几十条通知，延迟会变成灾难
3. **成本最高、可回退性最差。** 快捷指令、提醒事项、iCloud 目录一旦建立，业务负责人会形成使用习惯，之后改动成本高。应当在决策形态稳定后再固化通道

### 一条不可颠倒的依赖

**P0-3（自动授权）的留痕机制必须与授权同时生效，不得先放开授权后补留痕。**

否则会出现一段「动作已自动执行但无记录」的窗口，而这段窗口内发生的错误分类**事后无法发现**。

## 七、成功标准

AO v1.1 完成后，业务负责人的使用体验应当是：

### 日常状态

**大部分时间收不到任何通知。** Issue 创建、Worker 派发、分支与 PR、CI 重试、缺陷修复、rebase、证据生成——全部自动完成，不打扰。

### 收到通知时

手机上出现一条系统通知：「AO 需要一个业务决定 · D-0012」。

解锁打开后看到：

```
产品 PDF 二维码系统

需要你决定：
客户扫到无效二维码时，系统的回应方式
会泄露这个编号是不是真的存在

建议：让所有情况回应一致
影响：客户正常扫码不受任何影响
改错了：容易改回来

[ 同意 ]  [ 拒绝 ]  [ 稍后处理 ]  [ 查看摘要 ]
```

**看不到**：PR 编号、commit、分支、CI、门禁编号、用例编号、任何命令。

### 做出选择后

点「同意」即可，无需说明理由、无需打开电脑。任务自动继续。

若点「稍后处理」，任务保持暂停，不会自作主张。

### 合并与发布时

仍会被明确询问，且请求中会写明**这是不可逆动作**。手机上的「同意」只是授权，**实际合并在 Mac 侧执行并再次校验门禁**——门禁未过、存在未解决的 Advisor 冲突、或决策编号不匹配，一律不执行并回报。

### 可量化的判据

| 指标 | 目标 |
|---|---|
| 一个完整 Phase 中的人工介入次数 | **只出现在业务决策与合并批准两处** |
| 决策请求中含技术术语的比例 | **0** |
| 参谋七项输出完整率 | **100%**（缺项即判定未产出，不得通过） |
| 证据与实际代码的一致性 | **逐行一致**，不一致即视为无证据 |
| 超时默认同意的路径 | **不存在** |
| 自动执行动作的留痕覆盖率 | **100%** |

### 什么情况说明改造失败

- 业务负责人开始「习惯性点同意」——说明翻译层没让他真正理解在决定什么
- 出现「本该问却没问」的业务决定——说明 P0-3 的分类偏松，且缓解措施失效
- Advisor 给出通过但事后发现它没读源码——说明 P0-2 的软约束不足，需要引入机器校验
- 证据与代码不一致却无人发现——说明 P0-1 的验收标准未被真正执行

## 八、贯穿性风险（必须在 P0 阶段一并处理）

以下不属于任何单一模块，但会影响全部改造效果：

| 风险 | 建议处理时机 |
|---|---|
| **分类者即被授权者** | P0-3 的三条缓解措施必须同时生效 |

| **G-02 参谋原始输出未留存** | P0-2——补齐后作为留存规则生效的起点 |
