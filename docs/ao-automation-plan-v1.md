## 1. 当前人工节点分析

### 1.1 分析依据

本节不是设想，而是对 product-pdf-qr 已发生流程的复盘：从 G-01 需求确认、G-02 技术方案、G-03 开发准备到 Phase 1-A 实现，共经历 PR #2、#4、#6 三条链路与 Issue #1、#3、#5。

### 1.2 人工节点清单

| 节点 | 当前做法 | 分类 | 说明 |
|---|---|---|---|
| **业务规则确认** | 业务负责人逐条口头确认，Orchestrator 转达 Worker 写入文档 | **必须人工** | B-01~B-14 全部经此路径。属业务承诺与风险接受，不可自动化 |
| **需求范围确认（G-01）** | 业务负责人批准 | **必须人工** | 同上 |
| **技术方案判定（G-02）** | 业务负责人判定 | **必须人工** | 涉及风险接受与不可逆取舍 |
| **创建 GitHub Issue** | Orchestrator 依业务负责人给的规格撰写并创建 | **可自动化** | 内容源自已批准的计划文档，属机械转写 |
| **创建开发分支** | Worker 在 `ao spawn --branch` 时自动创建 | **已自动化** | 无人工介入 |
| **创建 Worker** | 业务负责人逐次批准后 Orchestrator 执行 | **可自动化**（需一次性授权） | 前提是 Issue 已批准且范围已冻结 |
| **创建 PR** | Worker 完成后自行创建 | **已自动化** | |
| **Reviewer 触发** | 业务负责人本人阅读 PR 并提出意见 | **待定义**（见 8.2） | 角色未定义，无法判断可否自动化 |
| **review context 生成** | Orchestrator 手工摘录分支内容（如 `review-context-pr6.md`） | **可自动化，但有结构性风险**（见 6.3） | 机械摘录可自动化，但"由谁决定摘什么"是风险点 |
| **DeepSeek Advisor 触发** | 业务负责人在外部运行 DeepSeek，把输出放入 `automation/outputs/`，再口头转达 | **可自动化** | 当前链路最长、失真风险最高的一环 |
| **参谋意见落库** | Orchestrator 转达 → Worker 写入文档 | **可自动化** | G-01 期间曾因此产生"七项不完整的转达摘要"，需二次补录原始输出 |
| **门禁判定** | 业务负责人判定 | **必须人工** | 治理规则明确要求门禁责任方独立判定 |
| **合并 PR** | 业务负责人手工合并 | **必须人工** | 治理规则明令禁止自动合并 |
| **发布生产** | 尚未发生 | **必须人工** | G-18 要求带时间的人工批准记录 |

### 1.3 分类小结

**必须人工确认（6 项）**
业务规则确认、需求范围确认、技术方案判定、门禁判定、合并 PR、发布生产。

共同特征：**涉及业务承诺、风险接受或不可逆后果**，且责任无法转移给 Agent。

**可以自动化（6 项）**
创建 Issue、创建 Worker、生成 review context、触发 Advisor、参谋意见落库、Reviewer 触发（待角色定义后）。

共同特征：**内容源自已批准的输入，属机械转写或调度**，本身不产生新的业务决定。

**已自动化（2 项）**
创建分支、创建 PR。

### 1.4 一个反直觉的观察

复盘显示，**当前流程中最容易出错的不是"自动化不足"，而是"人工转达过多"**。

具体证据：G-01 阶段 DeepSeek 的参谋意见经「业务负责人 → Orchestrator → Worker」两次转达后落库，结果七项固定输出中有五项标注为"本次转达未提供"，事后必须重新补录原始输出文件才补齐。

**结论**：自动化这类纯转达节点，降低的是失真风险，而不只是提升效率。这是本方案的首要动机，而非次要收益。

## 2. 自动化目标

### 2.1 目标形态

**当前形态**（每一步都要人工点头）：

```
任务 → 人工确认 → 执行 → 人工确认 → 执行 → 人工确认 → ...
```

问题：人工确认的密度掩盖了它们的**重要性差异**。「确认业务规则」与「确认可以创建 Issue」在流程上等权，导致真正需要深思的决策被淹没在机械批准里。

**目标形态**：

```
业务决策节点  →  自动执行链  →  责任审批节点
（少而重）        （多而机械）      （少而重）
```

### 2.2 三段的定义

**业务决策节点**——链路的输入。业务负责人在此确定业务规则、范围、风险接受。一旦确定即**冻结**，自动执行链在其边界内运行。

**自动执行链**——不产生新决定，只把已批准的输入转化为工程动作：建 Issue → 派 Worker → 建分支 → 实现 → 建 PR → 触发 Reviewer → 生成 review context → 调用 Advisor → 汇总证据。

**责任审批节点**——链路的出口。业务负责人基于自动链产出的完整证据，判定门禁并决定是否合并。

### 2.3 判断某节点属于哪一段

一个节点属于自动执行链，当且仅当它**同时**满足：

1. 输出完全由已批准的输入决定，不引入新的业务判断；
2. 出错可通过重跑或撤销单个 PR 完整恢复；
3. 不改变 requirements、不合并 main、不触及生产资产。

任一条不满足，即属于决策或审批节点，不得自动化。

### 2.4 明确不追求的目标

- **不追求减少人工审批的严格程度**。目标是让人工精力集中在真正的决策上，不是让批准变容易。
- **不追求端到端无人值守**。合并与发布永远需要人。
- **不追求缩短交付时间**为首要指标。首要指标是**减少转达失真**与**保证证据完整**。

## 3. 自动化权限边界

### 3.1 Orchestrator 自动权限（白名单）

| 权限 | 前置条件 | 可逆性 |
|---|---|---|
| 创建开发分支 | 对应 Issue 已批准 | 删分支即可 |
| 创建 GitHub Issue | 内容源自已批准的计划文档 | 关闭 Issue 即可 |
| 创建 Pull Request | Worker 已完成且 CI 已跑 | 关闭 PR 即可 |
| 触发 Reviewer | PR 已创建 | 无副作用 |
| 生成 review context | PR 已创建 | 文件可重生成 |
| 调用 Advisor | review context 已就绪 | 无副作用 |
| 创建 Worker | 对应 Issue 已批准且范围冻结 | 终止 Worker，分支未合并即无影响 |
| 记录参谋原始输出入库 | 输出文件存在且可校验 | 走 PR，可撤销 |

**白名单原则**：未在此表中的动作一律**不自动执行**。新增权限须走本文件的修订流程。

### 3.2 禁止自动（黑名单）

| 禁止项 | 理由 | 建议的强制手段 |
|---|---|---|
| **修改 requirements** | 唯一业务事实来源，改动等于改业务承诺 | CODEOWNERS + CI 断言 `requirements-v1.md` blob 不变 |
| **修改业务规则** | 同上；决策档案中的已确认结论亦不得自动改写 | CODEOWNERS 覆盖 `docs/decision-register-v1.md` |
| **合并 main** | 治理规则明令禁止自动合并 | 分支保护 + `auto_merge: false` |
| **发布生产** | G-18 要求带时间的人工批准记录 | 无自动化发布路径 |

### 3.3 三条补充禁令（本方案新增）

这三条不在原始要求中，但复盘显示它们同等重要：

**禁止自动修改治理文档。** `CLAUDE.md`、`docs/quality-gates-v1.md`、`docs/advisor-protocol-v1.md` 定义了规则本身。允许自动修改规则的系统等于没有规则。
> 例外与争议：Phase 1-A 中 Worker 修改了 `CLAUDE.md` 一行（把已失效的"没有功能代码"描述改为现状）。该改动方向正确，但**它证明了这条边界当前没有强制手段**。建议纳入 CODEOWNERS。

**禁止自动标记门禁通过。** 门禁通过是判定结果，不是状态累加。自动链只能**汇总证据**并标注"待判定"，不得写入"通过"。

**禁止 Agent 代替人类留下批准记录。** 当前 Issue #3、#5 上的"审核通过"记录均由 Orchestrator 依口头确认代写，并已注明"非业务负责人本人操作"。自动化会让这类代写更频繁、更不易察觉。
> 建议：批准必须是业务负责人在 GitHub 上的**真实操作**（PR approve、Issue 评论、label），Orchestrator 只能读取该操作作为条件，不得代写。

## 4. 多 Agent 协作模型

### 4.1 角色定义

| 角色 | 承担者 | 职责 | 权限 | 禁止 |
|---|---|---|---|---|
| **Orchestrator** | Claude | 任务拆解、流程调度、证据汇总、跨 Agent 协调 | 第 3.1 节白名单 | 不写功能代码、不判定门禁、不合并 |
| **Worker** | Codex | 工程实现、测试、提交 PR | 独立 worktree 与分支内的读写 | 不改 requirements、不扩范围、不跳测试、不合并 |
| **Advisor** | DeepSeek | 独立第二视角、质疑决定与方案 | **只读** | 不改任何文件、不指挥 Worker、不提交合并、不替业务负责人决定 |
| **Reviewer** | **待定义（见 8.2）** | 代码质量检查 | 待定义 | 待定义 |
| **业务负责人** | 人类 | 业务决策、门禁判定、批准合并、发布 | 全部 | —— |

### 4.2 独立性约束

按 `docs/advisor-protocol-v1.md`：同一任务的 **Orchestrator 本人与实施 Worker 不得兼任 Advisor**。

**本方案新增一条**：Reviewer 与 Worker 亦不得由同一 Agent 实例承担。若 Reviewer 最终定义为 Agent，必须与实施该 PR 的 Worker 分离，否则等于自审。

### 4.3 信息流向

```
业务负责人 ──决策──▶ Orchestrator ──任务书──▶ Worker
     ▲                    │                      │
     │                    │                      ▼
     │                    │                    PR + CI
     │                    │                      │
     │                    ├──review context──▶ Advisor（只读）
     │                    │                      │
     │                    ◀──七项意见────────────┘
     │                    │
     └──证据汇总 + 待判定──┘
```

**关键约束**：Advisor 的输入**不应只有 Orchestrator 的摘要**（见 6.3）。

## 5. 审核链路自动化

### 5.1 目标链路

```
Worker 完成
    ↓
PR 创建（Worker 自动）
    ↓
CI 自动运行（构建/类型/lint/测试）
    ↓
Reviewer 自动触发
    ↓
review-context 自动生成
    ↓
DeepSeek Advisor 自动复核
    ↓
证据汇总为"待判定"
    ↓
━━━━━━━━━━━━━━━━━━━━
人工批准合并（不可自动化）
```

### 5.2 各环节的自动化设计

**PR 创建**——已自动。要求 PR 描述必须包含：实现内容、覆盖的用例编号、门禁证据位置、明确标注不适用/未触发的门禁、已知未覆盖项。建议以 PR 模板强制。

**CI 触发**——已自动。CI **绿灯不等于门禁通过**：Phase 1-A 的 CI 全绿，但 G-09 仅部分覆盖。自动链必须保留这一区分，不得把 CI 结果直接翻译为门禁状态。

**Reviewer 触发**——待角色定义后设计。

**review-context 生成**——可自动化，但见 6.3 的结构性风险。自动生成应包含：PR 元信息、变更文件清单、核心文件**原文**（而非摘要）、对照检查表、四项明确结论。

**Advisor 调用**——可自动化。要点：
- 调用前校验 review context 完整性；
- 调用后**直接保存原始输出到文件**（如 `automation/outputs/advisor-<gate>-<n>.txt`），再由 Worker 走 PR 入库；
- **禁止 Orchestrator 转述后落库**——G-01 阶段的转达摘要缺失五项，就是这条缺失导致的；
- 校验七项固定输出完整性，缺项则标记为"未产出"，不得进入门禁证据。

**证据汇总**——Orchestrator 汇总为结构化清单，每项标注「通过 / 失败 / 不适用 / 未触发 / **待判定**」。**Orchestrator 不得写入"通过"**。

**人工批准合并**——不可自动化。

### 5.3 链路中断规则

任一环节失败，链路**停止**，不得跳过继续：

| 情形 | 动作 |
|---|---|
| CI 失败 | 退回 Worker 修复，不触发 Reviewer 与 Advisor |
| Reviewer 要求修改 | 退回 Worker |
| Reviewer 发现需求问题 | 重新触发 G-01，链路重置 |
| Reviewer 发现架构问题 | 重新触发 G-02，链路重置 |
| Advisor 七项输出不完整 | 标记未产出，门禁不得通过 |
| **Advisor 与 Orchestrator 冲突未解决** | **门禁判定为「未通过—冲突未解决」，转普通语言说明后交业务负责人裁决** |

## 6. 风险控制

### 6.1 防止 AI 自动修改业务规则

| 层 | 手段 |
|---|---|
| 权限层 | GitHub CODEOWNERS：`docs/requirements-*.md`、`docs/decision-register-v1.md`、`CLAUDE.md`、`docs/quality-gates-v1.md`、`docs/advisor-protocol-v1.md` 归业务负责人 |
| CI 层 | 断言 `docs/requirements-v1.md` 的 blob 哈希与基线一致（历史版本必须字节级不变） |
| CI 层 | 若 `requirements-v2.md` 有改动，PR 必须携带业务负责人添加的特定 label，否则 CI 失败 |
| 流程层 | Worker 任务书恒含「不得修改 requirements，冲突时停止并上报」 |
| 审查层 | review context 的第 4 节固定项：「是否修改 requirements」 |

**四层的必要性**：流程层靠自觉，审查层靠人看，只有权限层与 CI 层是强制的。当前项目**只有流程层与审查层**——Phase 1-A 中 `CLAUDE.md` 被 Worker 修改一行且顺利通过，正说明强制层缺失。

### 6.2 防止自动合并错误代码

- `agent-orchestrator.yaml` 已声明 `auto_merge: false`、`auto_rework: false`、`auto_advance: false`——**但其是否生效未经验证**（见 8.1）
- GitHub 分支保护：main 要求 PR、要求人工 approve、要求 CI 状态检查通过、禁止直推
- **CI 绿 ≠ 可合并**：证据清单中任一项为"待判定"即不得合并
- 合并动作只能由业务负责人在 GitHub 上执行，Orchestrator 无合并权限

### 6.3 防止信息不同步

这是本方案**最需要警惕**的一类风险，且部分由自动化本身引入。

**风险 A：Advisor 只看到 Orchestrator 的摘要。**
`review-context-pr6.md` 是 Orchestrator 手工摘录的，其开头已自我声明"摘录可能有遗漏或转述失真"。自动化会把这个中间层**固化**——Advisor 从此系统性地只看 Orchestrator 决定给它看的内容，而 Advisor 的全部价值在于**独立**。

缓解：
1. review context 中核心文件必须**附原文**，不得只给摘要；
2. 明确列出**未摘录**的文件清单，让 Advisor 知道盲区在哪；
3. 保留 Advisor 主动索取任意文件的通道；
4. 条件允许时，让 Advisor 直接读取分支，而不是读 Orchestrator 的转写。

**风险 B：参谋原始输出与落库内容不一致。**
G-01 已发生过：转达摘要缺失七项中的五项。
缓解：Advisor 输出**直接落文件**，Worker 只做搬运，禁止 Orchestrator 转述后落库。

**风险 C：文档与代码漂移。**
如 `CLAUDE.md` 中"没有功能代码"在 Phase 1-A 后失效。
缓解：CI 增加文档新鲜度检查（对应既有 W-01 告警门禁）；涉及状态描述的文档改动纳入 PR 检查项。

**风险 D：门禁状态被状态累加误读为通过。**
缓解：证据清单强制五态标注，Orchestrator 不得写"通过"。

### 6.4 防止 Agent 越权

| 越权形态 | 防线 |
|---|---|
| 扩大实现范围 | Issue 必含**非目标**清单；PR 描述须逐条对照；Reviewer 检查 |
| 修改测试以适配实现 | G-03 要求测试设计与实现分离；`test-plan-v1.md` 纳入 CODEOWNERS |
| 弱化测试让 CI 变绿 | 禁止 `skip`/`xfail`/放宽断言；CI 检测测试数量与跳过标记的异常变化 |
| 代替人类留批准记录 | 批准必须是业务负责人在 GitHub 的真实操作，Orchestrator 只读不写 |
| Orchestrator 直接改代码 | 角色约束：Orchestrator 不写功能代码；越界须业务负责人明确授权 |
| Advisor 越权 | 协议已定义只读、无执行权、无决定权 |
| Worker 触碰生产资产 | 环境边界：只用合成数据；生产操作由人类执行 |

**关于自我约束的诚实说明**：上表中多数防线依赖 Agent 遵守任务书，属**软约束**。真正的硬约束只有三类：GitHub 权限、CI 检查、以及人类的合并动作。**方案设计应假设软约束会被违反**，并确保违反时能被硬约束拦住或被审查发现。

## 7. 实施路线

### v1：当前项目可用

**范围**：只服务 product-pdf-qr，不做抽象。

内容：
1. 关闭 `agent-orchestrator.yaml` 的验证待办（见 8.1）——**这是 v1 的第一件事**，因为它决定后续一切
2. 定义 Reviewer 角色（见 8.2）
3. 建立硬约束：GitHub 分支保护 + CODEOWNERS + requirements blob 断言 CI
4. Advisor 输出直接落文件，取消 Orchestrator 转述环节
5. review context 自动生成（含原文与盲区清单）
6. 证据清单五态标注机制

**v1 完成判据**：Phase 1-B 的完整链路（Issue → Worker → PR → Reviewer → Advisor → 批准）中，**人工介入只出现在业务决策与合并批准两处**，其余环节无需人工转达。

**v1 明确不做**：不做跨项目抽象、不做自动合并、不做自动发布、不改变任何门禁的严格程度。

### v2：形成项目模板

**前置条件**：v1 在 product-pdf-qr 上完整跑通至少两个 Phase，且未出现自动化导致的失真或越权。

内容：
1. 把治理文档抽象为模板（requirements / decision-register / quality-gates / advisor-protocol / development-plan 的骨架）
2. 把 CI 硬约束抽象为可复用 workflow
3. 把 Worker 任务书结构化为模板
4. 把角色定义与权限边界固化为可配置项
5. 沉淀"哪些节点必须人工"的判定准则（第 2.3 节三条件）

**v2 的风险**：过早抽象会把 product-pdf-qr 的特殊性固化成通用规则。**建议在两个 Phase 跑通前不启动 v2**。

### v3：多项目复用

**前置条件**：v2 模板在至少一个新项目上验证过。

内容：
1. 模板实例化工具
2. 跨项目的 Agent 角色注册与独立性校验
3. 跨项目的门禁与证据标准统一
4. 多项目并行时的资源与优先级调度

**v3 的开放问题**：不同项目的风险等级差异极大（本项目二维码印在实物上不可召回，这一约束不具普适性）。跨项目复用必须保留**按项目调整门禁严格程度**的能力，而不是强制统一。

## 8. 本方案的前置条件与开放问题

### 8.1 `agent-orchestrator.yaml` 未验证（阻塞项）

该文件声明了 `auto_merge: false`、`auto_rework: false`、`auto_advance: false`、四类事件 `notify-only`，但文件头部与 `docs/delivery-status.md` 均注明：**其是否被 AO 或任何工具自动读取尚待验证**。

该待办自 G-01 起登记为「进入技术方案前验证」，历经 G-02、G-03 至今**未执行**。

**影响**：本方案 6.2 的第一道防线直接建立在它之上。若它实际未被读取，则"禁止自动合并"目前只靠人的自觉，没有任何机制保证。

**建议**：v1 的第一项工作就是验证它，并根据结果决定是继续依赖它，还是改用 GitHub 分支保护作为主防线。**在验证完成前，本方案的自动化范围不应扩大。**

### 8.2 Reviewer 角色未定义（阻塞项）

第 5 节要求"Reviewer 自动触发"，但本项目至今**没有定义过 Reviewer 是什么**——三条 PR 链路中，Reviewer 的职责一直由业务负责人本人承担。

必须先回答：

1. Reviewer 是人类、Agent，还是 CI 检查的集合？
2. 若是 Agent，由哪个模型承担？如何保证与 Worker 的独立性？
3. Reviewer 与 Advisor 的职责边界在哪？（Reviewer 查代码质量，Advisor 提供独立第二视角——但"发现架构问题"两者都可能触发）
4. Reviewer 的意见是否阻塞门禁？

**在此定义清楚前，"Reviewer 自动触发"无法设计。**

### 8.3 其他开放问题

1. **批准记录的真实性**：当前 Issue #3、#5 的"审核通过"由 Orchestrator 代写。自动化后这类代写会更频繁。是否要求业务负责人的批准必须是 GitHub 上的真实操作？
2. **Advisor 能否直接读分支**：若能，6.3 风险 A 大幅缓解；若不能，review context 的中间层将长期存在。
3. **自动化的回滚路径**：自动链出错时如何整体撤销？当前只有"关闭 PR"这一手段，是否足够？
4. **审计**：自动执行链的每一步是否需要留痕？建议需要，但会增加实现成本。
5. **v1 与 Phase 1-B 的关系**：v1 改造与 Phase 1-B 实现是否并行？并行会让两者互相干扰归因；建议串行，但会延后交付。
