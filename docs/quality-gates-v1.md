# 质量门禁：第一期

业务事实来源：`docs/requirements-v2.md`
版本日期：2026-07-31

## 门禁规则

- **强制阻塞**：未通过、证据缺失或结果不可判定时，工作不得进入下一阶段，PR 不得合并，版本不得发布。
- **告警不阻塞**：允许继续，但必须在交付记录中写明风险、责任人和处理期限；同一告警连续两个周期未关闭时升级为强制阻塞。
- “未触发”不等于“跳过”。只有尚未到达触发时机，或经评审确认当前交付物客观不存在适用对象时，才能记录为未触发，并附适用性判断。
- 不得通过删除、`skip`、`xfail`、注释、弱化断言或降低阈值让门禁变绿。
- 当前技术栈未定。下列标准与技术栈无关；精确命令、工具名称和报告路径必须在架构评审确定技术栈后补入，且不得改变通过标准。

## 强制阻塞门禁

### G-01 需求确认

- **门禁名称**：需求事实与验收条件确认（强制阻塞）
- **触发时机**：任何功能、业务变更或架构设计开始前。
- **通过标准**：范围、非目标、成功路径、失败路径、边界条件均已记录；每条验收条件可观测、可测试、可判定；所有用户可见未决项已登记且不存在影响本阶段设计的未决阻塞项。
- **验证方式**：业务负责人和产品负责人审阅需求与决策登记表，形成带日期的确认记录；测试人员逐条检查验收条件是否能转化为测试。
- **失败后的处理动作**：停止设计和实现，补齐或澄清需求；不得由工程自行假定用户可见行为。
- **责任方**：业务负责人批准，产品负责人维护，测试负责人验证可测性。

### G-02 架构评审

- **门禁名称**：架构、安全与可回滚性评审（强制阻塞）
- **触发时机**：技术栈选择、数据模型确定或首个功能实现前；架构边界重大变化时重触发。
- **通过标准**：方案明确组件边界、数据流、状态模型、故障处理、安全边界、备份与回滚；逐条映射核心不变量；所有高风险项有验证计划且无未接受的严重风险。
- **验证方式**：至少一名非方案作者按评审清单审阅设计，记录结论、异议和处置；对三态扫码、永久二维码、单一当前版本和不可物理删除做走查。
- **失败后的处理动作**：退回方案修改，关闭阻塞意见后重新评审，禁止先写实现再补评审。
- **责任方**：架构负责人提交，安全与测试负责人复核，Orchestrator 监督证据完整性。

### G-03 独立测试设计

- **门禁名称**：实现与测试用例设计分离（强制阻塞）
- **触发时机**：功能实现开始前，需求或风险模型变更后。
- **通过标准**：测试用例设计者与功能实现者不是同一主体；用例覆盖需求验收、反例、权限与状态转换、并发和回滚，且每个用例都有前置条件、步骤、预期结果和证据类型。
- **验证方式**：检查用例作者和实现者记录，执行需求到用例的双向追踪审阅。
- **失败后的处理动作**：重新指派独立测试设计者，补齐用例并评审后才能实现；不得让实现者单独自证。
- **责任方**：测试负责人组织，独立测试设计者产出，Orchestrator 检查职责分离。

### G-04 构建

- **门禁名称**：可重复构建（强制阻塞）
- **触发时机**：每次提交、PR 更新和候选发布。
- **通过标准**：从干净工作区按锁定输入执行构建，退出码为零，无缺失产物、未声明的网络下载或不可解释警告；同一提交重复构建得到等价产物。
- **验证方式**：执行技术栈确定后的标准构建命令并保存日志、退出码和产物摘要；具体命令待补。
- **失败后的处理动作**：停止后续测试与发布，修复构建或声明输入问题后从干净环境重跑。
- **责任方**：Worker 修复，CI 执行，评审者核验证据。

### G-05 类型检查

- **门禁名称**：静态类型检查零错误（强制阻塞）
- **触发时机**：每次提交和 PR 更新；仅在所选技术栈具备类型检查能力时触发。
- **通过标准**：项目规定范围内类型错误为零，无新增无理由豁免；豁免必须逐项有风险说明、责任人和到期日。
- **验证方式**：运行技术栈确定后的全量类型检查命令并保存机器可读报告；具体命令待补。
- **失败后的处理动作**：修正类型或经评审移除错误假设；不得扩大排除目录或使用宽泛忽略。
- **责任方**：Worker 修复，CI 执行，代码评审者审查豁免。

### G-06 代码规范

- **门禁名称**：lint 与 format 一致性（强制阻塞）
- **触发时机**：每次提交和 PR 更新。
- **通过标准**：lint 错误为零，格式检查无差异，无新增未批准规则禁用；自动格式化后工作区保持干净。
- **验证方式**：运行技术栈确定后的 lint 与 format-check 命令，记录退出码和差异；具体命令待补。
- **失败后的处理动作**：修复问题并全量重跑；不得通过全局禁用规则或排除修改文件绕过。
- **责任方**：Worker 修复，CI 执行，代码评审者检查规则变化。

### G-07 单元测试

- **门禁名称**：核心逻辑单元测试（强制阻塞）
- **触发时机**：每次影响业务逻辑或安全逻辑的提交和 PR 更新。
- **通过标准**：全部单元测试通过；修改逻辑的正常、异常和边界分支均有断言；覆盖率不低于项目批准基线且修改代码不存在无说明的覆盖缺口。
- **验证方式**：运行全量单元测试与覆盖报告；具体命令和阈值在技术栈确定后由评审批准补入。
- **失败后的处理动作**：修复实现或在不降低保护强度的前提下修正错误测试，然后全量重跑；禁止跳过失败用例。
- **责任方**：Worker 维护，独立测试设计者审阅用例，CI 执行。

### G-08 API 测试

- **门禁名称**：API 契约与错误处理验证（强制阻塞）
- **触发时机**：API 新增、修改或依赖的业务规则变化时；候选发布前全量触发。
- **通过标准**：已批准契约中的成功、认证失败、授权失败、非法输入、资源不存在、状态冲突和限流响应全部符合预期；响应不泄露内部标识、堆栈或敏感数据。
- **验证方式**：在隔离测试环境运行自动化契约与集成测试，保存请求摘要、响应断言和退出码；具体命令待补。
- **失败后的处理动作**：停止端到端与发布阶段，修正契约或实现并重新执行全套相关测试。
- **责任方**：独立测试人员设计，Worker 修复，CI 执行。

### G-09 端到端测试

- **门禁名称**：核心业务主线端到端验证（强制阻塞）
- **触发时机**：影响用户流程的 PR、候选发布和生产配置变更前。
- **通过标准**：使用合成数据完整通过“新建即出码 → 未上传 → 首次上传 → 新版替换 → 历史恢复 → 停用 → 重新启用”主线；二维码 URL 全程不变且每一步状态和当前版本指针准确。产品启用且有当前 PDF 时，服务端返回该 PDF 的正确内容并按浏览器在线打开方式设置响应；浏览器最终表现为预览或下载均可接受，不要求不同设备呈现形态一致。复制公开链接到另一个未登录会话仍能访问相同当前内容，产品停用后同一链接立即只能显示停用提示。产品编码去除首尾空格后只接受 1–64 个英文字母、数字、横线或下划线并以大写保存，中文、内部空格和其他特殊字符均被拒绝；格式正确但内容错误的编码只能停用后另建，不能修改、删除或进入新增状态。二维码文件名精确等于规范化编码加图片扩展名。Excel 中只有数据库既有重复时跳过重复并新增其他合法项，存在任意格式错误时列出全部错误且新增产品数量为零。重复上传与当前文件大小和 SHA-256 均相同的 PDF 时提示“与当前文件相同”，文件、版本和当前指针均不变化。
- **验证方式**：在专用测试环境执行自动化浏览器或等价黑盒测试，保存日志、截图或视频和关联提交；具体命令待补。
- **失败后的处理动作**：停止发布，定位首个失败状态转换，修复后从主线起点全量重跑。
- **责任方**：独立测试人员执行，Worker 修复，发布负责人核验证据。

### G-10 安全检查

- **门禁名称**：安全基线与依赖风险检查（强制阻塞）
- **触发时机**：每次 PR、依赖变化、认证或公开访问变化及候选发布。
- **通过标准**：密钥扫描无真实凭据；高危和严重安全问题为零；认证、会话、输入校验、访问控制与敏感日志检查通过；其余风险有批准的责任人和处理期限。
- **验证方式**：执行静态安全、依赖、密钥与配置检查，并由安全评审者对公开入口做人工走查；具体工具和命令待补。
- **失败后的处理动作**：立即停止合并和发布；若发现凭据先撤销并轮换，再修复根因与补测试。
- **责任方**：安全负责人定标与复核，Worker 修复，CI 执行自动检查。

### G-11 文件上传检查

- **门禁名称**：PDF 上传真实性与隔离验证（强制阻塞）
- **触发时机**：上传流程或存储处理变化时；候选发布前。
- **通过标准**：合法且与当前内容不同的 PDF 可上传；扩展名伪装、错误 MIME、错误文件签名、畸形结构、超限、空文件和路径字符攻击全部被拒绝。上传文件与当前 PDF 的文件大小和 SHA-256 均相同时必须提示“与当前文件相同”，不保存、不创建版本、不移动当前指针；所有失败文件均不可从公开入口读取。
- **验证方式**：用合成的正常、边界、恶意和内容重复样例执行自动化测试，核对响应、文件摘要、版本记录、当前指针与存储副作用。
- **失败后的处理动作**：关闭上传能力的发布路径，隔离测试残留，修复后重跑安全与上传全套用例。
- **责任方**：安全与测试负责人提供样例，Worker 修复，CI 执行。

### G-12 随机标识防枚举验证

- **门禁名称**：公开标识不可枚举与不可推导验证（强制阻塞）
- **触发时机**：标识生成、路由、数据迁移或二维码逻辑变化时；公网发布前。
- **通过标准**：标识由密码学安全随机源产生且有效熵不少于 128 位；不含或映射产品编码、自增 ID、时间序列；未知标识不泄露资源存在性；黑盒批量猜测不能发现顺序或前缀规律。
- **验证方式**：审查生成机制；对大量合成标识做唯一性、长度、字符集和序列相关性检查；执行未知标识黑盒请求并比较响应差异。
- **失败后的处理动作**：停止二维码生成与公网发布，废弃未发布的弱标识，评估已发布地址风险并形成迁移决策。
- **责任方**：安全负责人定义与复核，独立测试人员执行黑盒验证，Worker 修复。

### G-13 并发一致性验证

- **门禁名称**：并发写入与当前版本一致性（强制阻塞）
- **触发时机**：产品创建、导入、上传、恢复、启停或持久化机制变化时；候选发布前。
- **通过标准**：并发创建同一规范化大写编码最多成功一次；并发上传或恢复后恰有一个明确当前版本；重复请求不覆盖历史；失败或超时不留下半完成状态。Excel 导入在任意格式错误时必须原子失败，导入前后产品数据条数相同、新增数量为零；数据库既有重复仅被跳过，不导致无格式错误批次失败。扫码结果与最终提交状态一致。
- **验证方式**：在隔离环境用可重复并发与导入失败场景执行多轮测试，核对操作结果、导入前后产品数量、最终状态、历史记录和审计事件。
- **失败后的处理动作**：停止相关写入功能交付，修复原子性或幂等性并增加回归测试。
- **责任方**：架构负责人定义一致性约束，独立测试人员设计并发用例，Worker 修复。

### G-14 审计日志验证

- **门禁名称**：关键操作可追溯性（强制阻塞）
- **触发时机**：关键操作、认证、日志结构或审计存储变化时；候选发布前。
- **通过标准**：规定的登录、密码、创建、导入、上传、恢复与启停事件均记录时间、操作者、目标、动作、结果和关联标识；日志只追加、顺序可还原，且不包含密码、令牌、Cookie 或 PDF 内容。
- **验证方式**：对每类操作执行成功和失败样例，逐条核对审计事件；尝试普通应用路径修改既有事件并确认被拒绝。
- **失败后的处理动作**：停止发布，补齐事件或敏感信息清理；若已记录敏感信息，按安全事件处理并评估清除与轮换。
- **责任方**：安全负责人定义敏感边界，测试负责人验证，Worker 修复。

### G-15 备份验证

- **门禁名称**：备份完整性与可恢复性（强制阻塞）
- **触发时机**：首次部署准备、存储结构变化、备份策略变化，以及发布计划规定的周期。
- **通过标准**：配置、产品状态、当前版本关系、历史记录、审计日志和文件均纳入一致备份；恢复到隔离环境后引用关系完整、文件摘要匹配、核心只读验收通过；恢复时间与恢复点达到已批准目标。
- **验证方式**：只使用合成测试数据执行备份和隔离恢复演练，保存时间、大小、摘要、恢复日志和验收结果；严禁用真实业务文件做演练。
- **失败后的处理动作**：禁止首次公网发布或高风险变更，修复备份范围或恢复流程并重新演练。
- **责任方**：运维负责人执行，测试负责人验收恢复结果，发布负责人批准证据。

### G-16 Docker 构建

- **门禁名称**：容器镜像可重复与最小安全构建（强制阻塞）
- **触发时机**：架构确认采用容器交付后，每次容器配置变化和候选发布。
- **通过标准**：从锁定输入构建成功；运行进程非特权且非 root；镜像不含密钥、开发缓存或本地上传；严重和高危镜像漏洞为零；启动与健康检查通过。
- **验证方式**：执行技术栈确定后的干净容器构建、镜像内容审查、漏洞扫描和启动探测；具体命令待补。
- **失败后的处理动作**：停止发布，修复镜像层、权限、漏洞或健康检查后重新构建全部层。
- **责任方**：Worker 维护构建定义，安全负责人复核，CI 构建与扫描。

### G-17 公网验收

- **门禁名称**：公网候选环境黑盒验收（强制阻塞）
- **触发时机**：首次上线和每个候选发布；必须在专用候选环境完成，不得由 Agent 接触正式服务器或真实业务文件。
- **通过标准**：HTTPS、域名、三态扫码、当前版本切换、公开链接无登录访问与转发、停用即时失效、错误页无泄露和安全响应头均通过；主流移动端浏览器必须收到正确状态与当前 PDF 内容，但最终表现为预览或下载均可接受，不要求客户端呈现一致。验收仅使用合成数据，且候选版本与待发布提交一致。
- **验证方式**：由获授权人员在候选环境按验收脚本执行，保存提交标识、时间、环境、截图和结果；Agent 只审阅脱敏证据。
- **失败后的处理动作**：禁止发布，回到对应门禁修复并重新执行受影响的完整验收链。
- **责任方**：测试负责人执行，发布负责人确认环境，业务负责人确认用户可见结果。

### G-18 人工发布批准

- **门禁名称**：发布前人类明确批准（强制阻塞）
- **触发时机**：任何生产发布、数据迁移或对公网行为变更前。
- **通过标准**：所有适用强制门禁为通过；告警已有责任人和期限；发布范围、风险、备份、回滚步骤与负责人明确；有权限的人类留下带时间的批准记录。Agent 的完成声明或自动批准无效。
- **验证方式**：发布负责人核对门禁清单和证据索引，人工签署发布记录。
- **失败后的处理动作**：不得部署、不得合并作为发布替代；补齐证据或等待授权人决定。
- **责任方**：发布负责人组织，有权限的人类批准，Orchestrator 仅汇总状态。

### G-19 回滚演练

- **门禁名称**：应用、配置与数据变更回滚演练（强制阻塞）
- **触发时机**：首次上线、不可向后兼容变更、高风险发布以及发布计划规定的周期。
- **通过标准**：在隔离环境按书面步骤从候选版本回到上一稳定版本；服务恢复、数据关系完整、历史文件摘要一致、审计链不断裂；实际回滚时间不超过批准目标，且步骤不依赖未记录的个人知识。
- **验证方式**：使用合成数据执行计时演练，保存前后版本、命令记录、数据校验、文件摘要和验收结果。
- **失败后的处理动作**：禁止相应发布，修订变更策略或回滚手册并再次完整演练。
- **责任方**：运维负责人执行，测试负责人验证，发布负责人批准。

## 告警不阻塞门禁

### W-01 文档新鲜度

- **门禁名称**：非关键辅助文档新鲜度（告警不阻塞）
- **触发时机**：每次 PR 和候选发布。
- **通过标准**：README、操作说明和证据索引与当前行为一致，链接有效；不包括需求、决策、架构、安全和发布手册，这些关键文档缺失仍按对应强制门禁处理。
- **验证方式**：检查文档链接、最近变更和 PR 文档影响说明；具体自动检查命令待补。
- **失败后的处理动作**：记录告警、责任人和不超过一个迭代的期限；连续两个周期未处理时升级为强制阻塞。
- **责任方**：PR 作者修正，技术文档责任人复核。

### W-02 性能趋势

- **门禁名称**：非容量红线的性能趋势（告警不阻塞）
- **触发时机**：候选发布和定期基准测试。
- **通过标准**：关键流程相对已批准基线无超过约定比例的退化；当前未建立基线时，必须先记录样本规模、环境和结果。超出安全容量上限、超时导致不一致或可用性目标失败时，升级为强制阻塞。
- **验证方式**：在固定合成数据和固定环境运行可重复基准，比较历史结果；具体阈值和命令待架构与容量评审后补入。
- **失败后的处理动作**：登记趋势、原因、责任人和期限；若触及容量或一致性风险，立即转为强制阻塞。
- **责任方**：性能测试责任人执行，架构负责人评估风险。

## 证据记录模板

每次门禁执行至少记录：

- 门禁编号、关联 Issue/PR、提交标识、执行时间和执行者；
- 环境与合成数据说明；
- 完整命令或人工步骤、退出码、报告或截图位置；
- 结论：通过、失败或未触发；
- 失败与告警的责任人、处理期限和复验结果。
