## 使用说明

本登记表保留需求未明确事项的决策过程和工程约束。已确认业务结论已收编进 `docs/requirements-v2.md`；实现与验收应以 v2 为准。

- **待业务确认**：涉及用户可见行为、业务承诺、编码体系、合规或责任归属，工程不得自行定案。
- **已采用安全默认值**：工程依据安全、可测试、可回滚原则采用的默认方案；业务决定可覆盖，但必须留下覆盖记录并评估迁移成本。
- **已由业务负责人确认**：业务负责人已确认的补充规则；记录确认日期，后续实现与验收必须遵循。
- **部分确认**：同一条目包含多个子问题，已确认与仍待确认部分分别记录，不能把整个条目视为关闭。

技术默认值按以下优先级取舍：

1. 宁可可恢复的误拒，不要不可恢复的误接受。产品编码不可改、产品不可物理删除，错误写入的代价尤其高。
2. 所有公开访问必须经过应用层状态检查，不提供绕过产品状态或当前版本指针的路径。
3. 默认不引入邮件、短信、第三方账号等新外部依赖。
4. 默认不做物理删除。
5. 默认值必须集中配置、可自动测试，并能在业务确认后回滚或替换。

## 一、业务决策（均已确认）

### B-01 扫码后 PDF 的呈现方式

- 【问题】客户扫码后应在浏览器内预览 PDF，还是直接下载？“直接打开”没有明确这两种体验。
- 【推荐方案】服务端返回当前有效 PDF 内容，并按浏览器在线打开方式设置响应；不同手机或浏览器可能表现为预览或下载，两种表现均可接受，不要求系统强制统一。
- 【理由】浏览器和设备对 PDF 的最终呈现存在客观差异，业务目标是可靠返回当前有效内容，而不是控制所有客户端的展示形态。
- 【影响】验收改为检查响应内容、在线打开响应方式、产品状态和当前版本指针；不得把必须内联预览、必须出现下载按钮或所有设备表现一致作为通过条件。
- 【状态】已由业务负责人确认（2026-07-31）。
- 【覆盖记录】2026-07-31，业务负责人以“不强制统一预览或下载表现”覆盖原 B-01“内联预览并提供下载按钮”的推荐方案。差异是客户端最终呈现不再被统一约束；当前无功能代码，无迁移动作，质量门禁改为验证可判定的服务端契约并接受设备差异。

### B-02 产品编码格式

- 【问题】产品编码允许的字符、长度、空白和特殊符号如何定义，以便手工新增与导入能确定判定“格式错误”？
- 【推荐方案】输入时去除首尾空格；去除后只允许英文字母、数字、横线 `-` 和下划线 `_`，长度为 1–64 个字符；不允许中文、内部空格及其他特殊字符。
- 【理由】明确且受限的字符集可在不可修改、不可物理删除的前提下阻止错误编码写入，也保证二维码文件名可直接使用规范化编码。
- 【影响】手工新增、Excel 导入和所有编码入口必须使用同一规则；不符合规则的行属于格式错误。
- 【状态】已由业务负责人确认（2026-07-31）。

### B-03 产品编码大小写敏感性

- 【问题】`ABC-001` 与 `abc-001` 应视为同一产品还是两个不同产品？
- 【推荐方案】大小写不敏感，去除首尾空格并通过 B-02 校验后统一转换为大写保存；`A001` 与 `a001` 是同一编码。
- 【理由】单一大写表示消除展示值与判重值分叉，避免大小写差异生成不可删除的重复产品。
- 【影响】保存值、界面展示、判重、导入结果和二维码图片文件名均使用规范化后的大写编码。
- 【状态】已由业务负责人确认（2026-07-31）。

### B-04 误导入垃圾编码的处置

- 【问题】错误编码不能修改、对应产品也不能物理删除，是否允许其永久停用并从默认列表隐藏？
- 【推荐方案】第一期不新增“作废”或“隐藏”状态；格式正确但内容错误的编码只能停用，再创建正确编码，错误记录继续保留。
- 【理由】该方案遵守编码不可修改、产品不可物理删除的不变量，不制造删除或特殊状态例外。
- 【影响】后台会保留停用的错误编码；产品状态模型只需启用与停用，不再被额外状态阻塞。
- 【状态】已由业务负责人确认（2026-07-31）。

### B-05 历史 PDF 保留策略

- 【问题】历史 PDF 是否永久保留，是否存在法定留存期限、存储区域或销毁要求？
- 【推荐方案】历史 PDF 永久保留，只能查看和恢复，不能删除；不提供自动清理或人工物理删除入口。
- 【理由】永久保留与历史可查看、可恢复以及不物理删除的领域规则一致。
- 【影响】存储量只增不减，容量规划与备份必须覆盖全部历史文件；后续若改变保留规则，属于新的业务变更。
- 【状态】已由业务负责人确认（2026-07-31）。

### B-06 管理员密码重置机制与责任

- 【问题】第一期单管理员遗忘密码时，通过什么机制重置，以及由谁负责执行并确保其具备服务器访问权限？
- 【推荐方案】管理员忘记密码时，由业务负责人本人登录服务器执行密码重置命令；不提供网页或邮箱找回，持久化数据不得保存明文密码。
- 【理由】责任人与执行机制均明确，避免新增公开找回入口和邮件依赖。
- 【影响】后续运维手册必须把业务负责人本人列为执行责任方，并验证其受控服务器访问路径；不得把重置能力暴露在公开网页。
- 【状态】已由业务负责人确认（2026-07-31）。

### B-07 二维码地址泄露后的处置立场

- 【问题】永久二维码一旦外传，除停用产品外是否需要轮换公开地址？轮换会使已印刷二维码失效。
- 【推荐方案】二维码和公开链接允许转发，任何获得链接的人无需身份验证即可查看当前 PDF；第一期不轮换地址。需要停止访问时停用产品，原链接立即失效。
- 【理由】业务明确接受永久地址可转发且无法单独收回的风险；受控入口 T-01 与停用立即失效 T-02 共同提供停止访问的手段。
- 【影响】公开入口不做访问者身份验证；T-02 的实时状态检查是本规则成立的技术前提。客户在停用前已下载到本地的 PDF 副本无法追回。
- 【状态】已由业务负责人确认（2026-07-31）。

### B-08 Excel 导入的批次失败语义

- 【问题】同一批 Excel 同时包含合法行、重复行和格式错误行时，合法行应立即永久创建产品，还是整批不写入、修正后重试？需求已确认重复编码跳过，但未明确格式错误与合法行能否部分成功。
- 【推荐方案】采用混合语义：数据库中已存在的重复编码自动跳过，不阻断批次；只要 Excel 中存在任意格式错误，整批不导入，列出全部错误行号与原因，用户修正后重新上传。格式错误失败时必须原子回滚，产品数据新增数量为零。
- 【理由】重复跳过是已确认需求，而格式错误可能制造不可修改、不可物理删除的错误产品；二者风险不同，不能把重复误解为阻断全批的异常。
- 【影响】实现必须先完成全文件格式校验，再执行写入；测试需分别覆盖“只有重复时仍可新增其他合法行”和“存在任意格式错误时零持久化”。
- 【状态】已由业务负责人确认（2026-07-31）。

### B-09 二维码图片文件名的非法字符契约

- 【问题】二维码图片如何严格以产品编码命名，同时避免非法字符、静默改名和碰撞？
- 【推荐方案】直接使用 B-02、B-03 处理后的规范化大写产品编码命名，例如 `A001.png`；不得静默替换、截断或追加随机摘要。不符合编码契约的输入在产品入口即拒绝，兜底发现异常编码时拒绝生成文件而不是改写名称。
- 【理由】获批编码字符集本身对文件名安全，直接命名满足既有需求，并使编码与下载文件一一对应。
- 【影响】单个下载与 ZIP 内文件名都必须等于规范化编码加图片扩展名；任何偏差均为门禁失败。
- 【状态】已由业务负责人确认（2026-07-31）。

## 二、工程技术决策与业务覆盖记录

### T-01 PDF 经受控应用入口返回

- 【问题】PDF 能否通过长期有效的存储直链或静态目录绕过扫码入口访问？
- 【推荐方案】不暴露长期有效存储直链。每次公开请求先检查产品存在性、启停状态和当前版本，再通过受控响应返回内容；未来若使用临时签名地址，其有效期必须短且不可绕过状态检查。
- 【理由】只有统一入口才能保证停用、未上传和当前版本切换即时生效。
- 【影响】需要为文件传输容量和缓存策略做验证；实现可以替换，但公开状态检查契约保持不变。
- 【状态】已采用安全默认值。

### T-02 产品停用后旧 PDF 访问路径失效

- 【问题】产品停用后，先前获得的 PDF 访问路径是否仍能读取文件？
- 【推荐方案】所有由系统生成的在线访问路径在停用后立即失效，每次请求实时检查状态并只返回停用提示；已下载到客户本地的副本无法追回。
- 【理由】这直接落实“停用后扫码显示停用提示”，避免停用只改变页面却仍可绕过读取文件。
- 【影响】禁止长期公开缓存或永久文件直链；需覆盖停用前后同一路径的自动化测试。
- 【状态】已由业务负责人确认（2026-07-31）；这是 B-07 允许公开链接转发且不轮换地址的技术前提。

### T-03 编码归一化与重复保护

- 【问题】如何落实 B-02、B-03 的字符、长度、大小写和重复规则，避免生成多个不可删除产品？
- 【推荐方案】所有入口统一执行“去除首尾空格 → 校验 1–64 个英文字母、数字、横线或下划线 → 转换为大写 → 按大写值做原子唯一性判断”；只保存并展示规范化后的大写编码。
- 【理由】单一规范化值使保存、展示、判重和文件命名语义一致，原子唯一性保护并发写入。
- 【影响】`A001` 与 `a001` 只能对应同一产品；后续实现不得同时保留一个会参与业务展示的原始大小写版本。
- 【状态】已由业务负责人确认（2026-07-31）。
- 【覆盖记录】2026-07-31，业务负责人确认大小写不敏感但要求直接保存为大写，覆盖原“原始写法用于展示、另设归一化值判重”的安全默认值。差异是展示与持久化不再保留原始大小写；当前仓库无功能代码和业务数据，无迁移动作，后续实现直接采用新规则。若未来改变大小写策略，必须先评估已保存编码与二维码文件名的迁移。

### T-04 Excel 导入的原子校验与提交

- 【问题】如何同时落实“既有重复自动跳过”和“任意格式错误整批失败”，且失败时不留下产品数据？
- 【推荐方案】先对整份文件执行 B-02/B-03 规范化与格式校验并收集全部错误。若存在格式错误，只返回全部错误行号和原因，整个批次不写入；若不存在格式错误，再在同一原子提交中跳过数据库既有重复、写入其余合法编码。文件内规范化后重复项以首次出现为候选，后续项计入重复跳过。
- 【理由】先完整校验可保证格式错误时零持久化；重复项是需求明确允许跳过的结果，不应被误判为导致整批失败的格式异常。
- 【影响】测试必须在导入前后核对产品总数：格式错误失败后的新增数量严格为零；成功批次的新增数、重复跳过数与输入逐行结果守恒。
- 【状态】已由业务负责人确认（2026-07-31）。
- 【覆盖记录】2026-07-31，业务负责人以“重复跳过、格式错误整批原子失败”的混合语义覆盖原 T-04“合法行部分成功、错误行跳过”的安全默认值。差异是任意格式错误会阻止所有候选写入；当前无功能代码和产品数据，无需回滚或迁移，后续实现必须以零持久化断言为准。

### T-05 重复上传相同 PDF

- 【问题】管理员再次上传与当前 PDF 完全相同的文件时，是否保存并建立新版本？
- 【推荐方案】使用文件大小与 SHA-256 共同判断；两者均与当前 PDF 相同时直接拒绝，提示“与当前文件相同”，不保存文件、不创建版本记录、不移动当前版本指针。
- 【理由】相同内容不构成新业务版本，拒绝可避免无意义历史记录与存储增长。
- 【影响】重复上传是可判定的无副作用失败路径；不同大小，或大小相同但 SHA-256 不同，才进入正常新版本流程。
- 【状态】已由业务负责人确认（2026-07-31）。
- 【覆盖记录】2026-07-31，业务负责人以“相同文件直接拒绝且不建版本”覆盖原 T-05“提示后仍允许建立新版本”的安全默认值。差异是管理员不再能强制重复发布完全相同内容；当前无功能代码和文件数据，无需清理历史版本，后续实现需断言文件、版本和当前指针均无副作用。

### T-06 二维码文件名契约

- 【问题】如何使二维码图片名称严格等于规范化产品编码，同时保留异常输入的安全兜底？
- 【推荐方案】编码校验和大写规范化在产品入口完成，二维码图片直接命名为“规范化编码 + 图片扩展名”。不得静默替换、截断或追加摘要；若兜底检查发现编码不符合 B-02/B-03，拒绝生成文件。
- 【理由】获批字符集已排除路径分隔符、空格与特殊字符，正常路径不会触发失败关闭；兜底拒绝可防止异常存量或实现缺陷改写文件名。
- 【影响】单个与批量下载必须验证文件名精确一致且唯一，示例为 `A001.png`。
- 【状态】已由业务负责人确认（2026-07-31）。

### T-07 管理员凭据与重置技术边界

- 【问题】在不引入邮件、短信和第三方账号的前提下，如何安全存储、初始化和重置单管理员密码？
- 【推荐方案】密码使用经安全评审的现代抗暴力破解算法（默认 Argon2id）单向哈希，持久化数据不得保存明文密码；不设置硬编码默认密码。初始化与遗忘重置仅允许由业务负责人本人登录服务器后执行受控命令，不提供网页或邮箱找回；登录限速，会话 Cookie 使用 HttpOnly、Secure 和合理过期设置。
- 【理由】减少账号接管攻击面，并使敏感操作不暴露于公开网页；重置机制与执行责任人均已确认。
- 【影响】发布与应急手册必须包含业务负责人本人的受控访问、初始化、重置与审计证据；哈希参数和会话防护仍需技术评审。
- 【状态】重置机制与责任人已由业务负责人确认（2026-07-31）；哈希与会话防护为已采用安全默认值。

### T-08 历史版本只追加、不物理删除

- 【问题】上传新 PDF 或恢复历史版本时，旧文件与版本记录如何处理？
- 【推荐方案】上传只追加版本并移动当前指针；恢复只移动当前指针，不复制、不覆盖、不删除文件或记录，并追加包含操作者、时间、来源版本和目标版本的审计事件。
- 【理由】满足历史永久保留、可查看、可恢复和单一当前版本规则，也避免不可逆删除。
- 【影响】存储只增不减，需要容量监控与完整备份；不设计任何删除入口。
- 【状态】已由业务负责人确认（2026-07-31）。

### T-09 上传、导入与批量下载规模上限

- 【问题】PDF 大小、Excel 行数和 ZIP 批量数量没有上限，可能导致资源耗尽。
- 【推荐方案】采用集中配置的保守默认值：单个 PDF 50 MB、单次 Excel 5,000 行、单次 ZIP 1,000 个产品；超限明确拒绝并提示分批处理。数值在容量测试后可调整。
- 【理由】有界拒绝可恢复，无界接收可能拖垮服务；配置化使调整无需改变业务数据。
- 【影响】可能误拒绝真实大文件或大批次，因此公网验收前应以脱敏规模统计校准，并记录调整依据。
- 【状态】已采用安全默认值。

### T-10 公开随机标识的熵与生成

- 【问题】“随机、不可顺序猜测”需要可量化标准，不能只依赖看似随机的字符串。
- 【推荐方案】使用密码学安全随机源生成至少 128 位熵，以 URL 安全的无语义编码表示；公开标识与产品编码、自增 ID、创建时间无可推导关系，并以原子唯一性约束处理极小概率碰撞。
- 【理由】128 位熵使在线枚举在现实中不可行，且可以通过生成源审查、统计检查和黑盒枚举测试验证。
- 【影响】URL 会包含较长随机段；编码形式可替换，只要熵、不可推导性和永久性不降低。
- 【状态】已采用安全默认值。

### T-11 关键操作审计日志

- 【问题】产品、版本和管理员操作如何在故障或争议后还原？
- 【推荐方案】对登录成功与失败、密码修改或重置、产品创建、导入、启停、PDF 上传和历史恢复记录只追加审计事件，至少包含时间、操作者、目标、动作、结果和关联请求标识；日志不得记录明文密码、会话密钥或 PDF 内容。
- 【理由】单管理员系统仍需要可追溯性；只追加且敏感信息最小化，兼顾审计价值和泄露风险。
- 【影响】需要定义保留、访问控制和备份验证；审计格式可演进但既有事件不得无痕修改。
- 【状态】已采用安全默认值。

### T-12 文件上传内容验证

- 【问题】仅凭扩展名或客户端 MIME 类型无法确认上传内容确为 PDF，也无法阻止畸形文件进入存储。
- 【推荐方案】同时检查扩展名、声明类型、PDF 文件签名、结构可解析性和大小上限；验证失败时先拒绝且不建立版本。验证过程在隔离的临时区域进行，失败文件不进入正式存储路径。
- 【理由】拒绝可重新上传，接受恶意或损坏文件可能危及管理员和扫码用户；多层检查可独立测试。
- 【影响】极少数非标准 PDF 可能被拒绝，需要保留不含真实业务内容的失败诊断并由人工复核。
- 【状态】已采用安全默认值。
