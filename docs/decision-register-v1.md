# 决策登记表：第一期

业务事实来源：`docs/requirements-v1.md`
版本日期：2026-07-31

## 使用说明

本登记表只处理需求未明确或需要工程约束的事项，不改写已确认的业务规则。

- **待业务确认**：涉及用户可见行为、业务承诺、编码体系、合规或责任归属，工程不得自行定案。
- **已采用安全默认值**：工程依据安全、可测试、可回滚原则采用的默认方案；业务决定可覆盖，但必须留下覆盖记录并评估迁移成本。

技术默认值按以下优先级取舍：

1. 宁可可恢复的误拒，不要不可恢复的误接受。产品编码不可改、产品不可物理删除，错误写入的代价尤其高。
2. 所有公开访问必须经过应用层状态检查，不提供绕过产品状态或当前版本指针的路径。
3. 默认不引入邮件、短信、第三方账号等新外部依赖。
4. 默认不做物理删除。
5. 默认值必须集中配置、可自动测试，并能在业务确认后回滚或替换。

## 一、必须由业务负责人确认的业务决策

### B-01 扫码后 PDF 的呈现方式

- 【问题】客户扫码后应在浏览器内预览 PDF，还是直接下载？“直接打开”没有明确这两种体验。
- 【推荐方案】优先内联预览，同时提供明确的下载入口；不支持内联预览的浏览器降级为下载。
- 【理由】现场扫码通常以立即阅读为主，显式下载入口又能覆盖留存需求；该方案不改变二维码本身。
- 【影响】决定公开页面交互、响应方式和移动端兼容验收。若改为强制下载，只需替换呈现策略，数据无需迁移。
- 【状态】待业务确认（阻塞公网扫码体验验收）。

### B-02 产品编码格式

- 【问题】产品编码允许的字符、长度、空白和特殊符号尚未定义，但导入结果必须统计“格式错误”。
- 【推荐方案】业务负责人提供正式字符集与长度规则；确认前仅使用合成编码进行测试，禁止正式批量导入。测试暂定规则为去除首尾空白后长度 1–64 且不含控制字符，该规则不得被视为业务定案。
- 【理由】编码创建后不可修改且产品不可物理删除，贸然接受错误编码会形成不可逆脏数据；阻止正式写入是可恢复的误拒。
- 【影响】直接影响手工新增、Excel 校验、二维码文件名和重复判断。数据产生后再收紧规则可能迫使错误产品长期停用保留。
- 【状态】待业务确认（阻塞产品创建与正式批量导入）。

### B-03 产品编码大小写敏感性

- 【问题】`ABC-001` 与 `abc-001` 应视为同一产品还是两个不同产品？
- 【推荐方案】判重时大小写不敏感，展示时保留首次录入写法。
- 【理由】大小写录入差异常见；误建两个永久产品与二维码难以恢复，而把疑似项拒绝为重复可由管理员复核。
- 【影响】决定唯一性规则、导入计数和既有数据兼容方式。若业务选择大小写敏感，必须在首批正式数据写入前确定。
- 【状态】待业务确认（阻塞唯一性规则与正式批量导入）。

### B-04 误导入垃圾编码的处置

- 【问题】错误编码不能修改、对应产品也不能物理删除，是否允许其永久停用并从默认列表隐藏？
- 【推荐方案】第一期不新增删除或“作废”状态；错误编码只能停用，管理列表默认可筛除已停用项，审计记录保留误导入事实。
- 【理由】该方案遵守现有不变量且不制造删除例外；若业务不能接受长期保留，必须先变更领域规则。
- 【影响】可能积累停用记录；若新增“作废”状态，会影响扫码提示、判重、筛选、审计和验收范围。
- 【状态】待业务确认（阻塞产品状态模型评审）。

### B-05 历史 PDF 保留策略

- 【问题】历史 PDF 是否永久保留，是否存在法定留存期限、存储区域或销毁要求？
- 【推荐方案】在明确合规要求前永久保留，不自动清理、不提供物理删除入口。
- 【理由】需求要求历史版本可查看，删除不可逆；保留是更安全且可在未来新增受控归档策略的默认方向。
- 【影响】存储持续增长。若业务或合规要求销毁，需定义期限、审批、审计、备份同步删除和恢复边界。
- 【状态】待业务确认（阻塞存储容量与合规评审，不阻塞治理文档交付）。

### B-06 管理员密码重置责任

- 【问题】第一期只有单管理员且不引入邮件或短信找回时，谁有权发起和执行密码重置，如何核验身份？
- 【推荐方案】由业务指定的授权运维人员在受控环境执行离线重置流程，采用双人确认并保留审计记录。
- 【理由】避免引入新的外部依赖和网页找回攻击面，同时必须明确单管理员失去凭据时的责任链。
- 【影响】影响运维职责、应急时效和发布验收；若无法指定责任人，则必须另行评审找回通道及安全风险。
- 【状态】待业务确认（阻塞上线运维准备与公网发布）。

### B-07 二维码地址泄露后的处置立场

- 【问题】永久二维码一旦外传，除停用产品外是否需要轮换公开地址？轮换会使已印刷二维码失效。
- 【推荐方案】第一期接受不可轮换的永久地址承诺，泄露时通过停用产品阻断访问；业务同时确认该剩余风险。
- 【理由】“地址永久不变”与“泄露后轮换”不能同时满足，必须由业务选择对外承诺。
- 【影响】若要求轮换，需要重定义“永久二维码”、印刷与召回流程，并更新需求和验收标准。
- 【状态】待业务确认（阻塞公网风险接受与发布批准）。

### B-08 Excel 导入的批次失败语义

- 【问题】同一批 Excel 同时包含合法行、重复行和格式错误行时，合法行应立即永久创建产品，还是整批不写入、修正后重试？需求已确认重复编码跳过，但未明确格式错误与合法行能否部分成功。
- 【推荐方案】先完成整批预检并展示三类计数与逐行明细；只要存在格式错误，整批不写入，管理员修正文件后重新提交。仅包含合法行和重复行时，按需求新增合法行并跳过重复行。若业务希望保留“合法行部分成功”，必须明确确认其不可逆后果。
- 【理由】产品编码不可修改、产品不可物理删除；在错误批次中先创建合法行会产生无法整体撤销的用户可见结果。整批拒绝是可恢复的误拒，修正后可安全重试。
- 【影响】决定导入交互、提交边界、统计口径与幂等性测试。改为部分成功后无法仅靠切换事务策略撤回已经创建的产品。
- 【状态】待业务确认（阻塞实际 Excel 导入；确认前只允许无持久化预检）。

### B-09 二维码图片文件名的非法字符契约

- 【问题】需求要求二维码图片以产品编码命名，但 B-02 尚未确认编码字符集；若编码包含路径分隔符、控制字符、前导点、中文或目标文件系统不支持的字符，是拒绝编码、拒绝下载，还是允许文件名与编码不完全相同？
- 【推荐方案】优先在 B-02 中把正式产品编码限制为所有目标下载环境均可安全按原文命名的字符集，使文件名严格为“产品编码 + 图片扩展名”。若业务必须支持其他字符，应另行批准一个可逆、无碰撞且用户可理解的命名契约；不得静默替换、截断或追加短摘要。
- 【理由】静默转换会偏离“以产品编码命名”的既有需求，有限长度摘要也不能证明绝对唯一。确认前拒绝不安全命名是可恢复的误拒。
- 【影响】与 B-02、B-03 共同决定产品创建校验、单个下载、ZIP 内文件名及跨平台兼容测试。若业务允许转换，必须先更新需求或形成明确覆盖记录。
- 【状态】待业务确认（阻塞不满足已批准命名契约的产品创建与二维码下载）。

## 二、由工程系统采用安全默认值的技术决策

### T-01 PDF 经受控应用入口返回

- 【问题】PDF 能否通过长期有效的存储直链或静态目录绕过扫码入口访问？
- 【推荐方案】不暴露长期有效存储直链。每次公开请求先检查产品存在性、启停状态和当前版本，再通过受控响应返回内容；未来若使用临时签名地址，其有效期必须短且不可绕过状态检查。
- 【理由】只有统一入口才能保证停用、未上传和当前版本切换即时生效。
- 【影响】需要为文件传输容量和缓存策略做验证；实现可以替换，但公开状态检查契约保持不变。
- 【状态】已采用安全默认值。

### T-02 产品停用后旧 PDF 访问路径失效

- 【问题】产品停用后，先前获得的 PDF 访问路径是否仍能读取文件？
- 【推荐方案】所有由系统生成的在线访问路径在停用后立即失效，每次请求实时检查状态并只返回停用提示；已下载到客户本地的副本无法追回。
- 【理由】这直接落实“停用后扫码显示停用提示”，避免停用只改变页面却仍可绕过读取文件。
- 【影响】禁止长期公开缓存或永久文件直链；需覆盖停用前后同一路径的自动化测试。
- 【状态】已采用安全默认值。

### T-03 编码归一化与重复保护

- 【问题】在 B-03 确认前，如何避免大小写和空白差异生成多个不可删除产品？
- 【推荐方案】写入前去除首尾空白，使用独立的归一化值做大小写不敏感判重，同时保留首次录入原文用于展示；任何疑似冲突都拒绝新增并返回可复核原因。
- 【理由】误拒可人工复核，误接受会产生永久脏数据；展示值与判重值分离便于业务确认后调整。
- 【影响】需要原子唯一性保护和一致的归一化函数；若 B-03 决定大小写敏感，可替换判重规则而不改展示数据。
- 【状态】已采用安全默认值（受 B-02、B-03 最终决定约束，正式导入仍被阻塞）。

### T-04 Excel 导入预检不产生持久化写入

- 【问题】在 B-08 未确认批次失败语义前，工程如何验证文件解析、格式检查和重复统计，而不意外创建不可修改、不可删除的产品？
- 【推荐方案】将预检与提交明确分离。预检读取整批、按 B-02/B-03 的获批规则校验并生成成功新增候选、重复跳过、格式错误三类计数和逐行明细，但不创建产品、二维码或任何持久化业务记录；B-08 确认前禁用实际提交。
- 【理由】无持久化预检可以测试解析和统计，又不会提前决定用户可见的部分成功语义；任何结果都可丢弃后重试。
- 【影响】需验证预检零副作用、计数守恒和同一文件结果稳定。提交逻辑必须在 B-02、B-03、B-08 全部确认后按获批语义另行实现。
- 【状态】已采用安全默认值（实际 Excel 导入受 B-02、B-03、B-08 阻塞）。

### T-05 重复上传相同 PDF

- 【问题】管理员再次上传内容完全相同的 PDF 时应拒绝、忽略还是建立新版本？
- 【推荐方案】先用 SHA-256 内容摘要识别相同内容，明确提示“与当前版本内容一致”并要求再次确认；确认后允许建立新版本记录，不覆盖旧记录、不做物理删除。
- 【理由】硬拒绝可能阻止真实的重新发布需求，静默接受又容易制造误操作；二次确认是可恢复、可测试的折中。
- 【影响】版本数量可能增长，但审计链完整。若业务决定相同内容必须拒绝，可修改确认策略而无需迁移文件。
- 【状态】已采用安全默认值。

### T-06 二维码文件名契约的失败关闭

- 【问题】在 B-02、B-03、B-09 未确认前，工程如何避免路径穿越、跨平台非法文件名和批量 ZIP 重名，同时不改写“以产品编码命名”的需求？
- 【推荐方案】禁止静默替换、截断或追加摘要。生成文件前先按获批命名契约计算全部目标名称，并验证每个名称安全、与产品编码原文一致且在目标环境的比较语义下确定唯一；任一项不满足时拒绝对应单个下载，批量下载则在写入任何 ZIP 条目前整批拒绝。确认前仅用满足临时安全字符集的合成编码测试，不开放真实二维码文件下载。
- 【理由】失败关闭不会产生错误命名或覆盖文件，且可在业务确认后重试；先验证整个名称集合可确定性地证明无碰撞，不依赖有限摘要的概率保证。
- 【影响】部分编码可能暂时无法下载二维码，但不会生成偏离需求的文件。实际产品创建和下载需等待 B-02、B-03、B-09 的获批契约。
- 【状态】已采用安全默认值（真实二维码文件下载受 B-02、B-03、B-09 阻塞）。

### T-07 管理员凭据与重置技术边界

- 【问题】在不引入邮件、短信和第三方账号的前提下，如何安全存储、初始化和重置单管理员密码？
- 【推荐方案】密码使用经安全评审的现代抗暴力破解算法（默认 Argon2id）单向哈希；不设置硬编码默认密码。初始化与遗忘重置仅通过受控的离线管理命令完成，首次登录强制修改；登录限速，会话 Cookie 使用 HttpOnly、Secure 和合理过期设置。
- 【理由】减少账号接管攻击面，并使敏感操作不暴露于公开网页；具体责任人仍由 B-06 确认。
- 【影响】发布与应急手册必须包含初始化和重置证据；哈希参数应集中配置并可升级。
- 【状态】已采用安全默认值（上线受 B-06 阻塞）。

### T-08 历史版本只追加、不物理删除

- 【问题】上传新 PDF 或恢复历史版本时，旧文件与版本记录如何处理？
- 【推荐方案】上传只追加版本并移动当前指针；恢复只移动当前指针，不复制、不覆盖、不删除文件或记录，并追加包含操作者、时间、来源版本和目标版本的审计事件。
- 【理由】满足历史可查看和单一当前版本规则，也避免不可逆删除。
- 【影响】存储只增不减，需要容量监控；若 B-05 后续定义清理要求，必须新增独立、审批受控的策略。
- 【状态】已采用安全默认值。

### T-09 上传、导入与批量下载规模上限

- 【问题】PDF 大小、Excel 行数和 ZIP 批量数量没有上限，可能导致资源耗尽。
- 【推荐方案】采用集中配置的保守默认值：单个 PDF 50 MB、单次 Excel 5,000 行、单次 ZIP 1,000 个产品；超限明确拒绝并提示分批处理。数值在容量测试后可调整。
- 【理由】有界拒绝可恢复，无界接收可能拖垮服务；配置化使调整无需改变业务数据。
- 【影响】可能误拒绝真实大文件或大批次，因此公网验收前应以脱敏规模统计校准，并记录调整依据。
- 【状态】已采用安全默认值。

### T-10 公开随机标识的熵与生成

- 【问题】“随机、不可顺序猜测”需要可量化标准，不能只依赖看似随机的字符串。
- 【推荐方案】使用密码学安全随机源生成至少 128 位熵，以 URL 安全的无语义编码表示；公开标识与产品编码、自增 ID、创建时间无可推导关系，并以原子唯一性约束处理极小概率碰撞。
- 【理由】128 位熵使在线枚举在现实中不可行，且可以通过生成源审查、统计检查和黑盒枚举测试验证。
- 【影响】URL 会包含较长随机段；编码形式可替换，只要熵、不可推导性和永久性不降低。
- 【状态】已采用安全默认值。

### T-11 关键操作审计日志

- 【问题】产品、版本和管理员操作如何在故障或争议后还原？
- 【推荐方案】对登录成功与失败、密码修改或重置、产品创建、导入、启停、PDF 上传和历史恢复记录只追加审计事件，至少包含时间、操作者、目标、动作、结果和关联请求标识；日志不得记录明文密码、会话密钥或 PDF 内容。
- 【理由】单管理员系统仍需要可追溯性；只追加且敏感信息最小化，兼顾审计价值和泄露风险。
- 【影响】需要定义保留、访问控制和备份验证；审计格式可演进但既有事件不得无痕修改。
- 【状态】已采用安全默认值。

### T-12 文件上传内容验证

- 【问题】仅凭扩展名或客户端 MIME 类型无法确认上传内容确为 PDF，也无法阻止畸形文件进入存储。
- 【推荐方案】同时检查扩展名、声明类型、PDF 文件签名、结构可解析性和大小上限；验证失败时先拒绝且不建立版本。验证过程在隔离的临时区域进行，失败文件不进入正式存储路径。
- 【理由】拒绝可重新上传，接受恶意或损坏文件可能危及管理员和扫码用户；多层检查可独立测试。
- 【影响】极少数非标准 PDF 可能被拒绝，需要保留不含真实业务内容的失败诊断并由人工复核。
- 【状态】已采用安全默认值。
