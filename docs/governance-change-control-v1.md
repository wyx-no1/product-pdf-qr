# 治理变更控制 v1（Governance Change Control）

> 状态：**已经业务负责人确认**（2026-08-04）。对应 Issue #14。
> 本阶段只完成治理设计，不含代码实现，且**不实施任何强制治理工具**（见第 8 节）。
> 后续实施作为独立治理任务处理。

---

## 1. 本文档要解决的问题

PR #12 建立了门禁定义的**检测**能力：改动门禁定义会被机械标记为 `requires-re-review`。

该机制在 PR #12 自身上已实际生效，且未添加任何自我豁免。

**但检测不等于治理。** 标记之后由谁审、审什么、通过标准是什么，此前完全没有规则。PR #12 目前停在 OPEN 状态，根本原因就在这里。

本文档定义这套规则。

### 贯穿全文的一条不变量

> **被约束方不得控制约束本身。**

PR #12 的六轮 Review 每一轮都是它的一个实例：谁的代码在写权限下执行 → 门禁挂在哪个 commit → skip 判据验证什么性质 → 门禁定义是否受 PR 控制 → 工具配置能否被嵌套覆盖 → 解释器启动路径是否被覆盖。

本文档是第七个实例，也是层级最高的一个：**AO 不得修改并自动批准评价自己的规则。**

## 2. 变更等级

### 2.1 四级定义

| 等级 | 名称 | 包含 |
|---|---|---|
| **L1** | 普通代码变更 | 业务代码 `src/product_pdf_qr/**`、`migrations/**`、测试、普通文档、需求文档 |
| **L2** | 审核流程变更 | `docs/advisor-protocol-v1.md`、`docs/quality-gates-v1.md` 的流程条款、`docs/test-plan-v1.md` 的判定标准、`CLAUDE.md` 的协作与审核约定 |
| **L3** | Trusted Gate 变更 | `scripts/ao/trust.py` 的可信清单、`.github/workflows/**`、`Makefile`、`pyproject.toml` 中的门禁参数（覆盖率阈值、mypy strict、ruff 规则）、CI 直接调用的验证脚本、Evidence 生成与校验逻辑 |
| **L4** | 权限与规则变更 | 自动授权规则（P0-3，尚未实现）、**本文档自身** |

### 2.2 为什么本文档自身属于 L4

若修改本文档不落在最高等级，就存在明显的降级路径：**先改宽变更控制规则，再依据放宽后的规则提交实际变更。**

因此「修改分级与审批规则」必须与「修改自动授权规则」同级，且是最高级。

### 2.3 判定规则

**规则一：就高不就低。** 一次变更触及多个等级时，按其中最高的等级处理。

**规则二：判定必须机械可算，不依赖主观描述。** 不得依据 PR 标题、提交信息、作者自述或 Issue 分类来定级。

**规则三：判定在受信任侧执行。** 定级所依据的路径清单与判定代码，必须取自**默认分支**，不得取自被判定的 PR。

规则三是 PR #12 中 `evidence-publish.yml` 已确立的做法（可执行代码来自 base 分支，PR 检出物只当数据）的直接沿用。若定级代码取自 PR 自身，PR 改定级代码的同时即可把自己降为 L1。

### 2.4 判定依据

| 等级 | 机械判据 |
|---|---|
| L3 | PR #12 已实现的 `_definition_hash` 比对——与默认分支基准不一致即为 L3。此判据已在运行 |
| L2 / L4 | 路径归属：变更文件落入该等级的路径清单 |
| L1 | 默认。不落入 L2/L3/L4 的一切变更 |

**L3 已有可用的机械判据，L2 与 L4 依赖路径清单。** 路径清单本身属于 L4（它写在本文档内），因此修改清单需走 L4 审批。

## 3. 审批规则

### 3.1 角色

| 角色 | 性质 |
|---|---|
| **业务负责人** | 唯一的决策方 |
| **Orchestrator** | 协调方。组织审核、转达结论、派发任务。**无决策权** |
| **Worker** | 执行方。提出变更 |
| **Advisor**（DeepSeek） | 只读参谋。产出固定七项输出，**无执行权、无决策权**（见 `advisor-protocol-v1.md`） |
| **Reviewer** | 代码审查方。**当前尚未正式定义**——见第 6 节 |

### 3.2 谁可以提出

各等级均可由 Worker、Orchestrator 或业务负责人提出。**提出权不受限制，受限的是审批权。**

### 3.3 谁可以审核 / 批准

| 等级 | 需要的批准 |
|---|---|
| **L1** | Reviewer 通过 + Orchestrator 确认门禁全绿 |
| **L2** | 同 L1，且需业务负责人确认 |
| **L3** | Reviewer 通过 + **业务负责人显式批准**。Orchestrator 不得代为批准 |
| **L4** | Reviewer 通过 + **业务负责人显式批准**，且批准须为业务负责人**本人的 GitHub 操作** |

### 3.4 谁不能自审

以下四条为硬性禁止：

1. **提出者不得审核自己的变更。** 无论角色。
2. **AO（Orchestrator 与 Worker）不得批准 L3 与 L4。** AO 是被这些规则约束的对象。
3. **定级方不得是提出变更的一方。** 定级依据取自默认分支即为此。
4. **门禁定义的变更，不得由该门禁自身判定为通过。** 门禁能证明「代码通过了当前门禁」，不能证明「当前门禁的定义是恰当的」——后者只能由人判断。

### 3.5 禁止自我豁免

沿用 PR #12 已确立的原则：

- 不得添加「本次例外」
- 不得添加白名单
- 不得因「首次引入该机制」而跳过
- 不得把判定降级为 warning 或 neutral

**PR #12 如实把自己标记为 `requires-re-review`，是正确行为的范例。** 该先例应被保持——一旦开了豁免的口子，后来者会照此继续。

## 4. 规则变更期间

这是最容易出错的一段：一个 PR 提议修改规则，那么审判这个 PR 的，应该是新规则还是旧规则？

### 4.1 旧规则如何保护

**答案：旧规则。**

> 提议修改规则的变更，一律由**默认分支上现行的规则**判定，绝不由它自己引入的规则判定。

理由：若新规则可以判定引入它的那次变更，则任何规则都可以自我放行——PR 只需在同一次提交里既放宽规则、又依据放宽后的规则通过。这与第 2.3 节规则三是同一件事在时间维度上的表述。

**实现上**：判定代码与基准均取自默认分支，PR 的改动只作为**被判定的数据**。这一性质 PR #12 已经具备。

### 4.2 新规则如何生效

- **生效点**：合并进默认分支**之后**的下一次变更开始适用。
- **不追溯**：新规则不适用于引入它的那次变更本身，也不追溯适用于此前已批准的变更。
- **旧规则的失效点**：与新规则的生效点相同，不存在两套规则并行的窗口。

### 4.3 当前的实例

PR #12 修改了门禁定义（L3），因此：

- 由**旧规则**判定 → 标记 `requires-re-review` → **正确**
- 该标记不能由 AO 自行解除
- 解除需要业务负责人依据 L3 规则显式批准
- PR #12 引入的新门禁定义，在合并后才对后续 PR 生效

**本文档一旦通过，PR #12 的处理方式即有据可依。**

#### 业务负责人已确认的 PR #12 处理原则（2026-08-04）

1. **按修改前的旧规则审核**——即第 4.1 节的通则，PR #12 不由它自己引入的门禁定义判定
2. **`requires-re-review` 由人工确认**——AO 不得自行解除该标记
3. **不等待 Issue #14 的实施完成**——本文档的设计已足以支撑 PR #12 的审核；强制工具的实施是独立任务，不构成 PR #12 的前置

## 5. 核心不变量

> **AO 不能修改并自动批准评价自己的规则。**

拆成四条可检验的表述：

| # | 表述 | 当前保障 |
|---|---|---|
| 1 | AO 修改 L3/L4 时，判定其等级的依据不受该次修改影响 | ✅ 机械保障（基准取自默认分支，PR #12 已实现） |
| 2 | AO 不得批准 L3/L4 变更 | ⚠️ 规则约束，无机械强制 |
| 3 | 门禁全绿不构成对门禁定义变更的批准 | ✅ 机械保障（`requires-re-review` 不因 CI 绿而解除） |
| 4 | L4 的批准须为业务负责人本人操作 | ⚠️ 当前不成立，见第 6 节 |

**第 2 与第 4 条目前只是纸面规则。** 本文档如实记录这一点，不假装它们已被强制。

## 6. 现状如实记录

以下四项是已知缺口。本文档只记录，不在本 Issue 内解决。

### 6.1 治理文件保护是软约束

`CLAUDE.md` 中写有「Worker 禁止修改治理文件」，但：

- 无 CODEOWNERS
- 无分支保护规则
- 无 CI 断言

且 `CLAUDE.md` 自身也在被保护清单内——**规则与被规则保护的对象是同一份文件，没有外部强制**。

**可选的机械强制手段**（是否启用由业务负责人决定）：

| 手段 | 作用 | 代价 |
|---|---|---|
| **CODEOWNERS** | 指定路径的改动强制要求指定人审批 | 需配合分支保护才有强制力 |
| **分支保护规则** | 禁止直接推 main、要求指定检查通过、要求指定人批准 | 会改变当前工作流；紧急修复需走例外流程 |
| **CI 断言** | PR 触及治理文件路径时使门禁失败，除非携带授权标记 | 授权标记本身需防伪造，否则回到原问题 |

**建议**：CODEOWNERS + 分支保护是唯一能真正强制第 5 节第 2、4 条的组合。CI 断言单独使用会陷入「授权标记谁来发」的循环。

### 6.2 批准链的真实性

当前批准由 Orchestrator 在会话中转述，**不是业务负责人本人的 GitHub 操作**。

这意味着：第 5 节第 4 条「须为本人操作」当前不成立。

**改进方向**：L3/L4 的批准以业务负责人本人在 PR/Issue 上的 GitHub review 或评论为准，Orchestrator 的转述不构成批准。此项需要业务负责人本人参与，无法由 AO 单方面实现。

### 6.3 Reviewer 角色从未正式定义

第 3.1 节引用了 Reviewer，但该角色的承担方、职责边界、与 Advisor 的分工从未在治理文件中定义。

**影响**：第 3.3 节各等级都要求「Reviewer 通过」，而这一要求当前指向一个未定义的角色。

### 6.4 `agent-orchestrator.yaml` 从未验证

该配置声明为 notify-only（不自动合并、不自动返工），但**从未验证 AO 是否真的读取它**。

**影响**：若 AO 实际不读该文件，则「禁止自动合并」同样只是纸面规则。
