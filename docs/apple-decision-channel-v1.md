## 0. 设计出发点：真实发生过的打扰

本方案不是设想，而是对 product-pdf-qr 已发生流程的复盘。从 G-01 到 Phase 1-B，业务负责人被要求确认的事项中，**多数与业务无关**：

| 被打扰的事项 | 性质 | 业务负责人实际能判断吗 |
|---|---|---|
| 是否可以创建 GitHub Issue | 纯流程 | 无从判断，只能说「可以」 |
| 是否可以创建 Worker | 纯调度 | 同上 |
| 是否可以把设计文档提交入库 | 纯操作 | 同上 |
| PR #6 的 healthcheck 误判如何修 | 纯技术 | 需要懂 PostgreSQL 初始化时序 |
| `verify_clean_start.sh` 的 jq 依赖 | 纯技术 | 需要懂 shell 与 Docker |
| rebase 冲突如何解决 | 纯技术 | 需要懂 git |
| 三态提示优先级（停用 vs 未上传） | **真业务** | ✅ 能判断，且只有他能判断 |
| 二维码地址泄露是否接受风险 | **真业务** | ✅ 同上 |
| Excel 格式错误是否整批失败 | **真业务** | ✅ 同上 |

**结论**：真正需要业务负责人的决定不足十次，而打扰次数远超此数。本方案的目标不是「减少确认」，而是**把确认集中到他真正能判断、且只有他能判断的事情上**。

## 1. 自动授权范围

以下动作**默认自动执行，不再询问业务负责人**：

| 动作 | 可逆性 | 出错后果 |
|---|---|---|
| 创建 GitHub Issue | 关闭即可 | 多一条记录 |
| 创建分支 | 删除即可 | 无 |
| 创建 Worker | 终止即可，未合并即无影响 | 浪费算力 |
| 创建 PR | 关闭即可 | 多一条记录 |
| 触发 Reviewer | 无副作用 | 无 |
| 调用 DeepSeek Advisor | 无副作用 | 无 |
| CI 重试 | 无副作用 | 浪费算力 |
| rebase 与低风险冲突处理 | 分支可重置 | 需重做 rebase |
| 技术缺陷修复与重新测试 | PR 未合并即可撤销 | 需重做 |
| 生成审核证据索引 | 文件可重生成 | 无 |

### 1.1 判定某动作可自动执行的三个条件

必须**同时**满足，缺一即需人工：

1. **不改变业务规则、功能范围或用户可见行为**
2. **出错可通过撤销单个 PR 或终止单个任务完整恢复**，不留数据或外部副作用
3. **不合并 main、不发布生产、不触及正式服务器或真实业务文件**

### 1.2 「低风险冲突处理」的边界（必须写死，否则会被滥用）

rebase 冲突自动处理**仅限**：

- 冲突只发生在文档文件，且解决方式是**保留两侧内容的并集**或**采用已发生事实**（如「PR 已合并」取代「PR 待审核」）
- 冲突不涉及 requirements、治理文件、测试判定标准
- 解决后**不改变任何一侧原本表达的业务含义**

**任一条不满足即升级为人工决策。** 尤其：若两侧对同一业务规则给出不同表述，那不是冲突，是矛盾，必须人工裁决。

### 1.3 ⚠️ 本节最大的结构性风险

**分类者与被授权者是同一方。**

Orchestrator 既执行这些动作，又判断某动作属于「自动」还是「人工」。这与 review-context 曾经的问题同构：被约束方自行决定约束边界。

缓解（三条，缺一不可）：

1. **全部自动执行的动作必须留痕**，形成可事后批量查阅的清单，而非静默发生
2. **分类存疑时默认升级为人工**，不得默认自动——「不确定算不算业务决定」本身就是需要人判断的信号
3. **Advisor 在门禁复核时检查分类是否合理**，发现被错误归类为「自动」的业务决定须指出

## 2. 必须保留人工决策的范围

只允许以下五类情况打断业务负责人：

| 类别 | 判定标准 | 本项目已发生的实例 |
|---|---|---|
| **改变业务规则** | 影响 `requirements-v2.md` 中任一条目，或影响客户/管理员可见行为 | 三态优先级、Excel 空白行处理、停用期间管理端权限 |
| **改变功能范围** | 增减功能、改变阶段边界、改变「第一期不做」清单 | Phase 1 拆为 1-A/1-B、Phase 1-A 是否含认证 |
| **明显增加成本或周期** | 需要新增阶段、重做已完成工作、引入新外部依赖 | （尚未发生） |
| **接受不可逆业务风险** | 后果无法通过撤销 PR 或恢复备份消除 | 二维码地址泄露不轮换、历史版本永久保留 |
| **最终合并与正式发布** | 合并 main、部署候选或生产环境 | PR #2/#4/#6/#7 的合并 |

### 2.1 边界情形的处理

| 情形 | 归属 | 理由 |
|---|---|---|
| 技术方案有两种做法，业务结果相同 | **自动** | 业务负责人无从判断，且结果一致 |
| 技术方案有两种做法，业务结果不同 | **人工** | 已构成业务规则选择 |
| 发现设计文档自相矛盾 | **人工**（除非矛盾只有一种消解方式） | 见 Governance Issue #9 的处理：矛盾若能由已批准文档唯一确定，可由 Orchestrator 消解并留痕；否则必须上报 |
| 门禁失败，修复方式明确 | **自动** | 属技术缺陷修复 |
| 门禁失败，唯一修复方式是放宽标准 | **人工** | 放宽门禁等于改变质量承诺 |

## 3. 决策翻译层

**技术问题不得原样交给业务负责人。** 每个决策请求必须经过翻译，产出固定六项：

| 字段 | 要求 | 禁止 |
|---|---|---|
| **发生了什么** | 一句话，用业务语言 | 出现 git、PR、CI、分支、容器、SQL 等词 |
| **对业务有什么影响** | 客户或管理员会感受到什么 | 「架构耦合」「事务隔离」这类描述 |
| **推荐方案** | 明确一个，不要列平行选项 | 「建议根据情况选择」 |
| **其他选择** | 最多两个，各一句话 | 超过三个总选项 |
| **判断错误的后果** | 明确「容易改回来」或「改不回来」 | 「视情况而定」 |
| **按钮** | 同意 / 拒绝 / 稍后处理 / 查看摘要 | 自由文本输入 |

### 3.1 翻译示例（取自本项目真实发生的决策）

**技术原文**：

> 公开端点对不存在的 token 返回 404、对停用产品返回 200，仅凭状态码即可探测 token 是否对应真实产品，构成存在性探测通道。建议四态统一返回 200。

**翻译后**：

> **发生了什么**
> 有人拿到一个乱编的二维码网址时，系统的回应方式会泄露「这个编号是不是真的存在」。
>
> **对业务有什么影响**
> 外部的人可以用这个方法试探出你们有哪些产品编号，虽然看不到资料内容。
>
> **推荐方案**
> 让系统对所有情况都用同一种方式回应，看不出区别。客户正常扫码不受任何影响。
>
> **其他选择**
> 保持现状，接受这个试探风险。
>
> **判断错误的后果**
> 容易改回来。现在还没上线，改动只影响提示页面，不影响已有数据。
>
> **[ 同意 ]  [ 拒绝 ]  [ 稍后处理 ]  [ 查看摘要 ]**

### 3.2 翻译质量的自检

生成决策请求前，Orchestrator 须自检：

- 把这段话读给一个不懂程序的人，他能不能复述出「要决定什么」？
- 「推荐方案」是否给出了明确倾向，而不是把选择难题原样转交？
- 「判断错误的后果」是否诚实——**不可逆的事必须说不可逆**，不得为了让对方容易点头而淡化

## 4. Apple 通道设计

### 4.1 ⚠️ 必须先说明的平台限制

**iOS 快捷指令无法由 iCloud Drive 的文件变化触发。**

iPhone 个人自动化的触发条件仅限：时间、闹钟、睡眠、健身、收到邮件/信息、Wi-Fi、蓝牙、NFC、专注模式、电量、充电器、App 打开或关闭、CarPlay、低电量模式。**没有「文件出现」或「iCloud Drive 变化」。**

因此「Mac 写文件 → iPhone 自动弹通知」这条最直觉的路径**在原生能力下不成立**。必须另选推送载体。

其他相关限制：

| 限制 | 影响 |
|---|---|
| iOS 快捷指令**不能运行 shell 脚本** | iPhone 侧只能读写文件或发起网络请求，AO 交互只能在 Mac 侧 |
| iCloud Drive 同步**不保证即时**，可能延迟数分钟 | 决策请求送达存在不确定延迟 |
| Mac 休眠时**不执行轮询** | 决策结果可能滞留，直到 Mac 唤醒 |

### 4.2 方案 A（推荐）：提醒事项作为推送载体

利用「提醒事项」经 iCloud 同步且**带闹钟通知**这一原生能力，把它当作推送管道。

```
┌─── Mac ───────────────────────────────────────────┐
│ AO 需要业务决策                                     │
│   ↓                                               │
│ 生成决策请求 JSON（含唯一编号）                       │
│   → 写入 iCloud Drive/Shortcuts/ao-decisions/pending/ │
│   ↓                                               │
│ 触发 macOS 快捷指令「发起决策」                       │
│   → 创建提醒事项：标题=业务化一句话，到期=立即         │
└───────────────────┬───────────────────────────────┘
                    │ iCloud 同步
                    ▼
┌─── iPhone ────────────────────────────────────────┐
│ 收到提醒事项通知（系统原生，锁屏可见）                 │
│   ↓ 点击通知 / 打开快捷指令                          │
│ 运行 iOS 快捷指令「处理决策」                         │
│   → 读取 iCloud Drive 中的待决策请求                 │
│   → 显示：发生了什么 / 业务影响 / 推荐方案            │
│   → 菜单：同意 / 拒绝 / 稍后处理 / 查看摘要           │
│   ↓ 用户选择                                       │
│ 写入 answers/<决策编号>.json（含选择与时间）           │
│ 完成对应提醒事项                                    │
└───────────────────┬───────────────────────────────┘
                    │ iCloud 同步
                    ▼
┌─── Mac ───────────────────────────────────────────┐
│ AO 轮询 answers/ 目录                              │
│   → 读到结果，校验编号与幂等标记                      │
│   → 记录决策日志（时间、编号、选择）                   │
│   → 按结果继续或保持暂停                             │
└───────────────────────────────────────────────────┘
```

**优点**：全程 Apple 原生，无第三方服务，通知是系统级的、锁屏可见、不会被淹没。

**代价**：

- 提醒事项被当作通知管道，语义上略有借用
- iCloud 同步延迟不可控
- 需要 Mac 侧轮询 answers 目录

### 4.3 方案 B（备选）：本机 HTTP + 快捷指令直连

Mac 侧运行一个只监听本机/内网的小服务；iPhone 快捷指令用「获取 URL 内容」直接读写。

**优点**：即时、有状态、无同步延迟。

**代价**：需要 iPhone 能访问到 Mac（同一 Wi-Fi 或私有网络），出门在外不可用；且引入了一个需要维护的常驻服务。

### 4.4 v1 选择

**采用方案 A**，理由是它不依赖网络可达性，出门在外也能用，且不引入常驻服务。

**但必须接受它的代价**：送达延迟不可控。因此 —— **超时后保持暂停，绝不默认同意**（见第 6 节）。若延迟成为实际问题，再评估方案 B。

### 4.5 目录结构

```
iCloud Drive/Shortcuts/ao-decisions/
├── pending/     <decision-id>.json    待决策请求（Mac 写，iPhone 读）
├── answers/     <decision-id>.json    决策结果（iPhone 写，Mac 读）
├── processed/   <decision-id>.json    已处理归档（Mac 移入）
└── log/         decisions.jsonl       只追加决策日志
```

## 5. 第一版范围

只支持四个操作：

| 按钮 | 含义 | 后续动作 |
|---|---|---|
| **同意** | 采纳推荐方案 | AO 按推荐方案继续 |
| **拒绝** | 不采纳推荐方案 | AO **停止该任务**，等待进一步指示；不自动改用其他方案 |
| **稍后处理** | 暂不决定 | 请求保留在 pending，任务保持暂停 |
| **查看摘要** | 展开业务化详情 | 显示完整六项翻译内容，不结束决策 |

### 5.1 v1 明确不做

- 自由文本回复
- 多选项选择（超过「同意/拒绝」的分支）
- 在手机上查看代码、日志、CI 结果
- 在手机上触发合并或发布（**合并仍需在 Mac 上确认执行**，见 6.6）
- 决策历史浏览界面
- 多项目并行决策（v1 只服务 product-pdf-qr）

### 5.2 「拒绝」为什么不自动改用备选方案

若拒绝后自动切到「其他选择」，等于用一次点击替代了两次决定。业务负责人拒绝推荐方案时，可能是要选备选、也可能是要重新讨论——**这两者不能由系统猜**。v1 一律停下等待。

## 6. 安全边界

### 6.1 通知内容禁止项

**绝不出现在通知、提醒事项标题或决策请求中**：

- API Key、令牌、密码、密码哈希
- 服务器地址、内网 IP、端口、路径
- 代码片段、SQL、堆栈、命令行
- 产品编码、`public_token` 等业务标识
- 客户数据或真实业务文件内容

### 6.2 锁屏泄露（本节新增，原始要求未提及）

**通知在锁屏可见。** 即使不含技术信息，业务化摘要本身也可能泄露经营信息（如「是否接受某产品资料被外传的风险」）。

要求：**提醒事项标题只写决策类型与编号**，业务详情放在打开快捷指令后展示，需解锁才能看到。

例：标题写「AO 需要一个业务决定 · D-0007」，而非「是否接受二维码链接可被转发的风险」。

### 6.3 唯一编号与幂等

- 每个决策请求有唯一编号 `D-<递增序号>`，全局不复用
- 结果文件以编号命名，**同一编号只处理一次**
- Mac 侧读到结果后立即移入 `processed/`，再次出现同编号结果一律忽略并记录异常
- 请求内容含内容哈希，防止请求在 pending 中被篡改后仍被采纳

### 6.4 超时行为

**超时后保持暂停，绝不默认同意。**

- 无超时自动决策，无「静默即同意」
- 超过约定时长（建议 24 小时）后，Mac 侧发出一次提醒，**请求仍保留在 pending**
- 任务保持暂停状态，不空转、不占用资源

### 6.5 留痕

`log/decisions.jsonl` 只追加，每条记录：

```
决策编号 / 发起时间 / 决策类型 / 业务摘要 /
推荐方案 / 用户选择 / 选择时间 / 后续动作
```

**日志只追加不修改**，与项目既有的审计原则一致。

### 6.6 合并与发布不在手机上执行

即使业务负责人在手机上点了「同意合并」，**合并动作仍在 Mac 侧由 AO 执行并留痕**，且执行前再次校验：

- 该 PR 的所有强制门禁是否通过
- 是否存在未解决的 Advisor 冲突
- 决策编号是否匹配该 PR

**任一不满足则不执行合并**，并回报业务负责人。手机上的「同意」是授权，不是执行。

## 7. 用户视图

业务负责人在 iPhone 上**只看到四样东西**：

```
┌─────────────────────────────────┐
│  产品 PDF 二维码系统              │   ← 当前项目
├─────────────────────────────────┤
│  需要你决定：                     │
│  客户扫到无效二维码时，系统的       │   ← 需要决定的事情
│  回应方式会泄露编号是否存在        │
├─────────────────────────────────┤
│  建议：让所有情况回应一致          │   ← 推荐方案与影响
│  影响：客户正常扫码不受影响        │
│  改错了：容易改回来               │
├─────────────────────────────────┤
│  [ 同意 ]  [ 拒绝 ]              │   ← 操作按钮
│  [ 稍后处理 ]  [ 查看摘要 ]       │
└─────────────────────────────────┘
```

### 默认隐藏

Git、分支、PR 编号、Worker、CI、门禁编号、容器、命令、技术日志、测试用例编号、文件路径——**一律不出现在手机界面**。

需要时可在 Mac 上查阅完整记录；手机侧不提供技术视图入口。

## 8. 实施步骤（本轮不实施）

按依赖顺序，每步可独立验证：

### 第 1 步：决策请求的数据结构与日志

定义 JSON 结构与 `decisions.jsonl` 格式，先由 Mac 侧手工写入样例文件验证。**不涉及任何自动化**，只确认结构够用。

### 第 2 步：Mac 侧「发起决策」快捷指令

输入决策请求 JSON → 写入 pending → 创建提醒事项（标题只含类型与编号）。手工触发验证 iPhone 能否收到通知。

**这一步验证的是本方案最大的不确定性**：iCloud 同步延迟是否可接受。若此处失败，应转向方案 B，不必继续后续步骤。

### 第 3 步：iPhone 侧「处理决策」快捷指令

读 pending → 展示六项翻译内容 → 四按钮菜单 → 写 answers → 完成提醒事项。手工运行验证。

### 第 4 步：Mac 侧结果轮询与幂等

轮询 answers → 校验编号与内容哈希 → 移入 processed → 写日志。**先只做记录，不真正驱动 AO**，验证幂等与超时行为。

### 第 5 步：接入 AO 的暂停与恢复

把决策通道接入实际流程：需要人工决策时暂停任务并发起请求，收到结果后继续或保持暂停。

### 第 6 步：自动授权范围生效

把第 1 节的十类动作改为默认自动执行，同时**打开自动动作留痕**（1.3 节的缓解措施必须同步生效，不得先放开授权后补留痕）。

### 第 7 步：真实流程验证

在 Phase 2 的一个完整链路上验证：统计被打扰次数是否只剩真业务决定，以及是否有本该上报却被自动执行的动作。

## 9. 已知风险与开放问题

| 问题 | 说明 |
|---|---|
| **分类者即被授权者** | 见 1.3。三条缓解措施必须同时生效，否则自动授权会逐步吞掉本应人工的决定 |
| **iCloud 同步延迟不可控** | 第 2 步就要验证；不可接受则转方案 B |
| **Mac 休眠时结果滞留** | v1 接受该限制；任务保持暂停不会出错，只是变慢 |
| **提醒事项被当作推送管道** | 语义借用；若业务负责人也用提醒事项管理个人事务，需用独立列表隔离 |
| **翻译质量无法自动校验** | 六项内容是否真的「不懂程序也能懂」，只能靠人抽查。建议前若干次决策由业务负责人反馈翻译是否可读 |
| **v1 不支持多选项** | 遇到需要三选一的业务决定时，只能拆成多次「同意/拒绝」，体验较差。若实际频繁出现，应在 v2 支持 |
| **与既有治理规则的关系** | 本方案不改变任何门禁、不改变「禁止自动合并」、不改变 Advisor 强制调用节点。合并仍需人工授权 + Mac 侧校验执行 |

## 10. 本方案不做的事

- 不修改任何权限配置或 `agent-orchestrator.yaml`
- 不写功能代码、不创建 Worker
- 不接入企业微信、飞书、钉钉或任何第三方 IM
- 不开发独立 App
- 不改变任何既有门禁的严格程度
- 不引入自动合并或自动发布能力
- 不在手机侧暴露任何技术细节入口
