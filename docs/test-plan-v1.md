### 首次密码修改测试（新增）

对应门禁：G-10。验证 `must_change_password` 的服务端强制机制。

| 编号 | 验证内容 | 判定标准 |
|---|---|---|
| T-P-01 | 初始状态 | 部署 CLI 设置初始密码后，`must_change_password = true` |
| T-P-02 | 服务端强制拦截 | 该标志为 true 时，**直接请求任意管理端点**（绕过前端跳转）均被拒绝，不返回任何业务数据 |
| T-P-03 | 例外端点 | 仅修改密码端点与登出端点可访问 |
| T-P-04 | 拦截层级 | 拦截发生在认证中间件层，新增端点无需额外改动即自动受保护 |
| T-P-05 | 新密码不得与初始相同 | 用初始密码原样重填时被拒绝 |
| T-P-06 | 修改成功后的状态 | 标志清除、`password_updated_at` 更新、**其他全部会话被吊销**、写 `password_change` 审计 |
| T-P-07 | 重置后重新置位 | 业务负责人经 CLI 重置密码后，`must_change_password` **重新变为 true** |
| T-P-08 | 密码强度下限 | 少于 12 字符或与用户名相同时被拒绝 |
| T-P-09 | 审计不含密码 | 上述全部流程的审计记录中不出现明文密码或哈希 |

> **T-P-02 是本组核心**：只做前端跳转的实现会在此失败。初始密码经过部署脚本、CLI 历史或运维传递环节，属于已知暴露面，"强制修改"必须是服务端行为。
>
> **T-P-05 存在的理由**：不比对新旧密码，管理员原样重填一次即可清除标志，强制修改形同虚设。
>
> **T-P-07 常被遗漏**：重置产生的临时密码同样经过人工传递，若重置后不重新置位，该临时密码可能长期有效。

## 3A. token 不存在测试（新增）

对应门禁：G-08、G-10、G-12。验证 G-02 第一轮参谋审查修正的统一 200 策略。

| 编号 | 验证内容 | 判定标准 |
|---|---|---|
| T-N-01 | 随机不存在的 token | 返回 **200**，内容为无效链接提示页 |
| T-N-02 | 四种状态状态码一致 | 正常、停用、未上传、不存在**全部返回 200**，无一例外 |
| T-N-03 | 格式非法的 token（长度错误、含非 Base32 字符） | 同样返回 200 提示页，**不返回 400/404**，不回显输入内容 |
| T-N-04 | 缓存头一致 | 四种响应均含 `Cache-Control: no-store`，**包括不存在的情形** |
| T-N-05 | 响应头集合一致 | 三种提示页的响应头集合（除 `Content-Length`）一致，不出现仅在某一状态下才有的头 |
| T-N-06 | 时延无显著差异 | 不存在与停用的响应时延分布无显著差异（不做提前短路返回） |
| T-N-07 | 不泄露内部信息 | 无效链接页不含产品编码、内部 id、SQL、堆栈、路径 |
| T-N-08 | 未命中限流 | 连续大量未命中触发收紧限流，并写入审计事件 |
| T-N-09 | 正常扫码不被误伤 | 同一 IP 下大量**有效** token 请求不触发未命中限流 |

> **T-N-02 是本组核心**。初版设计对不存在返回 404、对停用返回 200，仅凭状态码即可探测 token 是否对应真实产品。该用例直接锁定这一修正，实现若回退到 404 会立即失败。
>
> **T-N-09 与 T-N-08 必须成对**。只测"枚举被拦截"而不测"正常扫码不被误伤"，会导致限流被调得过严——真实场景下大量客户可能共用同一出口 IP，误伤的业务后果比枚举风险严重得多。
>
> **已知残余项（不作为失败判定）**：四种状态的页面**内容**仍不同，理论上仍可据内容区分。这是明确接受的残余风险（`security-design-v1.md` 第 2 节），因此本组**不设**"响应体不可区分"的断言——设了就是要求实现做一件业务上已决定不做的事。

### 二维码规格与印刷解码测试（新增）

业务负责人 2026-08-01 已确认规格，风险 5 关闭，本组用例据此可判定。

| 编号 | 验证内容 | 判定标准 |
|---|---|---|
| T-Q-08 | 规格符合 | 生成图片为 PNG、总尺寸 1024×1280 px；上方二维码主体为 1024×1024 px、纠错等级 H、静区 4 模块；下方 1024×256 px 完整显示产品名称 |
| T-Q-09 | URL 编码 | 二维码载荷为 UTF-8 编码的公开 URL，解码结果与数据库中 token 完全一致 |
| T-Q-10 | 载荷最小化 | 二维码内容**只含公开 URL**，不含产品编码、内部 id、版本号或附加参数 |
| T-Q-11 | 元数据剥除 | PNG 中不含 `tEXt`/`iTXt`/`tIME` 等元数据块，不泄露库版本、生成时间或路径 |
| T-Q-12 | 印刷后解码 | 实际打印件可被主流手机相机解码 |
| T-Q-13 | 最小尺寸打印 | 缩放至实际使用的最小印刷尺寸后仍可解码 |
| T-Q-14 | 遮挡容错 | 遮挡约 20% 面积后仍可解码（H 级纠错约 30% 冗余，留出余量） |
| T-Q-15 | 低光照/倾斜 | 弱光与 30° 倾斜角下可解码 |
| T-Q-16 | 名称标签与旧缓存 | 中文、英文和 120 字符名称完整显示；已有 1024×1024 无标签缓存会被原子替换为带名称图片 |
| T-Q-16 | 无中心 logo | 图片中心未嵌入任何图形，纠错冗余未被占用 |

> **T-Q-12 至 T-Q-15 必须用真实打印件执行，不能只用屏幕截图**。规格再合理也只是纸面参数——磨损、油污、反光、印刷精度都只在实物上才暴露。这是二维码印在产品实物上、且地址永久不可更换的直接后果：**印错了无法召回**。
>
> **T-Q-14 的阈值刻意低于纠错上限**：H 级理论冗余约 30%，用例只要求 20% 通过，留出印刷质量波动的余量。若按 30% 设阈值，实测勉强通过等于没有安全边际。
>
> **T-Q-16 存在的理由**：中心嵌 logo 是常见做法，会悄悄消耗纠错预算——用了 H 级却把额度花在 logo 上，等于抵消了面向磨损的容错设计。若未来业务要求加 logo，本组用例必须重跑并重新评估纠错等级。

| 编号 | 场景 | 判定标准 |
|---|---|---|
| T-V-11 | 上传内容与**当前版本**相同 | 拒绝，提示「与当前文件相同」；版本数、`pdf_files` 行数、当前指针**三者均不变** |
| T-V-12 | 上传内容与**某历史版本**相同，但不同于当前版本 | **允许**；版本数 +1；当前指针移向新版本 |
| T-V-13 | T-V-12 场景下的物理存储 | `pdf_files` **不新增行**，新版本复用已有同 `sha256` 的文件行，磁盘无重复副本 |
| T-V-14 | 重复上传旧内容后历史完整性 | 所有历史版本仍存在且可查看、可恢复，无任何删除 |
| T-V-15 | 与「恢复」的区别 | 重新上传旧内容 → 新增版本行 + `pdf_upload` 审计；恢复历史版本 → **不新增**版本行 + `version_restore` 审计（含 from/to 版本号） |
| T-V-16 | 连续场景 | v1(A) → v2(B) → 上传 A → 得到 v3(A)；此时版本数为 3，当前为 v3，v1 仍存在 |

> **T-V-12 与 T-V-11 的判定方向相反，必须成对存在**。规则只按"是否等于**当前**版本"判断，与历史版本相同不构成拒绝理由。实现若把判重范围扩大到全部历史版本，T-V-12 会失败——而这正是最可能出现的实现偏差（"去重"直觉容易被过度应用）。
>
> **T-V-13 是数据层断言**：内容相同不应重复占用磁盘，但**必须新增版本记录**。物理去重与业务版本是两件事，混淆会导致历史丢失。
>
> **禁止在 `pdf_versions` 上建 `UNIQUE (product_id, pdf_file_id)`**：该约束看似合理，实际会让 T-V-12 直接写入失败。若实现中出现此约束，T-V-12 即为其暴露点。
>
> **T-V-15 存在的理由**：重新上传旧内容与恢复历史版本的**业务结果相似**（当前内容相同），但版本历史与审计记录完全不同。不分别断言，两条路径的实现就可能被错误合并。

### pdf_versions 不可删除、不可修改测试（新增，第二轮补强）

对应门禁：G-10、G-13、G-14。验证数据层的只追加保护。

| 编号 | 场景 | 判定标准 |
|---|---|---|
| T-V-17 | 应用无删除入口 | 不存在任何可删除历史版本的界面、接口或管理端点 |
| T-V-18 | 直接 DELETE 被拒 | 以应用数据库账号对 `pdf_versions` 执行 DELETE，**被数据库拒绝**（权限 + 触发器） |
| T-V-19 | 直接 UPDATE 被拒 | 以应用数据库账号对 `pdf_versions` 执行 UPDATE（尤其修改 `pdf_file_id`），**被数据库拒绝** |
| T-V-20 | `pdf_files` 同样受保护 | 对 `pdf_files` 的 UPDATE 与 DELETE 均被拒绝 |
| T-V-21 | 权限配置可验证 | 查询系统表确认 `app_rw` 对这两张表**只有 SELECT 与 INSERT** |
| T-V-22 | 触发器存在且生效 | 即便使用具备表权限的账号，触发器仍拒绝 UPDATE/DELETE |
| T-V-23 | 物理文件不删除 | 任何操作序列后，文件卷中的历史 PDF 文件均仍存在 |
| T-V-24 | 全流程后历史完整 | 经历多次上传、恢复、停用、启用后，历史版本数量**只增不减**，且每一版内容可正确读出 |

> **T-V-19 比 T-V-18 更重要，却更容易被漏测**。修改 `pdf_file_id` 可以让一条历史版本"指向另一份内容"——记录还在、内容被掉包，比直接删除更隐蔽，同样摧毁可追溯性。只防 DELETE 不防 UPDATE，等于只锁了前门。
>
> **T-V-21 与 T-V-22 分别验证两道防线**：权限层挡住应用发起的操作，触发器挡住任何来源的操作（含误用高权限账号执行的脚本）。两者覆盖面不同，缺一不可，因此必须分别断言，不能只测"删不掉"就算通过。

### 并发上传相同 PDF 测试（新增，G-02 门禁复核补强）

对应门禁：G-13。验证产品锁边界与锁内复核判重。

| 编号 | 场景 | 判定标准 |
|---|---|---|
| T-C-01 | 两个请求并发上传**同一份 PDF**（当前版本为其他内容） | 结束后**只新增 1 个版本**；另一请求被拒绝并提示「与当前文件相同」 |
| T-C-02 | 上述场景的存储副作用 | `pdf_files` 只新增 1 行；正式存储中该内容只有一份 |
| T-C-03 | 高并发重复 | 同一份 PDF 由 5–10 个请求同时上传，最终版本数仍只 +1 |
| T-C-04 | 并发上传**不同内容** | 两份不同 PDF 并发上传，两个版本均创建，最终当前版本恰为其中之一，无中间态 |
| T-C-05 | 锁内复核生效 | 构造"锁外读到旧当前版本"的时序（如在哈希计算阶段插入延迟），验证锁内重新读取当前版本后仍能正确拒绝 |
| T-C-06 | 锁粒度 | 不同产品的并发上传互不阻塞，可并行完成 |
| T-C-07 | 锁持有时间 | 文件校验与 SHA-256 计算发生在锁外（可通过锁等待时长不随文件大小线性增长确认） |
| T-C-08 | 并发上传与恢复 | 上传与恢复历史版本并发时，结束后当前版本恰有一个且指向确定结果，无"零个"或"两个"当前版本 |

> **T-C-01 是本组存在的全部理由**。初版设计把判重放在锁与事务之外：两个并发请求都在锁外读到当前版本为 v1（哈希 A），都判定"与新文件哈希 B 不同"，于是都写入——产生两个内容完全相同的版本。串行执行时第二次本应被 T-05 拒绝。**锁外读到的判重结论在写入时已经过期。**
>
> **T-C-05 是本组最难但最关键的一条**：它验证的不是"有锁"，而是"锁内**重新读取**了当前版本"。一个先在锁外判重、再取锁写入的实现，在低并发下 T-C-01 也可能偶然通过；只有主动构造时序才能稳定暴露。
>
> **T-C-07 防止过度修正**：把哈希计算也塞进锁内虽能消除竞态，却会让大文件上传长时间独占产品锁。断言锁等待时长不随文件大小线性增长，可确认昂贵操作仍在锁外。

### 文件移动失败恢复测试（新增，G-02 门禁复核补强）

对应门禁：G-13、G-14、G-15。验证"先移动文件、后提交事务"的失败方向与孤儿处理。

| 编号 | 场景 | 判定标准 |
|---|---|---|
| T-C-09 | 文件移动失败（目标不可写） | 事务不提交；**无版本记录、无 `pdf_files` 行、当前指针不变**；返回明确错误 |
| T-C-10 | 移动成功但事务提交失败 | 产生孤儿文件；**数据库中无任何该版本的痕迹**；当前指针不变；扫码行为不受影响 |
| T-C-11 | 孤儿文件不破坏业务 | T-C-10 之后，所有既有产品扫码、版本查看、恢复功能**全部正常** |
| T-C-12 | 孤儿自愈 | T-C-10 之后重新上传同一份 PDF，成功创建版本，且**不重复占用存储**（复用既有孤儿文件） |
| T-C-13 | 失败留痕 | T-C-10 产生 `pdf_upload_rejected` 审计，`detail` 含已移动文件的哈希，可追溯到该次失败请求 |
| T-C-14 | 移动原子性 | 中断移动过程后，正式存储中**不存在部分写入的半个文件**（rename 原子性） |
| T-C-15 | 目标已存在不覆盖 | 上传内容与既有文件哈希相同时，**跳过移动、删除临时文件**，既有文件字节不变、修改时间不变 |
| T-C-16 | 对账报告只读 | 孤儿对账命令能列出无引用文件，**且不删除任何内容**；执行前后存储内容完全一致 |
| T-C-17 | 无自动清理 | 系统中不存在任何自动删除孤儿文件的任务、定时器或接口 |

> **T-C-10 与 T-C-11 共同确认失败方向选对了**。设计刻意选择"先移动文件、后提交事务"：失败时留下孤儿文件（仅浪费存储），而非留下指向不存在文件的数据库记录（扫码直接失效）。这两条用例验证的正是"失败后业务仍完好"。
>
> **T-C-15 存在的理由**：内容寻址下同一哈希对应同一路径，覆盖一个**已被其他版本引用**的文件，在写入中断时会损坏那些产品的现有版本。必须断言既有文件字节与修改时间均未变。
>
> **T-C-17 是一条"不该存在什么"的断言**。T-08 规定存储只增不减，为孤儿开自动删除路径等于在系统里种下"判断无引用即删除"的逻辑——该判断一旦有缺陷（并发窗口、备份恢复后引用未重建），删掉的就是真实业务数据且不可逆。第一期明确不做，用例负责确认它确实没有被"顺手"加进来。

### 二维码生成失败补偿测试（新增，G-02 门禁复核补强）

对应门禁：G-08、G-13、G-14。验证二维码作为派生缓存的定位与补偿机制。

| 编号 | 场景 | 判定标准 |
|---|---|---|
| T-C-18 | 二维码不在创建事务内 | 产品创建事务提交时**不包含**二维码生成；可通过事务耗时不随图像生成波动确认 |
| T-C-19 | 生成失败不影响产品创建 | 二维码生成/写入失败时，**产品仍创建成功**，事务不回滚 |
| T-C-20 | 缓存写入失败的表现 | 图片已生成但缓存写入失败时，**仍正常返回图片给用户**；写 `qrcode_cache_failure` 审计；用户无感 |
| T-C-21 | 缓存未命中即时生成 | 删除缓存文件后请求下载，**仍能得到正确二维码**（内容与规格与缓存版本一致） |
| T-C-22 | 生成结果确定性 | 同一 `public_token` 多次生成，输出字节**完全相同**（纯函数性质） |
| T-C-23 | 契约不符时拒绝生成 | 编码不符合 B-02/B-03 契约时拒绝生成，**绝不产生占位图、默认图或改名文件** |
| T-C-24 | 失败产品的可见性 | 生成失败的产品在后台标记「二维码生成失败」并显示原因 |
| T-C-25 | 批量下载跳过失败项 | ZIP 中不含生成失败的产品，且下载结果**明确列出被跳过的编码**，不静默省略 |
| T-C-26 | 手动重试 | 提供重试入口；重试可反复执行且无副作用 |
| T-C-27 | 导入不受二维码影响 | 批量导入 5000 个产品时，二维码在事务外逐个生成；单个生成失败**不影响其余产品，也不改变导入返回的三个计数** |
| T-C-28 | 导入事务时长 | 导入事务持有时间不随二维码生成耗时增长 |
| T-C-29 | 验收标准 1 仍满足 | 新建产品后**立即**可获得二维码（缓存未命中时即时生成，不返回"稍后再试"） |
| T-C-30 | 对账报告 | 只读报告可列出「已创建但无有效二维码」的产品，不执行任何删除 |

> **T-C-23 是本组最重要的一条**。二维码会被印到产品实物上且不可召回——发出一个文件名与编码不一致的图片，比不发图片严重得多。T-06 要求契约不符时拒绝生成，用例必须确认实现没有"友好地"用占位图或改名文件兜底。
>
> **T-C-27 与 T-C-28 针对批量放大效应**：单个产品的二维码生成耗时可忽略，乘以 5000 就是分钟级的事务持有时间，会长期锁表并阻塞其他写入；更糟的是任何一个生成失败都会回滚整批已校验通过的产品。这两条用例锁定"二维码在事务外"这一修正。
>
> **T-C-22 解释了为什么无需复杂补偿**：二维码是 `public_token` 与规格的纯函数，任何时刻可确定性重建，因此它是缓存而非状态。缓存丢失只影响性能、不影响正确性——这正是它可以被移出事务的根本原因。

### Excel 文件大小与解析防护测试（新增，第二轮补强）

| 编号 | 场景 | 判定标准 |
|---|---|---|
| T-I-13 | Excel 超过 10 MB | 拒绝并提示；**在解析之前拒绝** |
| T-I-14 | 大小检查先于解析 | 超限文件**不进入解析流程**；可通过无解析日志、无解析耗时、内存无峰值确认 |
| T-I-15 | 流式中断 | 超限文件不先完整落盘再判断，接收过程中即中断 |
| T-I-16 | ZIP 炸弹 | 压缩比异常（解压后体积远超阈值）的 xlsx 被拒绝，进程内存不出现异常增长 |
| T-I-17 | XXE / DTD | 含外部实体或 DTD 声明的 xlsx 被拒绝或安全忽略；**不发起任何外部网络请求**、不读取本地文件 |
| T-I-18 | 解析超时 | 构造的高耗时文件触发超时中断并拒绝，不长期占用工作进程 |
| T-I-19 | 嵌入内容 | 含宏、嵌入对象或外部链接的 xlsx 不被执行、不被跟随 |
| T-I-20 | 正常边界 | 接近但未超过 10 MB 且 ≤5000 行的合法文件**正常导入成功** |

> **T-I-14 是本组核心**。行数限制只有解析之后才能生效——xlsx 是 ZIP 压缩包，恶意小文件可在解压时膨胀到极大体积，在"行数检查"生效前就耗尽内存。只测"超限被拒绝"而不测"拒绝发生在解析之前"，会让一个先解析后判断的实现照样通过。
>
> **T-I-20 与 T-I-13 必须成对**：只测拒绝不测放行，阈值被误设得过低（比如 1 MB）也不会被发现。

### 导入失败审计测试（新增，第二轮补强）

对应门禁：G-13、G-14。验证审计事务隔离策略。

| 编号 | 场景 | 判定标准 |
|---|---|---|
| T-A-01 | 格式错误整批失败 | 产品总数**不变**（零持久化）**且** `product_import` 审计记录**存在**，`result=failure` —— 两个条件必须**同时**成立 |
| T-A-02 | 失败审计的内容 | `detail` 含错误行数与三类计数；成功新增数为 0 |
| T-A-03 | 审计不随回滚消失 | 业务事务回滚后审计仍在，证明其写入独立于业务事务 |
| T-A-04 | 超限导入的审计 | 文件超 10 MB 或超 5000 行被拒时，同样产生 `result=failure` 审计并记录拒绝原因 |
| T-A-05 | PDF 上传拒绝的审计 | 校验失败、与当前文件相同被拒时，均产生 `pdf_upload_rejected` 审计 |
| T-A-06 | 成功路径的原子性 | 成功导入时业务数据与审计**同时存在**；不存在"有产品无审计"或"有审计无产品" |
| T-A-07 | 审计写入失败的处理 | 成功路径下审计写入失败时，业务变更一并回滚（宁可操作失败，不接受无审计的变更） |
| T-A-08 | 审计不可篡改 | 应用连接对 `audit_events` 无 UPDATE/DELETE 权限，尝试修改或删除被数据库拒绝 |

> **T-A-01 是本组存在的全部理由**。B-08 要求"格式错误失败时不得产生任何产品数据"，**但那约束的是产品表，不是审计表**。最容易出现的实现偏差是把"整批失败"理解成"什么都不写"——结果一次失败的导入完全无痕，反复投递恶意文件也不会留下记录。这条用例的两个断言必须同时检查，缺任一条都测不出该缺陷。
>
> **T-A-03 与 T-A-06 方向相反，共同锁定分路策略**：失败时审计必须**独立于**事务（回滚后仍在），成功时审计必须**在**事务内（同生共死）。只测其一，实现可能一律放在事务内（失败无痕）或一律放在事务外（成功不一致）。

> **T-I-05 与 T-I-03 必须成对存在**。若实现者把"重复"误当成"异常"，T-I-03 会失败；若把"格式错误"误当成"可跳过"，T-I-05 会失败。缺任一条，这个最危险的语义混淆就测不出来。
>
> **T-I-06 的断言必须是产品总数守恒**，而不是"返回了错误信息"。零持久化是结构性要求，只有对比前后总数才能验证。

## 7. 停用与启用测试

对应门禁：G-09、G-17

| 编号 | 场景 | 判定标准 | 对应 |
|---|---|---|---|
| T-D-01 | 停用后扫码 | 显示"该产品资料已停用" | 核心 7 |
| T-D-02 | 停用即时生效 | 停用后同一链接**立即**失效，无缓存宽限期 | B-07、T-02 |
| T-D-03 | 停用且从未上传 PDF | 显示"该产品资料已停用"，**不显示"资料暂未上传"** | 补充 10、B-10 |
| T-D-04 | 启用但未上传 | 显示"资料暂未上传" | 核心 2 |
| T-D-05 | 重新启用 | 原二维码恢复访问 | 核心 8 |
| T-D-06 | 停用期间管理端可上传 | 管理员可上传新 PDF；操作成功 | 补充 12 |
| T-D-07 | 停用期间管理端可查看/恢复历史 | 均可执行 | 补充 12 |
| T-D-08 | 停用期间公开入口始终停用 | 上述管理操作前后，公开链接**始终**只显示停用提示 | 补充 12 |
| T-D-09 | 停用期间换版后重新启用 | 客户访问的是**重新启用当时的当前 PDF**，即停用期间上传的新文件，而非停用前那一份 | 补充 12 |
| T-D-10 | 错误编码的处置 | 只能停用后另建正确编码；无修改、无删除、无"作废"状态 | 补充 4、B-04 |

> **T-D-09 是本组最容易被实现或测试写反的一条**。核心规则第 12 条字面是"重新启用后继续使用原二维码和当前 PDF"，孤立阅读容易理解成"回到停用前那一份"。v2 补充规则第 8 条已澄清为"重新启用当时的当前有效 PDF"。用例必须按澄清后的语义断言。

## 8. 端到端主线（G-09 强制）

必须作为一条连续主线跑通，中途不重置环境：

```
新建产品（即出码）
  → 扫码：资料暂未上传
  → 上传 v1 → 扫码：打开 v1
  → 上传 v2 → 扫码：打开 v2
  → 恢复 v1 → 扫码：打开 v1
  → 停用     → 扫码：已停用
  → 停用期间上传 v3
  → 扫码：仍显示已停用          ← 补充 12
  → 重新启用 → 扫码：打开 v3     ← 补充 12，不是 v1
```

全程断言：**二维码 URL 一字不变**；每一步的状态与当前版本指针正确；历史版本数量只增不减。

## 9. 备份与恢复测试

对应门禁：G-15、G-19

| 编号 | 验证内容 | 判定标准 |
|---|---|---|
| T-B-01 | 备份范围完整 | 数据库与文件卷**同时**纳入备份 |
| T-B-02 | 恢复一致性 | 恢复后每个产品的当前版本所指文件在文件卷中**真实存在** |
| T-B-03 | 恢复后主线可用 | 第 8 节主线可完整走通 |
| T-B-04 | 审计未丢失 | 审计事件数量与内容与备份时点一致 |
| T-B-05 | 回滚演练 | 应用与配置可回滚至上一版本并恢复服务 |

> T-B-02 是本组的核心断言。数据库与文件卷分离存储，只备份其一是最可能被忽略的故障；不做这条断言，备份的完整性就没有被真正验证过。
