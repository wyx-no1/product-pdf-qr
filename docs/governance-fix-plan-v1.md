## 0. 本方案的性质

本方案只修**治理文档与规则**，**不修改任何业务代码**。

修复涉及的四份文件中有三份是治理文件（`CLAUDE.md`、`quality-gates-v1.md`、`advisor-protocol-v1.md`），而本方案第 3 节恰恰要新增「Worker 禁止修改治理文件」的规则。

**说明**：该规则约束的是 **Worker**。本次修复由 Orchestrator 依业务负责人指示执行，走独立分支与 PR，由业务负责人批准合并——这正是新规则所要求的路径，不构成自我豁免。

## 1. 问题核实

以下四项均经实际核对，非推测。

### 1.1 G-02 状态存在两个相互矛盾的记录（已确认）

| 文件 | 位置 | 表述 |
|---|---|---|
| `docs/development-plan-v1.md`（main） | 第 12 行 | 「G-02 技术方案**已通过** DeepSeek Advisor 最终复核」 |
| `docs/development-plan-v1.md`（main） | 第 127 行 | 「G-02 **已由门禁责任方判定通过**」 |
| `docs/delivery-status.md`（main） | 第 13 行 | 「当前**等待 G-02 最终独立审核**，之后由门禁责任方判定 G-02」 |
| `docs/delivery-status.md`（main） | 第 120–121 行 | 「G-02 最终独立审核 ⬜ **未完成**」「G-02 门禁判定 ⬜ **未判定**」 |
| `docs/delivery-status.md`（main） | 第 127 行 | 「这些都**不等于 G-02 门禁已通过**」 |

**同一分支上两份文档给出相反结论。** 任何读者都无法从仓库判断 G-02 到底通没通过。

**部分已修复**：PR #6 的 `b008217` 已把分支上的 `delivery-status.md` 更新为「已通过（2026-08-01）」。但该修复**尚未合并到 main**，矛盾在 main 上仍然存在。

### 1.2 Phase 拆分在文档与实际执行之间脱节（已确认）

`docs/development-plan-v1.md` 定义的是**四个 Phase**：

| Phase | 名称 |
|---|---|
| 1 | 最小业务闭环（含工程初始化） |
| 2 | 后台管理能力 |
| 3 | 批量能力 |
| 4 | 质量增强 |

但**实际执行时 Phase 1 被拆成了两个子任务**：

| Issue | 标题 | 实际范围 |
|---|---|---|
| #3 | Phase 1：实现 PDF 二维码最小业务闭环 | 父任务 |
| #5 | **Phase 1-A**：工程初始化与基础环境 | 工程基础，无业务逻辑 |
| （未创建） | **Phase 1-B**：业务闭环开发 | 产品创建、上传、二维码、扫码 |

**`development-plan-v1.md` 从未更新以反映这个拆分。** 文档里没有任何 Phase 1-A / 1-B 的定义，而 Issue #5 与 PR #6 全部以 Phase 1-A 为名执行。

### 1.3 治理文件无任何保护规则（已确认）

`CLAUDE.md` 现有条款只保护 requirements：

> 最新已确认的 requirements 文档是唯一业务事实来源……历史版 `docs/requirements-v1.md` 不得用于指导新实现。

**没有任何条款禁止 Worker 修改治理文件本身。**

实际后果：Phase 1-A 中 Worker 修改了 `CLAUDE.md`（1 行）。该改动方向正确（把已失效的「没有功能代码」描述改为现状），但**它证明这条边界当前完全没有约束力**。

### 1.4 review-context 的定位未成规则（已确认）

`docs/advisor-protocol-v1.md` 规定了参谋意见的留存位置，但**未规定参谋审核所依据的材料必须是原始证据**。

实际后果：`review-context-pr6.md` 初版包含大量文件内容摘录，构成信息过滤层——参谋只能看到 Orchestrator 决定摘录的内容，而摘录者正是被审查方案的制定方。该问题已在 PR #6 中通过重写为纯索引解决，但**没有成为规则**，下次仍可能重演。

## 2. 修复方案

### 2.1 G-02 状态统一

**结论：G-02 已通过，判定日期 2026-08-01，判定方为业务负责人（门禁责任方）。**

| 文件 | 动作 |
|---|---|
| `docs/delivery-status.md` | 状态表改为 ✅ 已完成 / ✅ 已通过；新增「G-02 门禁判定记录」与「审核链路」（**已在 PR #6 的 `b008217` 完成**） |
| `docs/development-plan-v1.md` | 现有表述已是「已通过」，**无需改动**；但第 497 行「G-02/G-03 设计文档尚未纳入版本控制」已因 PR #4 合并而失效，须一并修正 |

**原则**：仓库中**不允许同时存在两个 G-02 状态**。任何文档提及 G-02 状态时，须与 `delivery-status.md` 的判定记录一致；`delivery-status.md` 为状态的唯一权威来源。

### 2.2 Phase 拆分规则

**正式定义**：

| Phase | 名称 | 范围 | 对应 Issue |
|---|---|---|---|
| **1-A** | 工程初始化与基础环境 | 目录结构、框架、数据库连接、migration 机制、初始 schema、配置、Docker、测试框架、CI、README。**无任何业务逻辑** | #5 |
| **1-B** | 业务闭环开发 | 产品创建、编码规范化、`public_token`、PDF 上传与版本管理、二维码生成、扫码访问 PDF | 待创建 |
| 2 | 后台管理能力 | 管理员认证、版本管理、停用/启用、恢复历史版本、审计补全 | 待创建 |
| 3 | 批量能力 | Excel 导入、预检、重复处理、导入审计 | 待创建 |
| 4 | 质量增强 | 并发测试、安全测试、二维码打印测试、备份恢复测试 | 待创建 |

**Phase 1-A 与 1-B 的门禁适用范围**：

| Phase | 适用门禁 | 不适用/未触发 |
|---|---|---|
| **1-A** | G-04、G-05、G-06、G-16 | 其余 12 项 |
| **1-B** | + G-07、G-08、G-11、G-12、G-13 | G-09 仅覆盖主线前四段，**不得标记通过** |

**同步范围**：

| 文件 | 动作 |
|---|---|
| `docs/development-plan-v1.md` | 把 Phase 1 拆为 1-A 与 1-B，更新总览表与阶段详述；修正已失效的第 497 行 |
| `docs/quality-gates-v1.md` | 新增「阶段适用性」小节，声明各 Phase 的门禁适用范围以 `development-plan-v1.md` 为准，并重申「不适用/未触发」的标注要求 |
| `docs/delivery-status.md` | 当前阶段更新为 Phase 1-A（PR #6 待审核），下一阶段为 Phase 1-B |

> **为什么 quality-gates 只加引用而不写 Phase 明细**：门禁标准本身应与阶段无关，否则每次拆分阶段都要改门禁文件，久而久之门禁会被阶段裁剪。把「哪个阶段适用哪些门禁」留在 `development-plan-v1.md`，`quality-gates-v1.md` 只声明这一分工，可避免耦合。

### 2.3 治理文件保护

**新增规则**（写入 `CLAUDE.md`）：

Worker **禁止修改**以下治理文件：

```
CLAUDE.md
docs/quality-gates-v1.md
docs/advisor-protocol-v1.md
docs/decision-register-v1.md
```

（`docs/requirements-v1.md` 与 `docs/requirements-v2.md` 已有更强的既有禁令，继续有效。）

**发现问题时的正确路径**：创建 **Governance Issue**，写明问题、影响、建议改法与依据，交业务负责人裁决；**不得自行修改**。

#### ⚠️ 必须设置的例外条款

**不设例外的话，这条规则会与已发生的合法工作直接冲突。**

Issue #5 明确要求 Phase 1-A 的 Worker「把 `docs/quality-gates-v1.md` 中所有『具体命令待补』占位替换为实际命令」——这是 Issue 授权的正当任务。若规则写成无条件禁止，Phase 1-A 将无法完成。

因此规则须包含例外：

> **例外**：当对应 Issue **明确授权**且改动**严格限于 Issue 指定范围**时，Worker 可修改治理文件。此类改动须在 PR 描述中单独列出并说明授权来源。**授权不得由 Worker 自行推定**。

**同时须记录本次的既有偏差**：Phase 1-A 中 Worker 修改 `CLAUDE.md` 属于 Issue **未授权**的改动。改动方向正确，但按新规则应走 Governance Issue。本次不追溯回退（回退会留下失效描述，风险更大），但作为规则确立的实例记录在案。

#### 强制手段的缺口（必须如实说明）

本规则目前**只是软约束**——依赖 Worker 遵守任务书。真正的硬约束需要：

| 手段 | 状态 | 说明 |
|---|---|---|
| GitHub CODEOWNERS | ❌ 未建立 | 治理文件改动须业务负责人 review |
| 分支保护 | ❌ 未建立 | main 要求 PR + 人工 approve + CI 通过 |
| CI 断言 | ❌ 未建立 | 检测治理文件改动并要求 PR 携带特定 label |

**建议**：本方案先确立规则，硬约束的建立作为后续独立任务。**在硬约束建立前，这条规则的实际强度与 Phase 1-A 中被违反的那条相同。**

### 2.4 审查证据链规则

**新增规则**（写入 `docs/advisor-protocol-v1.md`）：

1. **PR review-context 只能作为索引，不作为判断依据。** 它提供原始证据的位置，不提供内容、摘要或结论。
2. **原始证据必须可访问。** 索引中列出的每项证据都须给出可用的访问方式（GitHub URL、`git show` 命令、`gh run download` 命令等）。
3. **参谋不得仅依据索引形成判断。** 必须读取原始证据后再判断。
4. **某项证据无法访问时**，参谋须在意见中明确标注「该项未核验」，**不得**以索引描述代替核验，也不得因此跳过该项。
5. **索引与原始证据不一致时，以原始证据为准**，并须在意见中指出索引错误。
6. **索引须声明其盲区**：明确列出未列入索引的内容范围。

**理由**：参谋的全部价值在于**独立**。若参谋只能看到 Orchestrator 摘录的内容，而 Orchestrator 正是被审查方案的制定方，独立性即不成立——这不是执行不当，是结构性缺陷。

## 3. 修复的执行顺序与冲突说明

### 3.1 与 PR #6 的冲突

`docs/delivery-status.md` 同时被两处修改：

| 来源 | 内容 |
|---|---|
| PR #6（`b008217`） | G-02 状态修正 + 审核链路 + PR #6 审核状态 |
| 本次治理修复 PR | Phase 1-A / 1-B 拆分同步 |

**两者会在同一文件产生冲突。** 建议顺序：

1. **先合并 PR #6**（G-02 状态修正随之进入 main）
2. **再将治理修复 PR rebase 到更新后的 main**，只保留 Phase 拆分相关改动
3. 若需先合并治理修复 PR，则 PR #6 需 rebase

本方案的修复 PR 基于当前 `main` 创建，**已知会与 PR #6 冲突**，冲突范围仅限 `delivery-status.md` 的文档段落，解决成本低。

### 3.2 本方案不做的事

- 不修改任何业务代码
- 不创建 Worker
- 不建立 CODEOWNERS、分支保护或 CI 断言（作为后续独立任务）
- 不追溯回退 Phase 1-A 中已发生的 `CLAUDE.md` 改动
- 不改变任何门禁的严格程度
