### G-02 技术门禁复核反馈（已修正）

门禁复核提出的三项技术问题**全部已修正**，均为并发与失败路径缺陷：

| 问题 | 修正 |
|---|---|
| **上传判重存在竞态** | 产品行锁必须**先于**当前版本判重获取；当前版本读取与 size + SHA-256 比对**全部移入锁内**。原设计在锁外判重，两个并发上传同一份 PDF 的请求会各自创建一个内容相同的版本——锁外读到的判重结论在写入时已过期。文件校验与哈希计算仍留在锁外，避免长时间独占产品锁 |
| **文件移动与事务提交顺序未定义** | 明确为「临时区验证 → 获取锁 → 文件移入正式存储 → 事务提交」。这是在两种失败间的取舍：先提交后移动会留下**指向不存在文件的数据库记录**（扫码直接失效），先移动后提交只留下**孤儿文件**（仅浪费存储）。选择往无害方向失败。同时要求移动使用同文件系统内的原子 `rename`，目标已存在时跳过而**绝不覆盖** |
| **事务失败后孤儿文件无处理策略** | 第一期**不做自动清理，只做可见化**：孤儿具自愈性（内容寻址下同内容再次上传即自动转为被引用）；提供只读对账报告；失败时写审计并记录已移动文件的哈希。**刻意不实现自动清理**——为孤儿开删除路径等于在系统中种下「判断无引用即删除」的逻辑，该判断一旦有缺陷，删除的就是真实业务数据且不可逆，风险远大于存储占用 |
| **二维码生成阻塞长事务** | 二维码**移出所有事务**。关键认识：二维码是 `public_token` 与规格的**纯函数**，可确定性重建，因此属于派生缓存而非业务状态，没有理由参与事务。批量导入时该问题被放大 5000 倍——事务内逐个生成会导致分钟级锁表，且单个失败回滚整批 |
| **二维码生成失败无补偿机制** | 按失败类型分两类：**缓存写入失败**直接返回内存中已生成的图片、用户无感、写审计；**生成本身失败**（编码不符契约）则拒绝生成，**绝不产生占位图、默认图或改名文件**——二维码会被印到实物上且不可召回，发出文件名与编码不一致的图片比不发严重得多。失败产品在后台标记、批量下载明确列出被跳过的编码、提供手动重试。产品创建**永不因二维码失败而回滚** |

配套新增测试用例 **T-C-01 至 T-C-30** 共 30 条，覆盖锁边界、并发判重、移动失败恢复、孤儿处理与二维码补偿。
